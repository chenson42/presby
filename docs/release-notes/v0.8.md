## 0.8.0 — 2026-08-18

### Feature: The presby Domain Layer

**Background:** v0.7.0 and everything before it were the platform shell inherited from the starter — auth, roles, flags, audit, email. This release is the first that is *presby*: the church domain, and the isolation model it needs. There is no UI for any of it yet; the read paths exist and nothing surfaces them.

**Schema — 37 tenant tables** across `src/lib/db/domain/` (org, people, roll, officers, groups, authz, privacy, reporting), applied to Neon as migrations `0008`–`0012`:

- **Global person, org-scoped membership.** `people` holds the human; `memberships` carries roll status per organization. Decided on polity, not convenience: ministers of Word and Sacrament are members of the *presbytery* (G-2.0502) while ruling elders are members of the *congregation*, so one person's roll and service routinely sit at different orgs. The model was reversed twice mid-build before landing here (D1).
- **The roll is event-sourced.** `roll_actions` is append-only; an approved action is frozen by trigger and corrected by recording a `void`, never by update. The directory is a view of it, the annual statistical report a projection of it, per capita derives from it.
- **Officer terms, not officer flags.** Ordination is lifelong; service is termed. Session and diaconate rosters *materialize* from `officer_terms` by trigger and reject direct writes — materialized rather than a view because the permission resolver reads `group_memberships`, and a view would be invisible to it (F3).
- **Composite tenant keys.** Every tenant table declares `unique (id, organization_id)` and foreign keys between tenant tables are composite, so a row in org B cannot reference a person in org A (F2).
- **Partial adoption is the norm** (D9). Most congregations will never be tenants; a presbytery's launch-day job is holding records *about* non-tenants. `organizations.platform_status` carries that.

**Isolation — a database property, not an application one:**

- `presby_app` is `NOBYPASSRLS`; every tenant table is `FORCE ROW LEVEL SECURITY`. Without `FORCE`, Postgres exempts the table owner, RLS is silently inert, and every naive test still passes (F1).
- Two connections: `db` (RLS enforced, the app) and `getPlatformDb()` (bypasses RLS, platform pages only). `users.is_platform_admin` decides which *pages* are reachable, never whether a query is filtered.
- `withOrgContext()` verifies membership *before* setting the org GUC — RLS enforces tenancy, not authorization; the policy trusts whatever org id it is handed.
- The app now runs on the RLS-enforced connection by default, and the WebSocket pool (`drizzle-orm/neon-serverless`) is mandatory: neon-http has no session or transaction support, so it cannot carry a transaction-scoped GUC at all (F28). The isolation model dictated the driver.
- `scripts/test-rls.sql` — **36 assertions, and they must run as `presby_app`.** Run as the owner they prove nothing, because `neondb_owner` has `rolbypassrls = t`.

**Authorization:** `presby_effective_permissions(person, org, as_of)` resolves four arms — direct grant, group, administrative commission, session-granted delegation — and returns provenance with each permission, so "why does this person have this?" is answerable. `presby_available_organizations()` backs the org switcher.

**Roll read path:** `presby_roll_as_of`, `presby_roll_counts_as_of`, `presby_roll_changes`, plus `presby_reconcile_current_roll` and `presby_roll_cache_drift`. `memberships.current_roll` is a *cache* and cannot answer historical questions — reports replay through `presby_roll_as_of()`. It also drifts with the passage of time, because future-dated actions take effect on a day with no corresponding write (F29); the daily reconcile in `/api/cron/maintenance` exists for exactly that.

**Officer registers:** `presby_officer_roster(org, office, as_of)` and `presby_officer_history`. A second, non-consecutive term used to rewrite the first term's end date — the derived-group trigger destroyed officer history (F22).

**`/developer` — generated schema reference:** index, per-table pages, per-module ERDs, and `schema.json`. Table and column descriptions live in Postgres `COMMENT ON`, so the documentation cannot drift from the database. Each key invariant is marked `database`, `trigger`, or `paper` — **paper means the schema permits a violation and only review will catch it.**

### Fixes

- **LAN dev assets** — Next blocked `/_next/*` for phone-on-the-same-wifi testing, so the page rendered and never hydrated. `DEV_ALLOWED_ORIGINS` documented.
- **`<details>` on iOS** — a `display` rule on `<summary>` silently breaks native disclosure on iOS Safari. Two of the three bugs in this release were phone-only and invisible to `curl`, `tsc`, and `next build`.
- **ER diagrams** rendered, and table descriptions surfaced while collapsed.
- **OpenGraph metadata** added; the inherited starter title dropped.
- **Stale test guards** — deleted the obsolete neon-http `db.transaction()` guard (moot since the F28 driver switch) and re-pointed the cron-maintenance assertion at the F29 roll reconcile rather than a bare call count.

### Known Gaps

- **No UI for any of the above.** The roll read path is complete and nothing surfaces it.
- `organizations.path` is still `text`, not `ltree`; the ancestry trigger is unwritten.
- Derived groups are not seeded at org creation (F16) — the officer trigger raises until they exist.
- `ADMIN_ROLE` in `src/lib/permissions.ts` is still a wildcard, violating the no-wildcard invariant. Bounded (platform shell only, and the tenant connection cannot bypass RLS) but not removed.
- Photos: `people.photo_key` awaits an object-storage adapter (F13).
- 2 critical `@auth/core` advisories remain open pending the `next-auth` beta.32 upgrade, which needs its own e2e-gated auth pipeline.
