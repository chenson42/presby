## 0.11.0 — 2026-08-20

### Feature: Tenant self-service — directory, role administration, and support tickets

**Value:** `/o/<slug>` was a landing stub. This is the first content a congregation's own staff — not a platform admin — can act on inside it: see who belongs, grant and revoke the roles that were already sitting in the schema, and file a support ticket or leave lightweight feedback without going through email.

#### What's New

- **A privacy-filtered membership directory.** Field-level visibility rules (already enforced in SQL for reporting) now apply to a real UI a member can browse.
- **Role administration**, scoped narrowly: grant, revoke, and see who holds what against roles and permissions that already exist. It does not create a new role or a new permission — that stays an operator-only act. A self-lockout guard blocks a stated clerk from revoking their own last administrative grant by mistake.
- **A support-ticket loop**, filed by a designated role-holder and resolved as an ordinary human-plus-Claude-Code engineering task — there is no autonomous AI actor with standing write access to tenant data. Every ticket carries a category, an area, and a priority from a fixed vocabulary, chosen so an AI-assisted first pass has enough structure to act on without a round of back-and-forth. Attachments (PNG/JPEG/WEBP/PDF, magic-byte sniffed, 10MB) and five email-notification triggers are included.
- **A lighter-weight feedback on-ramp.** Any member can leave feedback about their congregation's experience; the ticket-filing role-holder can promote a piece of feedback into a formal ticket if it's worth acting on.
- **A platform-side triage view** at `/admin/tickets`, so tickets are workable without a database console.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `directory.view` | Browsing `/o/<slug>/directory` |
| `role_grants.manage` | Granting/revoking roles at `/o/<slug>/admin/roles` (bootstrap: `stated_clerk`) |
| `tickets.file` | Filing, tracking, and replying to tickets; promoting feedback; reading site contact messages (bootstrap: `support_contact`) |

All three surfaces ship behind their own flag (`org_portal.directory`, `org_portal.roles`, `org_portal.tickets`), seeded off.

#### New Routes

- `GET /o/<slug>/directory` — membership-scoped directory
- `GET /o/<slug>/admin/roles` — grant/revoke/view role assignments
- `GET /o/<slug>/tickets`, `/o/<slug>/tickets/new`, `/o/<slug>/tickets/[id]` — file, track, reply
- `GET /o/<slug>/feedback` — lightweight member feedback
- `GET /admin/tickets`, `/admin/tickets/[id]` — platform-side triage

### Feature: A congregation's own brand, live on its own pages

**Value:** every congregation was rendering in platform blue. A church's website and portal are supposed to feel like *that* congregation, not like a shared SaaS shell wearing a logo.

#### What's New

- An operator sets a congregation's color, logo, and type pairing at `/admin/organizations`; the pairing is derived into accessible light and dark ramps, never painted raw. Colors are picked once and checked against an AAA (7:1) contrast floor, not the legal minimum — this audience skews older, and the product's own content is about hearing loops and large-print bulletins.
- **Live today, wherever a member is signed into `/o/<slug>`**: brand tokens reach the full page, including menus and dialogs rendered through portals, not just the visible layout. Every route outside `(org)` — sign-in, the admin shell, the DECISION-040 access-denied page — stays in the platform palette by construction, so a branded page never leaks into a security-sensitive one.
- **A real design system, not just installed dependencies.** Hand-rolled buttons, tables, and form inputs across the admin, auth, and member surfaces were swept onto generated primitives; a tripwire now fails the build if a new one shows up hand-rolled.
- Dark mode is a real toggle now, not a stuck default — device-level today, account-level persistence tracked as a follow-up.
- A visual regression harness self-compares screenshots across 18 routes, both color schemes, and two viewports, and already caught one route with unstable sort order before it shipped.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `org.branding` | Setting or clearing an organization's brand at `/admin/organizations` |

Gated `ui.brand_theming`.

#### New Routes

- `GET /admin/organizations`, `/admin/organizations/[id]` — set, preview, and neutralize a congregation's brand
- `GET /admin/design-system` — internal reference for the generated primitives

### Feature: Public organization websites — the mechanism is built and tested, the rollout hasn't started

**Value:** a congregation's public website needs real content — real names, real photos, real service times — which can never enter this repository. The architecture keeps that content out of presby's own git history entirely while still letting the platform be the single runtime that serves it.

#### What's New

- **A private repository per congregation**, holding only page content and images — no application code. A small, public, versioned dependency (`presby-site-kit`) holds the actual shared rendering shell and a deliberately limited component set.
- **Content is staged, never fetched at request time.** A content repo's own CI validates a change and POSTs a structured bundle to presby, authenticated as the calling GitHub Actions workflow via OIDC — no stored credential, no callout back to GitHub when a visitor requests a page.
- **The "does this site exist" question is answered identically no matter why the answer is no.** A never-provisioned site, a suspended one, and a nonexistent slug all return the exact same response — proven at the database, unit, integration, and end-to-end layers, not just designed for it.
- An anonymous visitor can leave a message through a contact form; it's rate-limited, honeypot-protected, and shows up on the same ticket-loop tenant page a role-holder already checks.

This entire feature ships behind `sites.public_render`, **seeded off** — the mechanism is fully built and independently verified (real-Postgres integration tests, a real signed OIDC token, a real browser end-to-end run), but no real congregation has a provisioned site yet, and the reusable CI workflow a content repo would actually call hasn't been written. Three things are tracked before the first real one is: which GitHub visibility a content repo should use (a public repo would leak a suspended congregation's content even though the site itself correctly 404s), whether the shared rendering shell installs cleanly in the real production build environment, and whether a large image bundle fits the ingest endpoint's payload limit.

#### Permissions

No new tenant permission — visibility is a status check (`live` or not), not a grant. Provisioning a site or changing its status still requires the existing `FEATURES.ADMIN_ORGANIZATIONS`.

#### New Routes

- `GET /site/[slug]`, `/site/[slug]/assets/[key]` — anonymous, public
- `POST /api/sites/ingest` — GitHub Actions OIDC only
- `GET /admin/sites` — provision a site, set its status
