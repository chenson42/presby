## 0.46.0 — 2026-10-26

### Feature: developer portal, first step

**Value:** The Developer page now has a proper home and a frame around it, and it asks for your two-step sign-in code like the rest of the platform pages. This is the first step only: who can open it has not changed.

#### What's New

- **A proper home.** The Developer page now has a header with your account menu and a way back to PresbyPortal, a menu that works on a phone, and a start page with two sections.
- **Data model.** The old list of tables is now called Data model. Every existing link to a table or a diagram still works.
- **Documentation.** A new Documentation page lists the guides we plan to bring into the portal and says where each one lives today. Nothing there is built yet.

#### What has not changed, and what comes later

- **Access is the same as before.** Only a platform administrator whose account was flagged by hand can open the Developer pages. Nobody else can yet, and there is no screen for granting it.
- **Later steps.** A `developer` role that can be given to a person in any organization, and an API page (an inventory of the platform's internal endpoints and scheduled jobs, which says plainly that PresbyPortal has no public API), come in later releases. This release is not the finished developer portal.

#### Fixes

The Developer pages did not ask for your two-step sign-in code when your account requires one. They do now. 58 of the 105 tables were filed under "platform" with no diagram; every table is now filed under its real heading, and a test keeps it that way. The list of rules the system relies on was missing six of the project's principles and still carried a note that is no longer true. It now includes all six, and a test fails if one of the project's listed principles has neither an entry nor a recorded reason for being left out. Two working practices, No Real Data and Verify in a Browser, are deliberately left off, and the page says so. The wording of each entry is written by hand and is not checked. If the Developer page cannot check your access, for example while the database is unreachable, it now says so and offers Try again, instead of showing a technical error page or sending you somewhere else.

**For the operator.** No migration and no new setting; nothing needs to be applied before deploying. There is no what's-new post, because only a hand-flagged platform administrator can see these pages. Reading the Developer pages is not recorded in the audit log.

**Technical:** DECISION-258 and DECISION-261; findings F283, F284, F285 and F288 (`docs/schema-design-2.md` section 2ad). `src/proxy.ts` challenges `/developer` by path segment (so `/developerx` is not challenged) and the page gate repeats the check; `/developer/schema.json` answers JSON `401`, `403` and `503` itself. The admin console's header and navigation moved to `src/components/shared/console-*` and are used by both consoles. New: `src/lib/developer-portal/` (navigation, labels and the documentation rows as plain data, and the pure access decision), `src/lib/dev-docs.test.ts` (every table classified, every Key Invariants heading listed or excused) and `shell-boundaries.test.ts`. No `loading.tsx` exists under `(admin)/developer`, for the same reason as `/admin` (DECISION-251).
