## 0.26.0 — 2026-09-25

### A presbytery can email a congregation with no account a one-time link to file its annual statistical report

**Background:** Many congregations in a presbytery have no account on the platform and never will, but the presbytery still needs their annual statistical report. Until now the presbytery's clerk had to enter those figures by hand. This release lets the clerk send the congregation a link instead.

**Changes:**
- On the presbytery's reports page, a clerk with the statistics permission can issue a submission link for a member congregation and a report year, addressed to a named person by email, and can see whether each link is outstanding, expired, revoked or filed. Links expire, can be revoked, and only one can be outstanding per congregation and year. Links can only be issued for congregations the presbytery actually holds, and only for congregations that do not manage their own records on the platform — those file through their own portal.
- The recipient opens the link, sees the report form for that year, fills it in, states their name and office, and submits once. Nothing is saved if the submission fails, and a link that has expired, been used, or been revoked shows the same plain notice with no details.
- A filed report appears to the presbytery exactly as a report the congregation published itself would: as a published record it can read, with the figures the recipient attested.
- The feature ships switched off and is turned on per platform when a presbytery is ready.
- Behind the scenes: the report, its publication and the presbytery's copy are now written by one shared database routine whether a congregation publishes itself or files by link, so the two paths cannot drift apart. Issuing links and filing are both rate-limited.

## 0.26.1 — 2026-09-26

### Feature flags fail closed again; the public-site pages never open a database at build; the automated checks run again

**Background:** The project's automated checks had been failing on every change since late August, on a set of code-style errors that stopped the job before any of the substantive checks ran. Nobody was required to look, so nobody did. Fixing that surfaced a second problem hidden behind it: the helper that reads feature flags was supposed to treat a database error as "off" and never did, so a build with no reachable database crashed, and — more importantly — the one place that relied on that helper throwing to keep two-factor enforcement in place during a database blip would have silently lost that protection had the helper simply been patched.

**Changes:**
- A feature-flag read that fails now resolves to "off" and logs which flag, never the failing query. The two sign-in flags read the database themselves so a blip keeps sign-in open and keeps an already-required second factor required.
- The public congregation-site pages are declared dynamic, so a build never opens a database connection for them.
- The eight code-style errors are fixed on their merits (two of them were real component bugs; one was a date formatted in the server's time zone), the style check is part of the pre-push checklist, and the automated job runs it last so a style error can never again hide a build, security, or test failure. The job now runs on the Node version the project declares.
- One fix was reworked after review: the first repair for the branding form's stale-state bug would have cleared the "Brand saved." message on every save.
- No functional change on any screen beyond the branding form keeping its save message.

## 0.26.2 — 2026-09-26

### A database built from the migration files now matches the live one; CI can run every database-backed check

**Background:** Until now no database had ever been built from the committed migration files alone. When the first attempt was made, to give the automated checks a throwaway database of their own, it showed that the files did not reproduce the live schema: four columns differed, and a fresh database's permission lookup failed on its first call. The isolation test suite also depended on a helper function that lived only in the live databases, and the development fixture set collided with the platform's own seed.

**Changes:**
- A corrective migration brings the migration files and the live databases into agreement, and a new parity check keeps them there.
- The isolation suite's helper is now a committed file, and the fixture set loads cleanly on a fresh database — the documented from-scratch setup works for the first time.
- A new automated job builds a throwaway database from empty on every change, loads the fixtures, and runs all four thousand database-backed tests and the 520-assertion isolation suite. The end-to-end job is repaired to do the same. Both wait on two credentials the operator adds; until then they report themselves as skipped rather than pretending to pass.
- The rate-limit tests no longer depend on the local environment's settings.
- No functional change on any screen.
