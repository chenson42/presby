## ONE-LINE TAKE

## User Verbs

| Audience (surface) | Verb | Cadence |
|---|---|---|
| Prospective congregation (anonymous) | Reads what PresbyPortal does and does not do today; finds out how a congregation actually starts (the platform operator creates it and invites the first administrator; there is no self-service sign-up); finds who to ask | One-time, before any contact |
| Invited church administrator (anonymous, then newly authenticated) | Follows an invitation email; creates an account or signs in; enrols two-factor; lands on the portal; reads "first day" steps | One-time, high anxiety |
| Church administrator (authenticated, `/o/<slug>`) | Turns features on or off; adds people; proposes members; records Session and deacon terms; grants roles; sets branding; manages events and the public-calendar listing; files a ticket | On demand |
| Member (authenticated) | Signs in; uses a code or recovery code; changes password or email; switches congregations from `/home`; searches the directory; reads the calendar | Per session or on demand |
| Locked-out or confused user (anonymous or no roles) | Reads from `/signin` errors, `/totp`, `/no-organization`, `/access-pending`, "I can't see X" | On failure |
| Treasurer | Out of release 1 by default (Q5) | n/a |
| Maintainer (the keep-current verb) | Edits the help page in the same change that alters visible behaviour | Per release |

Two findings on the verbs:
- **Members cannot edit their own directory entry.** Staff with `people.manage` do that. The request's "directory entry" must be written as "how to read it and who to ask to change it", not "how to edit yours".
- **"Prospective congregations reading before signing up" has no sign-up to point at.** The first administrator is designated by the operator by email. That is the first thing page 3 below must say, and it needs a channel (Q3).

## Flows

**Flow 1 — Prospective congregation.** Marketing home, new "Help" link in the top bar → `/help` index grouped by "who you are" → "What PresbyPortal does today" → "How a congregation gets started" → contact path.
- Failure: unknown help URL gives a real HTTP 404 page with a link to the index. With no contact channel (Q3), the reader reaches a dead end, which is the worst outcome for this audience.

**Flow 2 — Invited administrator.** Invitation email → `/invite` → "Help with this page" link (a new in-app link) → the accepting-an-invitation page → back to the browser tab → account created or sign-in → two-factor enrolment → `/launch` → `/o/<slug>` → "Your first day".
- Failure: an expired or dead invitation shows one identical page. Help must describe that page's single meaning and never explain which cause applied (DECISION-189 enumeration rule).
- This flow runs straight through F166. See Gap 2.

**Flow 3 — Sign-in trouble.** `/signin` error, lockout, `/totp`, lost phone → "Can't sign in?" deep link (stable anchors: forgot password, locked, no code, recovery code) → outcome (reset email, wait, or contact the operator).
- Failure: a person who lost both phone and codes has no self-serve path today (reset is platform-admin only). Help must say so plainly and name the channel (Q3).

**Flow 4 — Inside the portal.** Avatar menu "Help", or a contextual link on a toggle-off or empty state (the careers page already explains how to turn the feature on) → the matching page, anchored → the reader returns by browser back, or "Open PresbyPortal" (`/launch`).
- Failure: a contextual link to a retired slug. Slugs are permanent, like org slugs (Gap 9).

**Flow 5 — Custom host.** `https://<church domain>/help` goes through the proxy's first branch, is rewritten to `/site/<host>/help`, and resolves to the church's own page if the content author made one, else the neutral 404.
- Platform help is never served there. The existing mechanism provides this with no new code, but it needs a test (Gap 8).

**Flow 6 — Keep-current (maintainer).** A pipeline's Phase 1 names the help pages it touches (new "Help impact" line) → design lists the edit → the implementer drafts it from the design's Copy table → QA copy-truthfulness covers the help diff → Phase 6 reads the page as the target reader.
- Failure: the pipeline finishes with no help edit and no "no user-visible change" note. That must read as a Phase 6 `SHIP WITH NOTES` at minimum.

## Gaps the Request Didn't Address

### 1. Per-congregation toggles and role-gated features, and how a page says what it needs
- The shipped UI is "absent, not disabled". The tile, nav entry and page simply do not appear, so a member or administrator cannot tell "off" from "not mine" from "not for my congregation type".
- Standard "Needs" block at the top of every task page:
  - **Who**: the role in plain words as the UI names it ("a church administrator", "the Session clerk"). Never `FEATURES` or permission keys in reader text. Keys live in registry metadata only.
  - **Turn-on**: the toggle's name exactly as `/o/<slug>/admin/features` shows it, and its default (calendar is on; careers, giving, parishes, public calendar, community, sensitive info are off).
  - **Congregation type**: giving applies to congregations and new worshipping communities, parishes to congregations. Say so.
  - **Operator-enabled**: custom domain and mail domain are not self-service. Say "we turn this on for you" and name the channel.
- One cross-cutting page, "Why can't I see this?", is a symptom → cause → who fixes table. It is the highest-value support-deflector in the set.
- Never "if your church has turned on…" without naming the toggle and where it is.

### 2. Features in flight: document shipped behaviour only, and mark the pages that depend on unshipped work

  - Today the only invitations are for the first administrator and first treasurer.

- **F166 (HIGH): first two-factor enrolment loses the recovery codes and `callbackUrl`.**
  - Writing "save your recovery codes" for the invite path now documents something the app does not reliably deliver.
  - Hold the "accepting an invitation" and "turn on two-factor" pages until F166 ships (Q1). The other 2FA content, using a code and using a recovery code at sign-in, is shipped behaviour and can go.
- **F343 (two-factor by role):** not in `docs/TODO.md` yet, so I could not read its scope.
  - Put every two-factor rule on exactly one page, "When you'll be asked for a code".
  - Link to it from everywhere else rather than restating it. Then F343 edits one page.

### 3. Screenshots: source, safety, freshness
- **Source.** The synthetic congregation is the `seed-dev.sql` fixture ("Alder Creek", `example.invalid` addresses) or `e2e-*` fixture orgs. A Playwright capture project is the natural generator. The repo already has Playwright, a `toHaveScreenshot` path template, and viewport projects.
- **Real-PII risk, concrete.**
  - The `development` Neon branch holds a real street address and phone for the sponsor congregation in `organization_profiles` (known since 2026-08-30, deliberately untouched).
  - The portal footer (`chrome_v3`) and the public site render org profile data.
  - `check:secrets` scans text, not PNG pixels.
  - Capture only from a from-scratch database seeded with `seed-dev.sql`. Verify the parent of Neon branch `pipeline-user-help` before using it, because a production-derived branch carries real data.
  - Use fixture users only, never a real session or the operator's account. The avatar menu shows an email.
  - Strip dev overlays.
  - Every committed image gets a human visual review in Phase 5.
- **Freshness.**
  - No pixel gating (flaky).
  - A manifest lists each image's route, fixture user, viewport, and capture release.
  - A cheap parity test requires every referenced image to exist, to have non-empty alt text, and to be listed in the manifest, with no orphans.
  - Regeneration is a one-command re-run (`npm run help:shots`). The keep-current rule says re-run it when a page it shows changes.
- **Role of images.** Text steps are the instruction, and images illustrate. Fewer is better: about 6–8 in release 1, phone-width crops plus one desktop hub shot. Light scheme only. No image shows a real brand.
- **Delivery.** Static files, in a directory not named after a tenant. The proxy matcher already skips images. Avoid `next/image` optimisation (the Next 16.3.8 Image SSRF advisory is open in TODO), so use plain `img` with width and height set (architect).

### 4. Content format and location
- No MDX dependency is installed, and none is needed. `react-markdown`, `remark-gfm` and `rehype-raw` are already direct dependencies (the admin release-notes viewer uses them).
- **Recommendation:**
  - Markdown bodies in the repo.
  - A typed TypeScript registry (`slug`, `title`, `summary`, `audience`, `needs`, `covers[]`, `labels[]`, `verifiedIn`, `order`, aliases). This avoids adding a front-matter parser.
  - Do **not** enable `rehype-raw`. Authors get the markdown allowlist, which also closes an HTML-injection door.
  - A parity test: every registry entry has a file and every file has an entry.
  - The renderer maps `#` to the page `h1` only. A test forbids a second h1.
- Alternative for the architect: typed TS content modules. They give stronger tooling but worse prose diffs and harder authoring by agents or the operator.
- **Runtime file reads need Vercel file tracing** (the admin viewer reads `docs/release-notes` at request time). Prefer static generation via `generateStaticParams` with `dynamicParams = false`. Pages should be fully static, with no `auth()` call, so there is no per-user render and they cache.
- **Architect decisions:** content directory (`docs/` is repo documentation; the architect decides), route group name, and static versus read-at-request.

### 5. Search and navigation at 360px
- No search in release 1. About a dozen pages is below any threshold where it helps. Search would need client JS or a dependency, and the browser's find already works.
- **Navigation instead:**
  - An index grouped by "who you are" (prospective, member, administrator).
  - A breadcrumb back to the index.
  - Previous and next within a group.
  - A collapsed "On this page" `details` on phones. Do not style `display` on a `summary` (the iOS bug in Key Invariants → Verify in a Browser).
  - A "Needs" block at the top.
  - An "Open PresbyPortal" button that goes to `/launch`.
- Tap targets are at least 44px. Tables get a focusable horizontal-scroll wrapper, because GFM tables overflow at 360px. Long words and URLs wrap. Images are `max-w-full`.
- Revisit search at about 30 pages.
- Adding a link to the marketing top bar at 360px, beside the wordmark and Sign in (and Continue plus Sign out when signed in), is tight. UX must check it, and the signed-in state is the worst case.

### 6. SEO and indexing
- The root layout is `noindex, nofollow` ("pre-release; revisit before launch"), and `robots.ts` is `Disallow: /` with `Allow: /site/`.
- **Default:** keep help noindex in release 1, matching the operator's posture. Per-page `generateMetadata` carries title and description already (so flipping is one place), and OpenGraph is inherited (link previews matter; see the layout comment). When indexing is turned on:
  - Add `Allow: /help`.
  - Add a platform sitemap listing only help pages. None exists today, although `/sitemap.xml` is in `PUBLIC_PATHS`.
- Canonical URL per page. Permanent slugs, with aliases and 301s on rename.

### 7. Accessibility
- One h1 per page. Headings strictly nested, with the author's headings starting at h2.
- A skip link and landmarks.
- Meaningful link text, with no "click here" and an external-link cue.
- `ol` for steps.
- Alt text required, enforced by the parity test.
- Tokens only, no palette literals.
- `text-base` body (the 16px floor), and the page description at the `dense` role. No `micro`, no `hero`. The h1 is the `title` role.
- Plain language, aimed at roughly grade 8, for church volunteers. Avoid "toggle", "tenant", "RLS".
- No `loading.tsx` under the help segment: the unknown-slug route calls `notFound()` and the invariant says it would turn into a 200.

### 8. Versioning versus "what you see may differ", and custom hosts
- One "current" truth, not a copy per release.
- Each page carries "Last checked against release X.Y.Z", from the registry `verifiedIn`.
- **The stamp is a claim, not a decoration.** It may only be moved by someone who re-walked the page (monthly documentation review, below), never by a bulk script.
- A global line on the index: "Written for congregations. If a screen looks different, tell us" with a link to the support route.
- Do not hedge every page. Hedging replaces being right.
- **Custom host:** `/help` there is the church's own content or the neutral 404.
  - Platform copy must never say "from your church's website go to `/help`".
  - Absolute help URLs in emails and the portal are always the platform origin.

### 9. Linking from in-app copy, and URL stability
- **Release 1 in-app links** (small, each a copy change that QA checks):
  - The marketing top bar.
  - The avatar menu ("Help").
  - `/signin` error states.
  - `/totp`.
  - `/no-organization` and `/access-pending`.
  - `/invite`.
- **Defer email-template links.** An email lives forever and its URLs are a promise, and the email-audience scan classifies every template.
- **Defer contextual links on feature pages** to a second pass, except the toggle-off states.
- A test asserts every in-app help link resolves to a registered slug or alias.
- **Referrer on token pages.** `/invite` arrives with its token in the query string. A help link from it should carry `rel="noreferrer"` (and external links on help too), so the token does not ride a Referer into access logs.

### 10. The standing keep-current rule (operator's second request)

**Where it is enforced.**
1. **New Workflow Rule 17 in CLAUDE.md** (orchestrator edits). Text: any change in "user-visible" scope below updates its help page, or states "no help impact" in the work-log, in the same housekeeping cluster as Rules 10, 13 and 14. Rule numbering: 16 is the last existing rule.
2. **Work-log template.** Add a "Help impact" line in Phase 1 (analyst names pages affected or new), carried into Phase 3 (the design's page list and Copy table) and Phase 6 (checked).
3. **`/release-notes` skill, Step 4.** Add a "Help" line beside the Functionality-map line. The release notes entry names the help page updated or "no help impact".
4. **Analyst Phase 6.** The walk reads each affected help page as the target reader against the shipped feature. A page that contradicts what shipped is `NEEDS REWORK`, and no help edit with no note is `SHIP WITH NOTES` at minimum.
5. **QA copy-truthfulness.** The same four checks apply to the help diff. The `labels[]` test (below) is a fifth, mechanical one.
6. **Monthly documentation review (tech-lead).** Re-walk every page's `labels[]`, and re-stamp `verifiedIn` only for pages actually re-walked.
7. **`/pre-push`.** Advisory only: "the diff touches an operator-facing or member-facing page and no help file changed". Not a hard fail.

**What "user-visible change" triggers it.** Any of:
- A page or route a non-operator can reach.
- A label, button or instruction string that a help page quotes.
- Who can do something: role, permission bundle, org-type scope, or a toggle's default.
- A new per-org toggle or a portal tile.
- A step in sign-in, two-factor or invitation.
- An email a person receives.
- A bug fix whose old behaviour a help page described or worked around (F166 deletes a caveat).

It does not trigger on: platform-operator-only surfaces (`/admin`, `/developer`), infrastructure, refactors, or schema changes with no screen change.

**Who writes it.**
- The tech-lead's design lists the pages and reuses the design's Copy table.
- The Phase 4 implementer drafts, because they know the behaviour.
- QA verifies.
- The analyst signs off at Phase 6.
- A new style guide (voice, "Needs" block, no permission keys, UI labels exact, no future tense) is part of this pipeline's deliverable.

**Cheap tripwires** (one `check:help` script, wired into `npm run check` as a ninth, with a unit test as in the other tripwires):
- Registry and file parity, with alt text and manifest parity.
- Every `ORG_FEATURE_CATALOG` key and every portal tile key is in some page's `covers`, or in a short explicit "undocumented" allowlist with a reason. The allowlist may only shrink. This is the best available signal, since a new toggle or tile is code-detectable.
- Every string a page lists in `labels[]` appears in a non-test `src/` file. A renamed button fails the check.
- Banned phrases: "coming soon", "will be able to", "planned", "in a future release".
- Every in-app help link resolves, and no published slug disappears without an alias.
- The functionality map names each registered slug at least once (the operator's "a feature's help page is listed in the map"). The map's volatile bullets gain a trailing `Help: <slug>` by convention.

The tripwires do not catch behaviour changes inside an existing feature. That part is the human rule above, and the design should say so.

### Adversarial pass (Pass 5)

- **Help promises what the app doesn't do.** Mitigations are the `labels[]` check, the banned phrases, and walking every flow as the real created person (as the Phase 6 rule requires). Highest-risk claims: recovery codes displayed again, statements emailed, anyone invited can approve, a member editing their own directory entry, a public website editable in the portal. The website content is edited in a git-staged repo by the operator or site author, not in the portal. Help must say so.
- **Help leaks which congregations are tenants.**
  - No real congregation is named. The marketing home's FPCW sponsor credit is a sanctioned exception to No Real Data on that one page, and it does not extend to help.
  - No counts ("used by N congregations").
  - The access-denied page's text is one string, byte-identical across statuses (DECISION-040). Help may explain that page only as "this one message appears whether or not the congregation uses PresbyPortal".
  - Examples use an obviously fictional name and slug.
  - Org slugs, if shown, are placeholders.
- **Real data in screenshots.** See Gap 3. The real-PII row on `development`, and an avatar menu showing an email, are the two concrete paths.
- **Stale pages.** The keep-current rule, the label and toggle tripwires, and the monthly re-walk. A page whose limitation depends on an in-flight feature carries the `limitation-until` marker.
- **Open redirect and injection.**
  - Help takes no user-controlled redirect parameter, so none is added. Keep it that way: `/help` must not accept `?next=` or `callbackUrl`.
  - `javascript:` and similar links in markdown are neutralised by the renderer's default URL transform, and raw HTML stays off.
  - Anchors are server-generated slugs from headings.
- **State-machine shortcuts.** None. It is static and unauthenticated.
- **Enumeration.** Unknown slugs and retired slugs return the same help 404. Help never branches on the viewer.
- **Self-targeting.** n/a.
- **Real contact address.** A real support address in a committed file trips the `check:secrets` off-allowlist email soft finding. Q3 settles which, and the annotation is `// leak-ok: role address`. The project's own sanctioned address style applies, never a person's.
- **External links.** `noreferrer`, `noopener`.

## Part 3 — Placeholders for planned features (revises my release-1 rule)

My earlier rule ("no roadmap, no coming soon, banned phrases") is **reversed in scope but kept in discipline**. Planned-feature placeholders are now in. The ban on future-tense text stays everywhere except inside one dedicated placeholder component. What follows is how to make them safe.

### What a placeholder is

- A registry entry with `status: "planned"`, rendered by one component. It states: the feature's name, who it is for, and "**Today:** what you can do instead". Nothing else.
- Fixed label text on every instance: "**Planned. Not available yet.** There is no date." The label is text, not color alone, and is repeated in the page title and heading, the index entry and the `<title>`.
- Never describe screens, buttons, steps or behaviour of the unbuilt feature. An invented label becomes a lie the day the design changes (the `labels[]` check would be meaningless for it). It does not say "will". It carries no dates, quarters or "soon", no priority ordering (list by area), and no call-to-action.
- **Where it appears:** a dedicated "Planned" page with one entry per feature, plus an optional end-of-page "Not available yet" block on the related shipped page. Never inline in numbered steps, where it would read as a step.
- **URLs:** planned entries live under `/help/planned/<slug>`. When the feature ships the real page gets its own slug and the planned URL redirects to it (the permanent-slug rule).
- **Indexing:** planned pages carry per-page `noindex` even after the site flips to indexable, so no search result is a "how to" for something that does not exist. Planned entries do not count as coverage in the "every toggle and tile is documented" tripwire.
- **Not a placeholder:** a defect. F166 (first enrolment loses the recovery codes) is a known issue, handled as a limitation line with a true workaround on the two-factor page, then deleted when fixed. Likewise anything tenant-specific: cutover and import plans name the sponsor congregation's private project, and a placeholder describes a capability for any congregation, never one tenant's work.

### What counts as planned: source of truth

`docs/TODO.md` is the single backlog aggregator (Rule 10), but it is hundreds of lines of defects, papercuts and reviews and is not a roadmap. The functionality map's "NOT built" line is a derived summary, already partly stale. Neither should decide on its own.

**Recommendation:**
- Placeholders come from a **short list the operator approves**, and each placeholder cites a TODO line through an explicit marker token, for example `[help:sign-in-invitations]`, placed on exactly one open (`- [ ]`) line.
- A tripwire fails if the token is missing, appears more than once, or sits on a Done or declined line.
- That makes expiry mechanical, because:
  - A cancelled plan means the line is removed or marked declined, and the test fails until the placeholder goes.
  - A shipped feature moves its line to Done (Rule 10, already required at ship), and the test fails until the placeholder is replaced.
- Entry criterion: the feature is user-visible, has its own queued or in-flight pipeline, and the operator has ruled it planned.
- Monthly documentation review re-confirms each placeholder with the operator ("still planned?"), and each records a `confirmedOn` date.

- Two-factor by role (F343).

### Keep-current

Rule 17 gets one more sentence: shipping a feature that has a placeholder deletes the placeholder and writes the real page in the same change. The tripwire above makes that mechanical. The "Help impact" line names the placeholder token. ### Public or signed-in only

**Recommendation: public.** Reasons:
- The repo already publishes TODO, STATE and every work-log, so a labelled placeholder adds findability, not exposure.
- It serves prospective congregations, who most want an honest "what is and isn't here".
- It keeps the principle that `/help` is reachable and cacheable signed out. A signed-in-only page needs session reads and breaks the static rendering the design wants.

Risk to name for the operator: public placeholders become an expectation surface, and a prospective congregation can read one as a commitment. The label, the "no date" line, per-page `noindex`, and no marketing-page link are the mitigations. Signed-in-only is the fallback if the operator prefers.

### Notes

**R1: proxy mechanism, decided once for both prefixes. Use a segment-boundary prefix bypass, not a registry-derived exact list (F348).**
- In `src/proxy.ts`, beside the `/site` bypass and before `edgeAuth()`: `p === "/help" || p.startsWith("/help/") || p === "/docs" || p.startsWith("/docs/")`. Never a bare `startsWith("/help")`, which would admit `/helpdesk`.
- Why not exact entries:
  - With an exact list, an anonymous visitor's typo'd, retired or pending slug is redirected to `/signin?callbackUrl=/help/typo` instead of the help 404. That is the dead end Phase 1 Flow 1 says must not happen.
  - It would also put a content registry, edited with every help change, into the proxy's import graph.
- The exact-path rule for `/invite` and `/file-statistics` exists because a token rides those paths. No token rides `/help` or `/docs`.
- The bypass is safe because R3 makes every page under these prefixes static and session-free by construction.
- It also keeps `/help` reachable by someone mid-enrolment, since the bypass sits before the 2FA gate.
- Tests in `src/proxy.test.ts` cover:
  - `/help`, `/help/x` and `/docs/x` pass without a session.
  - `/helpx` and `/docsx` redirect to sign-in.
  - A custom host's `/help` is rewritten to `/site/<host>/help`.
  - A signed-in user with an unverified required second factor reaches `/help`.

**R2: content format.** Markdown bodies plus the typed TS registry (the analyst's recommendation). TS content modules are rejected: backticks are common in help text and endemic in `/docs`.
- The registry `title` is the page's only `<h1>`. A content file may not contain a level-1 heading; `check:help` rejects one. That gives one source of truth for the title, and a test enforces the single h1.

**R3: static generation, not file tracing.** Every content route exports:
- `dynamic = "error"`: any accidental `auth()`, `headers()`, `cookies()` or `searchParams` fails `next build`.
- `dynamicParams = false`.
- `generateStaticParams()` from the registry's published entries.

Content is read only at build, so no runtime file read exists and no `outputFileTracingIncludes` entry is needed. QA confirms the routes are marked static (●) in `next build` output. `dynamic` is still supported in Next 16.4.2 because Cache Components is off. If `cacheComponents` is ever enabled, this lock moves to `ensureStatic` (a revisit trigger in DECISION-293).

**R4: the shared renderer.** `markdown-document.tsx` takes `{ markdown, resolveLink, resolveImage, headingBase }` and does no I/O.
- It accepts **no `rehypePlugins` prop**, so `rehype-raw` cannot be passed through it. The `/admin/docs` viewer's existing `rehype-raw` use is out of scope here; Increment 4 may migrate it.
- It keeps react-markdown's default URL transform, which neutralises `javascript:` links.
- It maps elements to explicit type-scale classes: `text-base` body, h2 `text-xl`, h3 `text-lg`, no `micro`. **No `prose` classes**: the typography plugin sets its own sizes, and `prose-sm` would put body text at 14px, below the 16px floor.
- `table` maps to the `ui/` primitive inside a focusable scroll wrapper.
- Heading anchors use a hand-written slug function with per-document de-duplication.
- Help's `resolveImage` accepts only manifest ids (`![alt](shot:<id>)`), so remote images and tracking pixels render nothing and fail the check.
- Help's `resolveLink` allows `/help/<published-slug>(#anchor)`, `/launch` and `/signin`, plus allow-listed absolute `https` links rendered with `rel="noreferrer noopener"`.
- Increment 4 supplies its own resolvers and `headingBase`: the internal docs have `#` headings, and none of help's content checks apply to them.

**R5: images.** Use static imports through the manifest, rendered with a plain `<img>` whose `width` and `height` come from the import. No `next/image` optimiser (the Next Image SSRF advisory in TODO is still open).
- Not `public/help/…`: files in `public/` are served at `/help/<file>.png` on **every** host, including a church's domain, where they would shadow the church's own path.
- Statically imported assets go to `/_next/static/media/` with hashed names. That is the same "any host" residual every platform asset already has, with no path collision.
- Light scheme only; about 6 to 8 images.

**R6: publication gating for pages of in-flight features (DECISION-294).** The registry has `status: "published" | "pending" | "planned"` and `requires?: "<token>"`. The token appears in `docs/TODO.md` as `[help:<token>]` on exactly one line.
- **The build** emits only `published` entries (and `planned` ones under `/help/planned`) in `generateStaticParams`, the index, the navigation and any later sitemap.
  - A `pending` page's markdown sits in the public repo, as work-logs do, but no route renders it. Its URL gives the same 404 as an unknown slug.
- **`check:help` rules:**
  - (a) A `published` page with `requires` needs its token's line to be **Done**. A page cannot go live ahead of its feature.
  - (b) A `pending` page must have `requires`, and its token line must be **open**. If the line is Done, the check fails with "feature shipped: publish its page", so pages cannot lag either.
  - (c) A `planned` page's token line must be open. If it is Done or declined, the check fails with "replace or remove the placeholder".
  - (d) A token missing or appearing twice fails.
  - (e) Several pending pages may share a token; a planned token belongs to exactly one entry.
- **Why "Done on main" is the right test of "in production":** the page and the feature ship in the same build artifact from `main`, which Vercel deploys. The page cannot appear before the code it describes.
- **Rejected alternatives:**
  - A release version: it is unknowable when the page is written, and it does not prove the feature is in that release.
  - A flag or toggle key: a runtime database read would make the help tree dynamic and break R3 and R8, and a per-org toggle is not "shipped".
- **TODO grammar (F349):** "In Flight" holds `- [x]` lines, so checkbox state alone cannot define Done.
  - **Done** = a `- [x]` line under `## Done`.
  - **Open** = a `- [ ]` line above `## Done` that does not contain the word "declined" (case-insensitive).
  - Any other combination fails as ambiguous.
  
  Phase 3 pins the grammar with fixture tests for each state.
- **The `labels[]` check runs on published pages only.** A pending page's labels name UI that is not on `main` yet, so the check bites at the commit that publishes the page. That is when it matters.
- **Coupling, named:** a pipeline whose integration commit moves a tokened TODO line to Done turns CI red until the same commit publishes the page. That is the forcing function. The Rule 17 text must tell the orchestrator that the integration commit publishes the page.
- **Pending is for new pages only.** A behaviour change to a published page (for example F166 removing its caveat) is edited in the fixing pipeline (Rule 17). F166's "accepting your invitation" and "turning on two-factor" become separate pending pages tokened on F166. Page 4 links to them only when they are published (R12 makes an earlier link a type error). There is no section-level conditional markdown.
- **Accepted residual (`paper`):** a feature merged to `main` behind a global platform flag that is off in production. The pipeline must not publish the page until the operator turns the flag on. Per-org toggles are covered by the Needs block. Also `paper`: a production flag flip by the operator changes what a page describes without any pipeline. Add it to the Rule 17 trigger list and the monthly re-walk.
