## Notable

### N-1 (carried forward, now sharper): `account/2fa/actions.ts` still duplicates the recovery-code helpers, and now also carries dead, buggy enrollment code

**Files:**
- `src/app/(admin)/admin/2fa/actions.ts:25-48` (`setFreshRecoveryCodesCookie`, `replaceRecoveryCodes`)
- `src/app/(account)/account/2fa/actions.ts:26-52` (identical helpers, `PENDING_TTL_MINUTES` constant) and `74-94` (`prepareEnrollment`)

Two separate issues bundled in the same file:

1. **The original N-1 duplication is still open.** `setFreshRecoveryCodesCookie` and `replaceRecoveryCodes` are byte-for-byte identical business logic in both `admin/2fa/actions.ts` and `account/2fa/actions.ts`, differing only in the cookie `path`. This was flagged 2026-05-17 and has not moved. Given `src/lib/totp-pending.ts` was created in the interim specifically to de-duplicate the *sibling* enrollment logic (N-3/M-3's fix), the recovery-code helpers are the one piece of 2FA logic that didn't get the same treatment. Extract to `src/lib/two-factor.ts` or a new `src/lib/recovery-codes.ts`, parameterized on cookie path — same fix recommended in May, still valid.

2. **New: dead code that reintroduces the N-3 bug if ever wired up.** `account/2fa/actions.ts:74-94` exports `prepareEnrollment(userId, email)`, which unconditionally mints a new secret and upserts the pending-enrollment row — no check for an existing unexpired row. This is exactly the bug that `getOrCreatePendingEnrollment()` in `totp-pending.ts` was written to fix (a user reloading the enrollment page gets a fresh QR code and their previously-scanned code silently stops working). `grep -rn "prepareEnrollment" src/` shows zero call sites outside its own definition and doc comment — `account/2fa/page.tsx` was correctly migrated to `getOrCreatePendingEnrollment` (see `page.tsx:11-14, 92-95`), but the old function was never deleted. The orphaned local `PENDING_TTL_MINUTES = 10` constant at line 26 exists solely to feed this dead function.

   **Fix:** delete `prepareEnrollment` (lines 70-94, including its header comment) and the now-unused `PENDING_TTL_MINUTES` constant (line 26) and the now-unused `generateSecret`/`encryptSecret`/`otpauthUrl` imports if nothing else in the file needs them (check before removing — `otpauthUrl`/`decryptSecret` may still be used elsewhere in the file for the management view). This is pure deletion, not a behavior change, but it removes a live landmine: any future edit that calls `prepareEnrollment` instead of the shared helper reintroduces a fixed bug silently, because both functions have plausible-sounding names and the same file exports both `clearFreshCodesCookieAction` (real) alongside `prepareEnrollment` (dead) with no marker distinguishing them.

### N-2: `changePassword` still has no rate limiting, five weeks after being flagged

**File:** `src/app/(account)/account/actions.ts:198-254` (comment at 247-250)

This is the same finding as 2026-05-17's N-6, unchanged. The code's own comment still reads "No rate limiting on failed password-change attempts. An attacker with a stolen session token could brute-force the current password." What's changed since May is the bar for fixing this: `checkRateLimit()` is now the established, load-bearing primitive for exactly this class of problem — it gates feedback submission (`src/app/(member)/feedback/actions.ts:101-112`), sign-in, TOTP verify, and password-reset request/consume. `changePassword` is now the *only* password-adjacent or session-adjacent mutation in the app that doesn't call it. Given the pattern is a 3-line call (`checkRateLimit(`pwchange:${session.user.id}`, { max: N, windowSeconds: W }, { userId, actor, reason })`) copy-pasteable from any of the four call sites above, this should move from "documented gap" to "fixed" before the next review — recommend adding to the punch-list with an explicit priority bump.

### N-3: Audit-of-the-audit-viewer is a documented gap, not a real one yet — verify the fork guidance is still accurate

**File:** `src/app/(admin)/admin/audit/page.tsx:1-6`

### M-2: `RawQueueRow` / `fromRaw()` snake_case mapping is a manual, hand-maintained shadow of `emailQueue.$inferSelect`

**File:** `src/lib/email/queue.ts:107-160`

Documented clearly (the comment at 103-106 explains why `db.execute` with raw SQL doesn't get Drizzle's camelCase mapping), and the CTE at lines 319-341 is a legitimate DECISION-014 exception so this isn't avoidable without restructuring the atomic claim. But `RawQueueRow` is a second schema that must be kept in sync by hand with any future `emailQueue` column addition — a new column added to `schema.ts` without a matching field in `RawQueueRow` would silently drop that column's value on every batch-claimed row (TypeScript won't catch it; `fromRaw` just won't populate the field). Worth a one-line comment at the top of `emailQueue` in `schema.ts` pointing back at `RawQueueRow` so the two stay linked in a future editor's mind. Low priority — no bug today, but a quiet coupling that outlives the comment that explains it.

### M-3: `warnIfDevVarsInProd()` and `EMAIL_DEV_REDIRECT_TO` console output use `console.warn`/`console.error`, not a shared logger

**File:** `src/lib/email/queue.ts:178-190, 204-207, 316, 399-404`

Same shape as the prior review's M-1 (`email.ts`'s dev-gated `console.warn`). All of these are either dev-only-guarded or genuine ops-observability logging in a cron/webhook context with no other logging surface (permanent-failure logging, lease-recovery logging). None violate "no `console.log` in production paths" — they're `warn`/`error`, and the one true `console.log` added this cycle (`src/app/api/cron/maintenance/route.ts:70`) is an intentional structured summary log in a cron handler, consistent with this pattern. Still, five call sites across two files doing ad hoc `console.*` with hand-built prefix strings (`"[email-queue] ..."`, `"[webhook/resend] ..."`, `"[cron/maintenance]"`, `"[feedback] ..."`) is now a large enough footprint that a tiny `src/lib/log.ts` wrapper (`log.warn(scope, msg, meta)`) would pay for itself. Cosmetic; not urgent.

## Observations

**O-1: Edge-runtime constraint remains fully respected, including in every new auth-adjacent module.** `src/lib/auth/local-login.ts` is the one new module that reads `feature_flags` from a Node-only auth path (`authorize()`/`jwt()` in `src/auth.ts`), and it carries an explicit "DESIGN CONSTRAINT" comment (lines 5-7) forbidding its import from `proxy.ts`. Verified: `proxy.ts` imports only `next/server`, `@/lib/auth/config`, and `@/lib/permissions`; `src/lib/auth/config.ts` imports only `next-auth` and the type-only `session-projection.ts`. No drift.

**O-2: Permissions vs. flags separation is not just correct but actively load-bearing in the new auth-mode-flags feature.** `auth.local_login` and `auth.require_2fa` are `feature_flags` rows (environment toggles), never `FEATURES` catalog entries — correctly modeled, since "is credentials sign-in enabled at all" and "is org-wide 2FA enforced" are environment questions, not per-user permission questions. The fail-open (`isLocalLoginEnabled`) vs. fail-closed-by-default (`computeEffectiveTwoFactor`) asymmetry is deliberately chosen per-flag based on the security consequence of each failure direction, and both directions are documented at the point of decision (`local-login.ts:17-30, 45-57`) rather than left implicit.

**O-3: Audit coverage on the new admin ops suite (email queue, audit viewer, feedback, what's-new) is thorough and the `check:audit` tripwire passes clean.** `npm run check` (both `check:audit` and `check:sql-date`) passes with zero violations against the full current tree. The one documented exception — the Resend webhook route is outside `check:audit`'s scan scope because it's a route handler, not an `actions.ts` file — is explicitly called out in the route's own header comment (`resend/route.ts:21-24`) rather than silently relying on the tripwire's blind spot.

**O-4: Server/client split holds across every new surface.** No `'use client'` directive was found on any page or layout added since 2026-05-17; every client component found (`feedback-prompt-card.tsx`, `feedback-status-control.tsx`, `retry-button.tsx`, `turnstile.tsx`, `fresh-recovery-codes.tsx`, `signin-credentials-form.tsx`) has a legitimate interactivity reason (optimistic UI, form state, a third-party script mount). No DB import was found in any client component.

**O-5: Timezone-safe date rendering is fully consistent — zero raw `toLocale*()` calls found outside `formatted-date.tsx` and its test.** Every new table/list surface (audit viewer, feedback triage, email queue, what's-new, home) renders timestamps through `<FormattedDate>`. The one deliberate exception to "read local, not UTC" — `shouldShowFeedbackPrompt()`'s UTC-vs-local-write asymmetry in `src/app/(member)/home/page.tsx:15-28` — is not a `<FormattedDate>` violation (it's a date *comparison*, not a *render*) and is correctly cited back to DECISION-023 in both the code comment and the schema comment (`schema.ts:392-394`).

**O-6: The feedback dev-loop's security invariants (hook count-only, clobber-prevention upserts, XSS-safe rendering and email) all independently verified and hold.** `scripts/feedback-check.mjs` provably never reads `body`/`category`/name from the DB (its own SQL is `SELECT count(*)`, no other columns). All three `feedbackPromptState` upserts (`submitFeedback`, `snoozeFeedbackPrompt`, `setFeedbackOptOut`) set exactly one column each in `onConflictDoUpdate.set`, matching the schema comment's invariant. The admin feedback page renders all member content as plain JSX text (no `dangerouslySetInnerHTML`), and the admin notification email passes every member-supplied string through `escapeHtml()` before HTML interpolation (`feedback/actions.ts:40-45`).

**O-7: `db.batch()` vs. raw-SQL-CTE convention (DECISION-014/018) is applied consistently and each exception is justified individually.** The email-queue atomic claim (`queue.ts:319-341`) and the maintenance cron's expired-token sweep (`route.ts:34-60`) both use raw `sql` with an inline comment citing why `db.batch()` can't do the job (batch writes can't reference a prior write's result in the same batch). No unexplained raw-SQL escape hatches found.

This cycle's new surface (v0.5→v0.6: `/home`, feedback loop, what's-new, email queue, audit viewer, lockout, Turnstile, auth-mode flags, CSP) was built to a noticeably higher bar than the 2026-05-17 baseline — every genuinely risky invariant (XSS, PII, clobber-prevention, signature verification, fail-open/fail-closed posture, Edge-runtime boundary) now carries an explicit comment at its point of risk rather than relying on convention. 6 of 10 prior findings are fixed outright, 1 resolved by correcting the doc instead of the code (a legitimate resolution), and 2 remain open — one of which (`changePassword` rate limiting) has now sat unfixed for a full review cycle while the pattern it needs became the app's standard everywhere else.
