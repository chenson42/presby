## Intent (harvest Tier 2 #15, 2026-07-01)

Expired password-reset and email-verification tokens accumulate forever:
the starter only deletes the requesting user's own token on re-mint, and
there is no scheduled cleanup. westervillelions solved it with an
opportunistic sweep on mint
(`/Users/cshenso/git/westervillelions/src/lib/auth/password-reset.ts:41,123`).

**New consideration since the harvest:** the starter NOW has a cron route
(`/api/cron/email-queue`, every 5 min) — a natural home for token GC that
the harvest's on-mint recommendation predates. Analyst should weigh:
on-mint sweep (zero infra, runs only when the feature is used) vs extending
the cron route (regular, but couples email-queue's worker to token
hygiene) vs a second cron path in vercel.json (clean but another schedule).
Also: trusted-device rows and TOTP pending-enrollment rows — do they
expire/accumulate too? Inventory every TTL'd table and today's cleanup
behavior; the fix should cover the real set, not just the two named.
Watch the enumeration-safety contract on the reset path (the sweep must
not change response behavior) and the recently-changed
password-reset/actions.ts (upsert + recordAudit + enqueueEmail).

## Phase 1 — Functional Refinement — 2026-07-01

**Owner:** analyst
**Status:** complete

### Summary

READY WITH NOTES. This is a background hygiene feature with no user-visible surface — no flows, no permissions, no flags. The full TTL-table inventory surfaced three tables that need coverage (passwordResetTokens, emailVerificationTokens, userTotpPendingEnrollments), confirmed that "trusted device" rows do not exist in this codebase, and found one functional bug: the cross-user pending-email collision check in requestEmailChange does not filter on expiresAt, meaning an expired but undeleted emailVerificationTokens row permanently blocks other users from requesting a change to that address. Placement recommendation is a new `/api/cron/maintenance` route with its own vercel.json schedule entry — not an extension of the email-queue cron. Audit events are not warranted; a structured log line per sweep run is sufficient.

### What I did

**TTL Table Inventory (all tables with expiresAt or time-bounded semantics):**

passwordResetTokens (`src/lib/db/schema.ts` lines 253-270)
- TTL: 60 minutes from mint.
- Max rows: 1 per user (uniqueIndex ix_pwd_reset_user on userId; upsert on conflict).
- Current cleanup paths:
  1. Re-request: onConflictDoUpdate overwrites in place — no orphan created.
  2. Consumption: consumeResetToken does DELETE WHERE token=$hash AND expiresAt > now() RETURNING — atomic, single-use. Consumed rows are gone.
  3. Password changed via /account: changePassword explicitly DELETE WHERE userId.
- Orphan scenario: User requests a reset, then never clicks the link and never changes password. Row stays until one of the above three paths fires — potentially forever.
- Accumulation bound: one row per user max. Bounded but not zero.

emailVerificationTokens (`src/lib/db/schema.ts` lines 229-247)
- TTL: 24 hours from mint.
- Max rows: 1 per user (uniqueIndex ix_email_ver_user on userId; upsert on conflict).
- Current cleanup paths:
  1. Re-request: onConflictDoUpdate overwrites.
  2. Successful verification: verify-email page deletes in the db.batch() alongside the users update.
  3. Expiry detected at verification: verify-email page deletes if tokenRow.expiresAt < new Date().
  4. Cancel: cancelEmailChange explicitly DELETE WHERE userId.
- Orphan scenario: User requests email change, never clicks link, never cancels, never re-requests. Row stays indefinitely with newEmail set to the target address.
- FUNCTIONAL BUG (note for tech-lead): requestEmailChange's cross-user pending collision check (`src/app/(account)/account/actions.ts` lines 110-119) queries emailVerificationTokens WHERE newEmail = X AND userId != self — with NO filter on expiresAt. An expired but undeleted row for user A targeting email X permanently blocks user B from requesting a change to X, returning "That email is already pending verification on another account." GC fixes this, but the tech-lead should also decide whether to fix the query defensively (add AND expiresAt > now() to the pendingTaken check).

userTotpPendingEnrollments (`src/lib/db/schema.ts` lines 147-159)
- TTL: 10 minutes from enrollment start (PENDING_TTL_MINUTES constant in /account/2fa/actions.ts).
- Max rows: 1 per user (userId is PK; upsert on conflict).
- Current cleanup paths:
  1. Re-enrollment start: prepareEnrollment onConflictDoUpdate overwrites.
  2. Successful confirmation: completeEnrollment deletes.
  3. Expiry detected at confirmation: completeEnrollment checks expiresAt and deletes.
- Orphan scenario: User opens enrollment QR page, scans, then abandons without entering a code. Row stays until the next enrollment attempt. Very transient (10-min TTL, one row max).
- Lowest priority of the three. Include in sweep for completeness; the upside is primarily cleanliness.

Tables confirmed NOT needing GC:
- verificationTokens (NextAuth magic-link table): Google OAuth only; no rows in this deployment.
- sessions: JWT sessions, not DB sessions; table receives no rows from NextAuth in JWT mode.
- userTotpRecoveryCodes: No TTL. Used codes are marked with usedAt but are replaced wholesale on regeneration via replaceRecoveryCodes(). No unbounded accumulation.
- emailQueue: Accumulates sent/failed rows but these are not TTL-based. Separate concern — out of scope for this feature.
- No twoFactorTrustedDevices table exists. Trusted-device functionality is not present in this codebase; the proxy.ts only checks twoFactorVerified from the JWT claim. Nothing to clean up.

**Placement recommendation: new `/api/cron/maintenance` route**

Rejected: extending email-queue cron. The email-queue route's contract is "process pending outbound email." Mixing token GC there creates conceptual coupling a future developer won't expect when reading the route. It also forces token GC onto the 5-minute email-queue schedule regardless of whether that cadence is appropriate.

Rejected: on-mint sweep (westervillelions pattern). Adequate for some scenarios but does not run on stale installations where users have abandoned flows and never retry. The emailVerificationTokens functional bug (stale rows blocking other users) needs periodic cleanup, not just per-request cleanup. On-mint also runs inside request latency.

Chosen: new `/api/cron/maintenance` route (`src/app/api/cron/maintenance/route.ts`) with a new entry in vercel.json. A daily schedule ("0 3 * * *") is appropriate — these tokens have 60-minute and 24-hour TTLs; cleaning once daily is more than adequate and keeps cron noise low. The route reuses CRON_SECRET (no new env var). Returns a JSON summary with deleted counts per table. This is the better teaching artifact: shows how to add a second maintenance cron alongside the operational email-queue cron.

**LIMIT posture (Neon HTTP driver):**
Drizzle does not support .limit() on DELETE directly for Postgres. The sweep must use a subquery pattern: `DELETE FROM table WHERE id IN (SELECT id FROM table WHERE expiresAt < now() LIMIT N)`. Recommended N: 500 per table per invocation. At daily cadence with bounded accumulation (one row per user per table), 500 is generous headroom. Tech-lead should confirm the raw SQL vs Drizzle ORM approach.

**Enumeration safety:**
No risk. The cron sweep runs independently of all auth flows. requestPasswordReset always returns { ok: true } regardless of sweep timing. The sweep result is never surfaced in any user-facing response.

**Audit events:**
Not warranted. Token GC is hygiene, not a security mutation. The `check:audit` tripwire (`npm run check:audit`) would require an AUDIT_ACTIONS key if the route is treated as an actions.ts file — but it is a route handler, not an actions file, so no tripwire applies. A structured console.log summary (e.g., `{ deletedPwdReset: N, deletedEmailVerify: M, deletedTotpPending: K }`) is the right output for ops observability.

### What I did

**`src/app/api/cron/maintenance/route.ts` — new file**

Shape mirrors `src/app/api/cron/email-queue/route.ts` exactly. No `limit` query-param (the email-queue has one for admin override; maintenance doesn't need it — the 500 cap is hard-coded for safety).

```typescript
import { sql } from "drizzle-orm";
import { db } from "@/lib/db";

const CRON_SECRET = process.env.CRON_SECRET;

// Vercel cron invokes via GET. See vercel.json for the schedule (0 3 * * *).
// Runs daily at 03:00 UTC to prune expired tokens from three tables.
// POST is intentionally omitted — no admin "run now" surface exists yet.
export async function GET(req: Request) {
  // Guard: CRON_SECRET must be set for the worker to run.
  // Returns 503 so the Vercel cron dashboard surfaces a visible failure
  // rather than silently no-oping — same pattern as the email-queue route.
  if (!CRON_SECRET) {
    return Response.json(
      { error: "Maintenance cron disabled: set CRON_SECRET to enable." },
      { status: 503 },
    );
  }

  const authHeader = req.headers.get("authorization");
  if (authHeader !== `Bearer ${CRON_SECRET}`) {
    return Response.json({ error: "Unauthorized." }, { status: 401 });
  }

  // DELETE expired rows, 500 per table per invocation.
  // Drizzle does not support .limit() on DELETE for Postgres; the subquery
  // form is required. RETURNING gives us the deleted count without a
  // separate SELECT. Untyped sql`` (no generic) is intentional — the type
  // parameter is unnecessary on execute() results.
  const [pwdResetResult, emailVerifyResult, totpPendingResult] =
    await Promise.all([
      db.execute(sql`
        DELETE FROM "password_reset_tokens"
        WHERE id IN (
          SELECT id FROM "password_reset_tokens"
          WHERE "expires_at" < now()
          LIMIT 500
        )
        RETURNING id
      `),
      db.execute(sql`
        DELETE FROM "email_verification_tokens"
        WHERE id IN (
          SELECT id FROM "email_verification_tokens"
          WHERE "expires_at" < now()
          LIMIT 500
        )
        RETURNING id
      `),
      db.execute(sql`
        DELETE FROM "user_totp_pending_enrollments"
        WHERE "user_id" IN (
          SELECT "user_id" FROM "user_totp_pending_enrollments"
          WHERE "expires_at" < now()
          LIMIT 500
        )
        RETURNING "user_id"
      `),
    ]);

  const summary = {
    deletedPwdReset: pwdResetResult.rows.length,
    deletedEmailVerify: emailVerifyResult.rows.length,
    deletedTotpPending: totpPendingResult.rows.length,
  };

  // Structured log for ops observability (Vercel Function logs / Datadog).
  console.log("[cron/maintenance]", JSON.stringify(summary));

  return Response.json({ ok: true, ...summary });
}
```

**Why `db.execute(sql\`...\`)` over Drizzle typed wrappers**

The architect endorsed raw SQL for this pattern. Drizzle's `.delete().where()` does not accept `.limit()` on Postgres; the subquery workaround requires `db.execute` anyway. Using `sql\`...\`` directly is cleaner and more readable than a Drizzle-typed wrapper around a non-standard query shape. The "untyped sql`` (no generic)" comment follows the established convention (see the lockout UPDATE in auth.ts).

**Why `Promise.all` over sequential awaits**

All three DELETEs are independent — no foreign-key dependencies between the three tables for the rows being deleted (all three already have `ON DELETE CASCADE` from users, but we're deleting by expiresAt, not by userId). Running in parallel halves wall-clock time.

**`vercel.json` — second cron entry**

```json

  "crons": [
    { "path": "/api/cron/email-queue", "schedule": "*/5 * * * *" },
    { "path": "/api/cron/maintenance", "schedule": "0 3 * * *" }

}
```
