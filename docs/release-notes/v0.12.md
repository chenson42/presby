## 0.13.0 — 2026-08-24

### Feature: Admin can create an organization

**Value:** Every organization on presby, until now, came from a raw SQL insert — there was no route, server action, or UI anywhere in the app that could create a new `organizations` row. Discovered mid-task while onboarding the platform's first real congregation (First Presbyterian Church of Westerville); this closes the gap so a platform admin can bring a new congregation onto presby without touching a database console.

#### What's New

- **`/admin/organizations/new`** — name, slug, type (congregation/presbytery/synod/GA), and platform status. The slug is permanent once set (an inline warning says so on the form itself, not just in documentation), so it's validated against both the same DNS-label rule the schema enforces and a new reserved-word list (`www`, `admin`, `api`, and every one of presby's own live top-level routes) that closes a real, previously-open collision risk against a future `<slug>.presby.app` subdomain.
- **Officer-term recording works from the first minute.** Creating a congregation now seeds its Session and Board of Deacons rosters (plus the membership-tracking group every organization needs) in the same transaction as the org itself — previously this required a manual database step before a session clerk could record a single officer term.
- Every failure mode — a taken slug, a malformed slug, a reserved slug, missing permission — surfaces a specific, human message; nothing falls through to a raw database error.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `admin.organizations` | Creating an organization at `/admin/organizations/new` — no new key, reuses the existing admin surface |

#### New Routes

- `GET /admin/organizations/new` — the create-organization form
- Server action `createOrganizationAction` (no new API route — every write on this admin surface is a server action)

### Infrastructure: presby-site-kit v3.4.0, and the platform's first real congregation content repo

**Background:** Building the first real (non-fixture) congregation site — First Presbyterian Church of Westerville's public site, migrated by hand from a real WordPress export into a new private content repo (`site-fpcw`) — surfaced two real gaps in `presby-site-kit`'s component set, the same way v3.1.0–v3.3.0's fixes were each found by building against real content rather than fixture testing alone.

**Changes:**
- `featureGrid`, `valuesGrid`, and `ministryList` blocks gained an optional per-item image, mirroring `staffList`'s existing photo support — previously only `hero`, `callout`, and `staffList` could carry an image at all, which was a real gap on a site built almost entirely from photo-and-text cards.
- A new `gallery` block — a single-image-at-a-time auto-playing carousel, with a play/pause toggle, pause-on-hover/focus, and `prefers-reduced-motion` support built in from the start rather than added later. `presby-site-kit`'s second client component, after `Nav`.
- presby's own dependency pin moved to v3.4.0.
- `site-fpcw` (private) now holds 14 real pages migrated from the church's WordPress export — not yet ingested; the organization itself isn't provisioned yet (see the Feature above) and real photos are still being gathered (`site-fpcw/MANIFEST.md` has the full list).

### Defect Fix: No way back to the public site from an access-denied page

**Problem:** A member who lost access to a congregation (or whose organization's relationship ended) landed on an access-denied or relationship-ended page under `/o/<slug>` with only a "Back to your organizations" link — no way to reach the congregation's own public site.

**Root Cause:** `OrgAccessDenied`/`OrgAccessEnded` never received the slug needed to link back to `/site/<slug>`.

**Fix:** Both components take a `slug` prop and render a second "Visit the public site" button. `tsc` caught every one of the seven pages sharing these components once the prop went required.

**Testing:**
- [x] Two new regression tests
- [x] Verified live: signed in as a seeded admin, hit a real access-denied page, clicked through to the real public site

### Verified

1720 unit tests passing (0 failed, 141 skipped without a DB connection; 1858/1861 with one loaded — the 3 remaining failures are `rate-limit.test.ts`, pre-existing and unrelated) · `presby-site-kit`'s own suite, 109/109 across the two new pieces · 14 new e2e cases for the org-creation flow and the public-site link-back, including a real 360px viewport pass · every block in `site-fpcw`'s 14 pages independently confirmed to actually render (not just parse as valid JSON) against the real `renderSiteBundle()` · typecheck, all four tripwires, and build all green.

Two real bugs were found and fixed while building this release, not designed around in advance: seeding presby-site-kit's platform-wide group templates needed the platform database connection, not the tenant one, because of the same RLS discipline that protects every other tenant table; and the originally-designed `.onConflictDoNothing()` seed pattern silently wasn't idempotent, because `group_types` has no unique constraint to conflict against — the same bug already existed, undetected, in an unrelated test file's own setup, now tracked for cleanup in `docs/TODO.md`.

**Still ahead of a real deploy**: `sites.public_render` stays off, First Presbyterian Church of Westerville's organization row hasn't been created yet (the tool now exists; using it is the next step), and `presby-site-kit`'s git-dependency install remains unverified against Vercel's actual build sandbox. All tracked in `docs/TODO.md`.

## 0.12.0 — 2026-08-21

### Feature: Public-site profile data, and a real component library to render it

**Value:** `/site/<slug>` (still flag-gated off) had the plumbing for a congregation's public website but nothing for it to actually say — no address, no service times, no social links, and the shared rendering package (`presby-site-kit`) was a stub that only ever showed a page title and "Content coming soon." This release closes both gaps together, and proves the whole path works with a real end-to-end run rather than tests alone.

#### What's New

- **A congregation's public-site profile** — address, phone, up to five named social links (Facebook, Instagram, X, YouTube, one other), and structured weekly schedules for both service times and office hours (day, start, end, an optional label). Set once by a platform admin at `/admin/organizations/[id]`, read anonymously through the same enumeration-safe function (`presby_published_site()`) that already gates page content — a site that isn't live leaks nothing new.
- **`presby-site-kit` is a real component library now** (v1.0.1, a separate versioned dependency): a hero, a four-up feature grid, a callout band, a service-times list, a staff directory, a values grid, a ministry list, an events list, a sermon-archive link, a donate link, and constrained Markdown prose — plus footer chrome (address, hours, social icons, a "get directions" link) composed automatically from the new profile data. Every piece is independently omittable: a congregation that hasn't set a phone number simply has no phone line, not a blank one.
- **Content is typed data, never executable code.** A content repo authors a page as a list of typed blocks (`{ type: "hero", props: {...} }`); an unrecognized block type is skipped, not rendered, not executed. This was a deliberate call against using real MDX, which lets an author embed arbitrary JavaScript — a private content repo is a lower trust tier than presby's own code, and this keeps every crossing of that boundary data-only. A hand-rolled Markdown renderer (no new dependency) backs the prose block; an adversarial test confirms a `<script>`/`onerror` payload in page content never executes, only ever renders as inert text.
- **Verified for real, not just in tests.** The whole pipeline — a genuine GitHub Actions workflow run, a real signed OIDC token, a live POST to a running dev server, a real render — was exercised twice this release, once to prove the mechanism and once after a real bug fix. It's the first time this architecture has been driven end-to-end by an actual external CI run rather than a simulated one.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `admin.organizations` | Setting a congregation's profile/service-times at `/admin/organizations/[id]` — no new key, reuses the existing admin surface |

#### Also

- **A real bug found by the end-to-end run, not by any unit test**: Postgres serializes a `time` column as `"10:15:00"`, not `"10:15"` — `presby-site-kit`'s first release only matched the shorter form and silently printed the raw value instead of formatting it. Neither side's own test fixtures used the real shape; only running the actual pipeline caught it. Fixed and shipped same-day as `presby-site-kit` v1.0.1.
- **Admin ticket lists no longer overflow.** A long ticket subject blew out the table column on both the platform triage queue and a congregation's own ticket list — `whitespace-nowrap` plus an unclipped max-width let text force the layout wide instead of truncating. Both now truncate with the full subject available on hover.

### Verified

1688 unit/integration tests (up from 1653) · 9 new e2e cases against `/admin/organizations/[id]`'s two new sections, run twice with no flakiness · `presby-site-kit`'s own suite (67 tests across 16 files, a separate repo) · a real GitHub Actions ingest run, twice, against a running local server via a public tunnel · isolation suite re-run clean (99 assertions, 0 failures) after the schema addition · typecheck, lint, build, and all four tripwires green.

One coverage gap was caught and closed mid-pipeline: QA's first pass on the profile-data admin UI failed for missing e2e coverage against the page's own established precedent (the brand-editor's CRUD smoke test); a targeted follow-up closed it and QA re-verified clean.

**Still ahead of a real deploy**, unchanged from v0.11: the `sites.public_render` flag stays off, no real congregation has a provisioned site, `presby-site-kit`'s git-dependency install is unverified against Vercel's actual build sandbox, and `site-<slug>` content-repo visibility (public vs. private) remains an open operational decision. All tracked in `docs/TODO.md`.
