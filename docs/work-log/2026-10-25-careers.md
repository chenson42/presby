## ONE-LINE TAKE

> A congregation's staff publish job openings on their own public site, anyone can apply with a resume without an account, a small hiring committee reads the applications (and nobody else does), and the applicant's personal data and file are removed one year after the position closes. The anonymous upload and the retention promise are the two places this can go wrong.

## What the fpcw design does not survive in presby

fpcw's careers module ran on a self-hosted server, wrote to Google Drive, and sat behind a WordPress site. Presby differs in six ways.

1. **The public asset route would serve resumes.**
   - `/site/<key>/assets/[key]` resolves *any* blob in the org by uuid.
   - It sends `Cache-Control: public, max-age=31536000, immutable` and the stored content type.
   - Resumes put in `blob_assets` through `store()` would be anonymously retrievable by anyone holding the key. They would also sit in shared caches that a purge cannot reach.
   - The authenticated ticket-attachment route (`private, max-age=3600`, `attachment` for PDF) is the right precedent. The public one is the anti-precedent.
2. **The blob adapter cannot honour a retention promise as built.**
   - `presby_app` holds SELECT and INSERT on `blob_assets`, and there is no delete in the adapter.
   - `store()` dedups on `(organization_id, content_hash)`. A candidate who applies to two postings with the same file shares one blob row between them.
   - Purging posting A's applications would then delete or orphan posting B's resume, which is still inside its retention window.
3. **A 10 MB upload does not reach the server.**
   - Next's default Server Action body limit is 1 MB, and `next.config.ts` sets no `serverActions` option.
   - Vercel's documented function request-body ceiling is 4.5 MB (to confirm in Phase 2).
   - The ticket form's "up to 10MB" copy is probably already false for the same reason. I did not run it, so this is unverified.
4. **Applicant PII would leak into shared tables.**
   - `audit_events` stores `ip` and `user_agent` on every row written through `insertAuditRow`.
   - `email_queue` keeps `to_email`, `html_body` and `text_body` forever. Platform admins can see it at `/admin/email_queue`, and only credential templates are redacted today.
   - `checkRateLimit` writes `RATE_LIMIT_BLOCKED` audit rows carrying the IP.
   - So "an audit trail with no applicant PII" is not automatic here, and neither is "email with no applicant PII".
5. **Nobody can be given `careers.applicants`.**
   - `assertPermissionSubset` means the person granting a role must hold every permission in it.
   - A new key that nobody holds can never be granted in a congregation. This is the F111 trap that `domains.manage` solved in 0057 by backfilling `founding_administrator`.
6. **There is no custom-host endpoint to mint a form token.**
   - `/api/*` is a neutral 404 on a church's own domain.
   - fpcw's `GET /api/careers/form-token` and `POST /api/careers/apply` do not exist as options.
   - Server-rendered tokens and an action or route under the site tree are the presby shape.

## Flows

**Flow 1 — Visitor reads openings**
- Entry: the site's Employment page (a `careers` live slot) or the platform `/careers` list.
- Step 1: the list shows published postings in manual order, each with title, location, type, pay range, summary, posted date and closing date.
- Step 2: "View and apply" opens `/careers/<posting-slug>` with the full description and the apply form.
- Outcome: the visitor reads the full posting.
- Failure: toggle off, site not live, or read failure all show the same "isn't available right now" notice. Zero postings shows the empty state. A draft or unknown slug is the site's one neutral 404. A closed posting shows "no longer accepting applications" with no form and `noindex`.

**Flow 2 — Applicant applies**
- Entry: the posting page.
- Step 1: the server renders the form with a signed form token (org, posting, issue time) and a hidden honeypot. The posting, org and site key are bound on the server, never form fields.
- Step 2: the applicant fills the fields and attaches one file. The form states what is kept, for how long, and that nobody is told to include SSNs or health information.
- Step 3: submit. Server order, cheapest first: honeypot (fake success, no spend), request size pre-check, rate limits (IP, per-site, per-email, global), Turnstile if configured, token age window, posting re-resolved to open and before its closing date, field validation, file sniff, per-posting daily cap, store file, insert row (one transaction), notifications.
- Outcome: on-screen confirmation naming the position, plus a generic confirmation email if an address was given.
- Failure:
  - Field errors are inline, with a persistent summary; this form does not rely on toasts.
  - File errors say what was wrong and the limit.
  - Rate limit says how long to wait.
  - Token expired or submitted too fast gives one generic "reload and try again".
  - A database failure says nothing was saved.
  - A posting that closed mid-form is refused with plain words.
  - Nothing the applicant typed may be wiped by a failed submit (G14).

**Flow 3 — Manager publishes a posting**
- Entry: `/o/<slug>/admin/careers` (placement is the architect's).
- Step 1: create a draft: title, location, type, pay min/max/unit, summary, closing date optional, rich-text description. A staff-only preview shows what the public sees.
- Step 2: publish; the posting appears on the next page load.
- Step 3: reorder with move up/down; close; reopen.
- Outcome: the list shows status, application count and position order.
- Failure: validation inline. Two managers editing at once get a "changed since you opened it" notice, not silent last-write-wins.

**Flow 4 — Reviewer reads applications**
- Entry: the Home tile (with its "new" badge) or the posting's Applications tab. The path is Home tile → posting list → count link → applications.
- Step 1: one card per application, newest first, every field visible with no expanders.
- Step 2: "Open resume" downloads through an authenticated handler. Nothing public, nothing inline.
- Step 3: "Remove application" (early redaction) behind an `AlertDialog`.
- Outcome: the reviewer reads, downloads, and removes on request.
- Failure: a manage-only holder never receives this data, and the tab is absent, not disabled. A missing or removed file gets a plain message.

**Flow 5 — Retention**
- Entry: the daily cron.
- Step 1: close postings whose closing date has passed.
- Step 2: for applications whose retention date has arrived, remove the personal fields and the file in one transaction and write one audit row (application id, posting id, kind, actor null).
- Outcome: a redacted application keeps only its id, posting, submitted date and "removed on" date.
- Failure: a failed removal leaves the application intact and retries next run. The run logs counts only.

**Flow 6 — Admin sets up the feature**
- Entry: `/o/<slug>/admin/features`.
- Step 1: flip the toggle.
- Step 2: the founding administrator adopts the hiring-committee role and grants it to the committee group, so membership drives access and rotation is automatic (see Q4).
- Step 3: the site author adds the slot and nav link.
- Outcome: a committee member gets the tile within the session-refresh window.
- Failure: if the toggle is on but no page carries the slot or nav link, visitors see nothing and the admin cannot tell. Show a status line (see G10).

## Permissions & Flags

  - `careers.applicants`, tier 3. This is my tier ruling. Applications are non-members' employment records. They hold contact details and third-party reference notes. Resumes and cover notes can imply age, health, family or immigration status. That is the highest tier, with the pastoral and medical data.

- **Flag(s):** none (operator rule). One per-org toggle, toggle-only, category `people`, provisioned off, a missing row meaning off. The tile and every public read compose the existing flag → category → toggle → permission chain.
- **Asked in this order:** site live, then toggle, then permission for staff surfaces.
- **Audit:**
  - Audit publish, close and reopen, as public-disclosure changes.
  - Audit resume download, early redaction, retention redaction, and the toggle (already audited).

  - Do not audit applicant submission, list views, posting edits or reorder.
  - A submission audit row would store the applicant's IP and user agent, which is exactly the PII the promise excludes.

## Gaps the Request Didn't Address

### Passes 1–4

**G1. Resume storage (blocks Phase 3 schema).**
- It cannot be `blob_assets` through the public asset route, and a purge needs a delete that the adapter lacks.
- Ruling for Phase 2: either a careers-owned file table with no public route, or `blob_assets` plus an allow-listed asset route plus a non-deduping salted hash.
- I lean to the former, because it makes erasure a per-row property and removes the shared-blob hazard.
- The tickets attachment route is the serving model: handler gated on `careers.applicants`, `Content-Disposition: attachment` with a server-generated filename, `private, no-store`, `nosniff`.
- No "Open in Drive" equivalent exists. The reviewer downloads the file.

**G2. Size ceiling (blocks the apply surface).**
- Cap resumes at 4 MB, not 10, unless Phase 2 finds a direct-upload path that fits the blob store.
- Raising `serverActions.bodySizeLimit` is global and widens the DoS surface of every authenticated action.
- A route handler under the site tree (not `/api`) allows a `Content-Length` pre-check and keeps the global limit untouched. It also works on a custom host through the proxy rewrite.
- Copy says "up to 4 MB". Re-verify the 1 MB claim in the tickets form and track it separately.

**G3. Retention versus "all deletes are soft" (operator ruling, Q2).**
- Reconcile by redaction. The application row is never deleted. A `SECURITY DEFINER` function nulls the name, email, phone, cover note, references and file reference, and stamps `redacted_at` and kind.
- The file bytes are the one thing that must be truly destroyed. A soft-deleted `bytea` still holds the resume.
- That is a narrow, documented exception to the soft-delete rule for PII under a legal retention clock. The audit row and the counts survive.
- The retention date is materialised when the posting closes, as fpcw did, so a scan is a single indexed predicate.
- **Backstop:** fpcw's "no closing date means never closes, clock never starts" lets applicants to a perpetually open posting sit forever. Add `purge_after = least(closed_at + 1 year, submitted_at + 2 years)`, so there is an absolute ceiling.
- **Reopen rule:** reopening must not let a manager extend retention indefinitely. Reopening resets the close-based clock, but never past the submission-based ceiling.
- Neon backups and point-in-time history outlive a delete. The copy must not say "permanently erased"; the history window is unverified.
- Applicants are never `people`, `households` or `contact_methods` rows. Otherwise "Never Hard-Delete a Person" collides with erasure, and applicant addresses would reach the directory or a mailing audience.

**G4. Permission bootstrap (operator ruling, Q4).**
- Nobody holds `careers.applicants` in a new org, and `assertPermissionSubset` forbids granting a key you do not hold.
- Unless it is backfilled onto `founding_administrator` (the 0057 pattern), the hiring-committee role cannot be granted in any congregation.
- If it is backfilled, the founding administrator can read applications. That breaks "a Church Administrator does not read tier 3 by default".
- Recommended default: both keys go into the founding-administrator bundle, as an accepted `paper` residual detected by the audit of downloads.

**G5. Home tile and badge.**
- The tile registry is deliberately flag/toggle-only and has no permission check.
- No count badge exists anywhere yet.
- The 7-day count must be computed only inside the `careers.applicants` branch, and the badge must never render for others. Where that read lives is the architect's call.
- A manager-only holder sees the tile but no badge.
- The accessible label must say "N new applications", not an unlabelled number.
- Seven days is a cliff: a week-old unreviewed application loses its badge. Show the latest-application date as fpcw did, since no per-viewer state exists.

**G6. Rich text.**
- Presby's public contract forbids `dangerouslySetInnerHTML`.
- Recommend storing a validated structured document, with paragraph, heading, bold, italic, bulleted and numbered lists, and http/https/mailto links only. It would be rendered as React elements, so no HTML ever reaches the DOM.
- Paste normalisation from Word and Docs needs an editor library. That is a new dependency, so Phase 2's call, with Tiptap/ProseMirror the likely candidate.
- Validate on the server (depth, node count, length), not only in the editor.
- fpcw's sanitize-HTML-twice approach also works but contradicts the public-tree contract.

**G7. Notifications.**
- A new template key must be classified in the email audience registry (CI enforces this).
- Recommend notifying holders of `careers.applicants` at their role address (`person:role`, the first use of that audience), with a generic body: "A new application was received for {Position}. Sign in to review." No name, no field values.
- Fpcw's shared jobs@ inbox has no presby analog unless a typed address is configured.
- The applicant confirmation goes to an unverified, attacker-typed address. Its body must say nothing the applicant typed, not even their name. A fixed body means it cannot be used to send arbitrary content in the church's name.
- `email_queue` keeps the recipient address and rendered body forever. Either extend the existing credential-style redaction to this template, or drop the confirmation email and rely on the on-screen confirmation (Q6).

**G8. The public URL and the site-integration step.**
- A live slot cannot read the request, so a per-posting page needs a platform-owned route.
- Recommend `/careers/<posting-slug>` on the same model as `/give`:
  - the static route beats the catch-all;
  - it uses `resolve…Site(key)`, `redirectIfNeeded` and `force-dynamic`;
  - it has no `loading.tsx`;
  - it has the one neutral 404.
- Also add a platform `/careers` list that falls through to the bundle's own `/careers` page when one exists, and the `careers` live slot for any content page. This gives a congregation with no site editor a working careers page and gives the posting page a valid back link.
- Reserve only `careers/<something>` in `RESERVED_SITE_SEGMENTS`, not exact `careers`. The reserved-path check is first-segment based today, so the change needs care.
- All links come from `SiteUrls` (add a method), never hand-built.
- Cutover checklist for the site author: place the slot on the Employment page and add the nav entry in the private site repo.

**G9. Closing dates and time zones.**
- `closing_date` is the last day applications are accepted, in the org's zone.
- The apply handler must check it itself and not rely on the cron closing the posting.
- Dates travel as `YYYY-MM-DD` text (`check:sql-date`).
- Pay is min ≤ max, non-negative, with a unit and sane caps.

**G10. Admin visibility and empty states.**
- A manager cannot tell whether the careers page is live. Show a status line ("Openings appear on /employment" or "No page on your website shows openings yet") from the published bundle, as the calendar pipeline proposed.
- A brand-new install shows a "Create your first posting" empty state.
- The applications tab shows "No one has applied yet."

**G11. Mobile and accessibility.**
- Everything at 360px, including the staff list, the editor toolbar and the apply form.
- The file picker must work on a phone, and targets are at least 44px.
- Errors are tied to fields (`aria-invalid`, `aria-describedby`), with a `role="alert"` summary above Submit.
- The honeypot is off-screen with `tabIndex=-1` and `autoComplete="off"`, and it must not trip browser autofill.
- Applicant text in the review card is at least 16px with wrapping (`overflow-wrap:anywhere`).

**G12. 2FA mid-enrolment.** The staff surfaces sit under `/o/*`, so the proxy pushes an unenrolled user to `/totp`. The public tree has no session. No change needed.

**G13. Track K.** The import is a one-time script in private notes (no real data in the repo).
- Import published and draft postings: descriptions convert from fpcw's small HTML subset, and slug, order, posted date and closing date carry over.
- Do not import applicants (Q11). The church's Google Drive and fpcw's retention clock end with the hard cutover, so the church owes a manual deletion date for in-retention resumes. Export a non-PII list (application id, posting, purge date, Drive file id) so this is auditable.
- Q7 ("Drive is link-only") stands for presby, which never touches Drive. The operator confirmation is still pending.

**G14. Pre-hydration and form reset.**
- This is not a `useForm` form, so `HydrationGate` is not required by the tripwire.
- React 19 resets an action form when the action resolves (verify in Phase 4). A failed submit could wipe six fields. The form must keep typed values on error.
- A file input cannot be refilled by script, so the error copy says "attach your resume again" only when the file really is lost.

### Rulings on the analyst's handoff

**G1 — Resume storage (F289, F290): a careers-owned `job_application_files` table, not `blob_assets`.**

Why not `blob_assets`:

- **It is served publicly.** The public asset route serves any key in the org with `public, max-age=31536000, immutable`.
- **Dedup conflicts with purge.** Dedup is a table constraint (`blob_assets_org_hash_key`). Getting around it means salting the hash, which makes `content_hash` mean something other than what it says.
- **Purge would need a broad delete grant.** `presby_app` would need DELETE on a table where, on development, **108 of 113 rows are referenced by no FK** (site images found through the bundle's `imageKeys`, and photos). A delete grant would make every one of them deletable by the tenant connection.

The table shape:

- `job_application_files (id, organization_id, application_id, content_type check in (pdf, docx), byte_size check 1..4194304, sha256, bytes bytea, created_at)`.
- Composite FK to the application. No dedup.
- No original filename stored. It is PII-adjacent and a bidi-spoofing vector. The download name is server-generated.

Serving:

- Only the authenticated GET handler serves files, through a definer gated on `careers.applicants`.
- Headers: `Content-Disposition: attachment; filename="<ascii, server-built>"`, `Cache-Control: private, no-store`, `nosniff` (already global). Add `Content-Security-Policy: sandbox` on the response.
- Every download writes an audit row (ids only) in the same transaction.

Delete path and dedup versus purge: covered under Invariants above. F290 is resolved by construction.

**F289 — is it live today?**

Latent, yes; currently exploitable, no. It needs its own bug-fix pipeline, run next, and it does not block careers.

What the route can reach. It resolves `getBlobStore().resolve()` for any key at an org whose site is live. FKs on development show five consumers:

**G2 — Upload transport (F291): a route handler at `(public)/site/[slug]/careers/[posting]/apply/route.ts`, POST.**

Verified limits:

- **Next 16.4.2:** the server-action default body limit is 1 MB (`node_modules/next/dist/server/app-render/action-handler.js:513-515`). `next.config.ts` sets no `serverActions`.
- **Vercel** (docs, "Request body size"): *"The maximum payload size for the request body or the response body of a Vercel Function is 4.5 MB"*. Anything larger gets `413 FUNCTION_PAYLOAD_TOO_LARGE`. The limit applies to the response too, so a download is capped the same way.

What that means for the handler:

- Cap: 4 MiB (4,194,304) per file. Total request cap: 4,450,000 bytes.
- Missing `Content-Length` → 411. Over the cap → 413 with the app's own copy, returned before `formData()` is called. Re-check `file.size` after parsing.
- The client checks the size first, so users never see Vercel's own error page.
- Don't raise `serverActions.bodySizeLimit` globally.

Why a route handler rather than a server action:

- It keeps the 1 MB limit on every authenticated action.
- It isn't under `/api`, so it works on a custom host.
- It returns JSON to a fetch-driven client form. That also settles G14: React 19 resets a form after an action, but this form doesn't use one, so typed values stay put.
- It sits outside `check:audit`'s `actions.ts` scan, which is correct because the submission must write no audit row.

**F291 is confirmed by reading the source, not by running it.** The ticket forms say "up to 10MB":

- `file-ticket-form.tsx:253`
- `[id]/reply-form.tsx:85`
- `admin/tickets/admin-reply-form.tsx:104`

They post through server actions, so anything over about 1 MB fails before the action runs. On Vercel, anything over 4.5 MB couldn't be downloaded either. This needs a separate small bug-fix pipeline, not in careers. It isn't urgent: the copy is false, but no data is exposed.

### Proposed decisions (architectural; orchestrator records them)

- **DECISION-262 — Applicant data is tier 3 and expires by redaction; the file bytes are the one hard delete.**
  - Applicants are never `people`.
  - Personal fields are set to null in place; `redacted_at` and kind are stamped, and redaction is irreversible by trigger.
  - The `job_application_files` row is deleted only by a redaction definer, after its parent is redacted (trigger plus deferred check).
  - "Due" is derived: closed + 1 year, capped at submitted + 2 years.
  - The sweep is an owner-only definer step in the daily maintenance cron. Audit rows carry ids only.
  - **Residual (`paper`):** point-in-time history, dead tuples and production branches.
- **DECISION-263 — Applicant files are not blob assets.**
  - A careers-owned table with no dedup and a 4 MiB cap, served only by an authenticated, attachment-only, `no-store` handler through a `careers.applicants` definer.
  - `blob_assets` remains the store for durable, content-addressed, possibly-public artifacts.
  - Rejected: a non-deduping or delete path on `blob_assets`.
- **DECISION-264 — The careers public surface.**
  - `/careers/<posting>` is a static segment; `/careers` lets the bundle's own page win.
  - The reserved-path check gains descendants-only reservation.
  - Applying is a site-tree route handler, not an action and not under `/api`. The global action body limit is untouched.
  - The form is fetch-driven, behind `HydrationGate` with `method="post"`.
  - The form token is HMAC-derived from `AUTH_SECRET`, sent as a hidden field, never a cookie.
  - One submit definer. No applicant audit row. No applicant email.
- **DECISION-265 — Careers permissions.**
  - `careers.manage` (tier 1) and `careers.applicants` (tier 3); neither implies the other.
  - Both join the founding-administrator bundle in both definitions (the first key above tier 1 there; `paper`, detected by the download audit), plus a `hiring_committee` template.
  - Applicant reads are definer-only and permission-checked in the database.
  - The badge is a presentational tile annotation computed outside the registry.
- **DECISION-266 — Posting descriptions use the site-kit markdown subset, rendered by `renderMarkdown`.**
  - No editor dependency (Tiptap/ProseMirror rejected: a second content model on the public tree).
  - Paste is converted with the browser's own `DOMParser`; the server validates the text.
