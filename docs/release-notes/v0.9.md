## 0.9.0 — 2026-08-18

### Feature: Per-Congregation Two-Factor Policy

**Background:** two-factor was an all-or-nothing switch for the whole installation, because `auth.require_2fa` is a row in `feature_flags` and that table has no `organization_id`. One congregation could not require 2FA while another did not — which matters when the people being asked to use an authenticator app include members who find it genuinely difficult.

At the same time `/admin/2fa` was not an admin tool at all. It operated entirely on `session.user.id`: enrol yourself, regenerate your own recovery codes. It duplicated `/account/2fa` down to the buttons, and the admin nav labelled it "Your 2FA".

**Changes:**

- **`organization_settings.require_two_factor`**, default false, so every existing congregation keeps today's behavior and 2FA is opt-in per church. It lands on settings rather than `organizations` because the org tree is deliberately public and per-org configuration lives in settings — and as a typed column rather than a key in the settings jsonb, because it is read on the sign-in path.
- **Most-restrictive wins.** A member is required if their own record requires it *or* any congregation they belong to does. A minister of Word and Sacrament is a member of the presbytery while serving a congregation (G-2.0502), and the requirement is resolved *before* anyone picks an organization — sign-in precedes the org switcher — so there is no "current org" to consult.
- **`/admin/2fa` is now the policy page**: every organization with a requirement toggle, plus a "required, but not enrolled" list — the accounts that will be asked for a code they cannot produce. Each links to the user page, where `forceResetTwoFactor` already lived. Self-enrolment now exists in exactly one place.
- **Security finding M5 closed by deletion.** The four ungated exported actions on that route are gone; the single action replacing them is gated on the new `admin.two_factor` permission, audited as `org.2fa_policy.changed`, and carries a regression test that names M5.
- **Dead code removed**: `prepareEnrollment` (no callers) and a `PENDING_TTL_MINUTES` constant that shadowed the shared one.
- **A missing `AUTH_TOTP_ENCRYPTION_KEY` no longer crashes the 2FA page.** It threw an unhandled runtime error mid-render, where Turnstile no-ops without keys and Resend falls back to stdout. It now shows a configuration notice that tells the member no action is needed and the operator exactly which variable to set.

**The part worth reading (DECISION-033).** The per-church lookup runs at sign-in on the RLS-enforced connection with **no organization context set** — and none can be, because choosing an organization happens after authentication. That is finding F26 in a new place: a plain join is filtered to zero rows and returns false *for exactly the users the policy protects*, failing silently while looking correct. `presby_two_factor_required()` is therefore `SECURITY DEFINER`, and measured against the real database as `presby_app` with no GUC:

```
presby_two_factor_required(<user>)   →  true
the equivalent naive join            →  0 rows
```

Written as a Drizzle join, this feature would have protected nobody. Both readings are now permanent assertions in `scripts/test-rls.sql`.

**Not addressed, deliberately:** TOTP is still the only second factor, and TOTP is exactly what older members struggle with. An emailed one-time code needs no new dependency — the durable email queue already exists — but it is its own design, and it is tracked rather than smuggled in here.

**Verified:** 39 isolation assertions as `presby_app` (was 36) · 434 unit tests (was 424) · 49 e2e against a real dev server including the MFA-enrolled fixture · typecheck, lint, build, both tripwires.
