## 0.42.4 — 2026-10-25

**Security: a security update to how sign-in with an outside account is checked.**

**Value:** Before sign-in with an outside account such as Google is switched on, we added a check that the platform only accepts an email address the outside provider says it has confirmed.

#### What's New

- **Nothing should look different.** Signing in with your email and password, entering your authenticator code, and using a recovery code all work as before, and you land where you did before.
- **You do not need to do anything.** You will not be signed out.
- **What changed behind the scenes.** The sign-in check now requires the outside provider to say the email address is confirmed before the platform looks at any account. If it does not, the sign-in is refused with the same "Access Denied" page that appears for other refused sign-ins.
- **Sign-in with Google is not turned on yet.** This update is groundwork for turning it on safely.
- **If anything looks off,** such as being refused when signing in with an outside account, please tell us with the feedback button.

## 0.42.3 — 2026-10-25

**Security: a security update to how sign-in sessions are handled.**

**Value:** We hardened how the platform keeps track of a sign-in session, so a step that checks who you are can only be completed in the places meant to complete it.

#### What's New

- **Nothing should look different.** Signing in, entering your authenticator code, and using a recovery code all work as before, and you land where you did before.
- **You do not need to do anything.** You will not be signed out, and you will not be asked for a code again because of this update.
- **What changed behind the scenes.** The platform now accepts that a sign-in step is complete only from its own verification screens. Other requests to change a session's state are refused.
- **If anything looks off,** such as being sent back to the code screen after entering a correct code, please tell us with the feedback button.

## 0.42.2 — 2026-10-24

**Security: a security update to how forms check what you type.**

**Value:** A reported weakness in one of the software libraries that checks form input has been closed.

#### What's New

- **Nothing should look different.** We upgraded the library that checks what you type into forms, for example that an amount is a number or a date is real. The upgrade closes a published security advisory. Forms and the messages they show are meant to stay exactly as they were.
- **What the advisory was.** In theory, a request that was both unusually large and shaped in one particular way could make the server use far more memory than it should. The platform already limits how much data a form can send, and the one place that accepted a list of that kind is a platform-administrator screen, so exposure was narrow. It is now closed at the source.
- **One small caveat.** If someone sends a request by some route other than the app's own pages, a few of the "that doesn't look right" messages may read slightly differently. The app's own forms can't produce those requests.
- **If anything looks off,** such as a form that won't accept something it used to accept or a message that reads strangely, please tell us with the feedback button.

## 0.42.1 — 2026-10-24

**Polish: the invitation screens now say who has to accept.**

**Value:** When a platform administrator invites someone to be a congregation's founding administrator or treasurer, the confirmation now says whose acceptance makes it official. That removes the guesswork about whether the role is already in place.

#### What's Changed

- **The confirmation names the person.** After you send or resend an invitation, the message now reads "The founding administrator designation takes effect when {name} accepts it from the email. Until then nobody holds this role." For a treasurer it names the person's first name only and ends "…nobody holds this access."
- **If a name is not available,** it says "the person at {address}", or "the invitee".
- **The invitation line on the organization page names the person too.** An open invitation says who it is waiting on, and an expired one says it has expired instead of calling itself open.
- **First send now shows the address.** The first confirmation says "Invitation sent to {address}", the same as a resend already did.
- **The treasurer's name now appears in the invitation list.** It shows the person's first name, as the founding administrator's name already did.
- **Very long names wrap on a phone screen** instead of running off the edge.
- **Names no longer carry hidden text-direction characters** that could scramble a sentence. This applies when an administrator types a founding administrator's name, and also to the name a new invitee enters when accepting. A few harmless direction marks are still left in place.

The wording says what happens when the person accepts. It does not say the email arrived or was opened, because we cannot know that.

## 0.42.0 — 2026-10-23

### Feature: a person can have more than one email address, with one main

**Value:** People have a personal address and a work address, and staff in particular use both. Until now a person could have one. Now each person can have several, labelled, with one main address, and the platform has a single place that decides which address a message goes to.

#### What's New

- **More than one email address per person.** On a person's edit page you can now add as many email addresses as you need (up to 10), label each Personal, Work or Other, and pick one as the main address. Before, a person could have only one. The Add person wizard takes the same list.
- **Removing an address keeps a record.** A removed address stops being used and no longer shows, and a record of the change is kept. If you remove the main address, the oldest remaining address becomes the main one, and you are told which. An address you corrected counts from the day you corrected it.
- **What members see.** The member directory shows each person's main address. A staff member who is also listed in the member directory also shows their Work address. Both stay hidden if the person hides their email.
- **Search matches only what is shown.** Searching the member directory or Find a person now matches only the details a person's card shows, so a hidden email or phone no longer turns up. In Community, the Members, Everyone and Participants lists work the same way. The Visitors, Staff and Former lists match every address on file for a person.
- **Shared addresses.** If you save an address that is already on file for someone else in your congregation, you see a note. Households can share an address; an invitation to a shared address won't go through.
- **"Don't send mail to this address."** You can now set this on each address. Routine mail skips it, and an invitation to it asks for an extra confirmation.
- **A warning when you invite someone whose address is already here.** When a platform administrator invites someone to be a congregation's founding administrator or treasurer, and that address is already on file for a person on that congregation's roster who signs in, the screen now says so. The invitation is still sent, and the warning explains that it is refused unless the invitee accepts while signed in to that person's own account.
- **People in more than one congregation.** A person who belongs to more than one congregation has one set of email addresses, shared by those congregations.
- **What did not change.** Giving statement emails still use the address on the donor's giving record. Sign-in, password reset and account emails still use the account's own address and never a contact address.

#### Known limits

- A staff member who is only recorded as staff, and is not listed in the member directory, shows no Work address to members.
- The Community lists show a person's main address. To see every address with its label, open the person's edit page.
- When you add a person, the duplicate check uses the address typed on the first step. Addresses added on the next step are not checked for a match.
- If you confirm that a new entry is an existing person, any contact details typed in the wizard are not saved to that person.
- Searching the member directory treats `%` and `_` as search characters rather than plain text.
- Because a person in several congregations shares one set of addresses, a person who can manage people at one congregation can change an address that another congregation also uses. Each change is recorded in the audit log with the congregation that made it.
- Removing a person's address is recorded, not erased, but some other records in the people and membership area can still be deleted by the application. This release changes email addresses only.

**For the operator: deploy order.** Apply migration `0064` first, then deploy the code, with a snapshot of production first. The new code reads columns that `0064` adds. In the few minutes between the two, saving a person's contact details can fail; nothing is corrupted. On `development`, run the function-definition check described in `docs/deployment.md` under "Person emails" before `0064`. The runbook and verification queries are there.

**Technical:** migration `0064_presby_person_emails`. `contact_methods` gains `created_at` and `ended_at`, `DELETE` is revoked from `presby_app` and `presby_platform`, a guard trigger makes the address, kind, person and creation time immutable and lets only the acceptance function set `verified_at`, and a deferred constraint trigger keeps exactly one active main address whenever a person has any active email. `presby_preview_invitation` and `presby_accept_invitation` are re-created with `ended_at is null` at their four `contact_methods` sites (F211). `presby_person_email(person, purpose)` is the credential authority behind the `credential`, `role` and `personal` purposes; `src/lib/contact-methods/` holds the pure routing and plan code, `store.ts` (the only writer) and a closed registry that classifies every email template key. DECISION-215–219 and findings F210–F217 are recorded (`docs/schema-design-2.md` §2w): F210–F214 and F216 are closed, F215 and F217 are open and pre-existing. F176 stays open for `addresses` and the other tables. Work-log: `docs/work-log/2026-10-23-person-emails.md`.
