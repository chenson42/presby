## 0.5.2 — 2026-05-19

### Infrastructure: `upstream-sync` supports scaffolded projects, not just true forks

**Background:** The `upstream-sync` skill assumed every derived repo was a true git fork — it computed the sync baseline with `git merge-base HEAD upstream/main`. A project that was *scaffolded* from the starter (cloned-then-detached, copied, or `degit`-style) shares no git history with the canonical repo, so `merge-base` returns nothing and the first-run path broke. In practice many forks of this starter are exactly that: a new project that was *based on* the starter rather than a GitHub fork.

The enabling insight: the skill's `MODE=gh` path queries the canonical repo's commit list directly over the GitHub API and never needed shared history — only a baseline SHA or date. The skill just wasn't acknowledging that.

**Changes:**
- The skill now names two supported repo kinds explicitly: *true git fork* (shared history) and *scaffolded / vendored copy* (no shared history). "Fork point" is reframed as "baseline"; the `forkPointSha` state-file key is retained for backward compatibility with a documented dual meaning.
- Pre-flight Check 1 now handles a missing/empty `origin` and classifies the repo as `fork` / `scaffolded` / `unknown-pending` (resolved later by a history test). Repo kind never blocks the run.
- Step 2 baseline resolution is now a four-strategy ladder: (1) `git merge-base` for true forks, with a no-common-ancestor fall-through that detects a scaffolded copy instead of producing a garbage baseline; (2) user-supplied starter SHA; (3) approximate scaffold date resolved to a canonical SHA via `gh api … -f until=`; (4) latest-canonical HEAD as an explicit last resort.
- Fixed a latent bug: `lastSyncedDate` is now seeded from the fork/scaffold date when known rather than always today, so the first `MODE=gh` run does not miss commits between the baseline and today.
- Failure Mode B and the state-file schema comment updated to match; new strategies added to the skill's "Known Untested Paths" honesty section.

**Testing:**
- [x] Skill-doc-only change — no application code touched; `npm run typecheck` unaffected
- [x] Reviewed the four baseline strategies for internal consistency and against the existing `MODE=gh` / `MODE=git` Step 3 fetch logic
- [ ] Not yet exercised against a live scaffolded-project ↔ canonical pair (tracked in the skill's "Known Untested Paths")

## 0.5.1 — 2026-05-19

### Defect Fix: Admin docs viewer rendered raw `<a name>` text and sorted versions lexicographically

**Problem (two bugs, one viewer):**

1. **Anchor placeholders rendered as visible text.** Release notes use `<a name="0.4.0"></a>` markers above each version heading so the TOC links (`[0.4.0](#0.4.0)`) scroll to the right place. ReactMarkdown sanitizes inline HTML by default — the anchor tags were either stripped or rendered as text. The TOC links worked anywhere a browser auto-generates an `id` from the heading slug; everywhere else they 404'd silently in-page.
2. **Version filenames sorted lexicographically.** `Array.prototype.sort()` (and `localeCompare` without `numeric: true`) compares `"v0.10.md"` and `"v0.9.md"` character-by-character — `"1" < "9"` — so `v0.10` would appear between `v0.0` and `v0.2` in the sidebar. The bug doesn't manifest at this project's current version but lands as soon as a fork crosses `v0.9 → v0.10`.

**Root Cause:** Both were caught in sibling projects (`../westervillelions`, `../npvitals`) that have already crossed their respective version-threshold or accumulated enough anchor links to surface the bugs in production. The starter has had the same latent bugs since v0.1.

**Fix:**

- Added `rehype-raw` to the ReactMarkdown plugin chain in `src/app/(admin)/admin/docs/page.tsx` so HTML in markdown (including `<a name>`) renders as real DOM elements.
- Changed the file sort to `b.localeCompare(a, undefined, { numeric: true })` so embedded numeric segments are compared as numbers.

### Documentation Cleanup: strip per-file inventories from release notes

**Background:** Sibling project `westervillelions` ran a sweep across its release notes to remove "Files Added" / "Files Modified" sections, with the rationale that release notes describe user-facing value and bug context — not implementation. A reader who needs a per-file diff can run `git log vA.B.C..vX.Y.Z`. Back-ported to the starter.

**Changes:**
- Removed all `Files Added` / `Files Modified` sections (both `#### Heading` and `**Bold:**` styles) from `docs/release-notes/v0.1.md` through `v0.5.md`.
- Updated `.claude/skills/release-notes/SKILL.md` to remove those sub-blocks from the Feature, Enhancement, Defect Fix, and Infrastructure/Security templates. Added an explicit "No file lists" reminder to the Feature template.

## 0.5.0 — 2026-05-18

### Feature: Commit-Message Standards + Escape-Rate Reporter

**Value:** The 7-day retrospective had no quantitative anchor. Every retro was qualitative observation only, which made it hard to tell a real trend ("we're escaping more bugs to production lately") from anecdote ("I noticed a couple of bad commits last week"). This release gives the retrospective a real number: a rolling 30-day escape rate, broken down by how each bug was eventually caught. The classification has to come from the commit author, so it's enforced at commit time by a git hook installed automatically on `npm install`.

The deeper bet: as the pipeline catches more bugs in-process (Phase 5 QA, periodic reviews, the new upstream-sync), the bugs that *do* commit get more interesting. Their distribution across catch channels tells you which gates are working and which aren't. That's the signal the retrospective has been missing.

#### What's New

- **Conventional Commits grammar enforced at commit time.** Subject line must match `<prefix>(<optional-scope>): <description>` with prefix from `feat | fix | chore | docs | test | refactor | style | perf | build | ci`. `Merge `, `Revert `, and `Release ` prefixes are exempt. Description is 1–100 characters.
- **`fix:` commits require two trailers:**
  - `Caught-By: automated-test | agent-review | human-review | production`
  - `Discovered-In: Phase-1 | Phase-2 | Phase-3 | Phase-4 | Phase-5 | Phase-6 | post-merge | production | retrospective`
- **The `Caught-By` boundary rule** lives in `CLAUDE.md`: if CI would have caught the bug without any agent judgment, use `automated-test`. If an agent had to decide to run a non-mandatory check, use `agent-review`. Two non-overlapping conditions, intentionally — the metric only works if the classification is consistent.
- **`npm run stats:escape`** prints a 30-day rolling report: per-channel breakdown (absolute counts and percentages), total `fix:` count, missing-trailers count (the bypass-and-pre-cutoff indicator), and the grandfather cutoff date in the header. Output is stdout; tech-lead copies it into the weekly retrospective.
- **Mixed-commit rule:** one prefix per commit. A commit that adds a feature and fixes a bug must be split. The validator passively enforces this (only one prefix is accepted); `CLAUDE.md` explains why.
- **Hook installs automatically.** `scripts/install-hooks.sh` runs via the npm `prepare` lifecycle (no `husky` dependency), is idempotent, backs up any existing `commit-msg` hook, and is a no-op when `.git/` is absent (safe in deploy environments).
- **Grandfather cutoff: 2026-05-18.** Commits before this date lack the new trailers by design; `stats:escape` declares the cutoff in its header so the first retrospective's number is honest.
- **`pre-push` integration: skipped on purpose.** Forcing `stats:escape` at push time surfaces problems too late for the author to act on. Reconsider after three retrospectives if bypass rates persist.

#### Out of Scope / Deferred

- **MTTR per channel.** Would require a third `Fixes-Bug: <sha>` trailer and substantially more per-commit friction. Deferred to a future work-log.
- **In-pipeline catch rate.** Most bugs in this pipeline get caught and fixed *inside* Phase 5 and never become commits — they don't show up in `git log` at all. `stats:escape` measures the escape rate only. A complementary tool that mines work-logs for in-pipeline catches is a separate feature.

**Work-log:** `docs/work-log/2026-05-18-commit-message-standards.md` (six phases, SHIP IT verdict).

#### Known Footguns

- **First retrospective.** Until `fix:` commits using the new trailers accumulate, `stats:escape` will show `0 fixes, all pre-cutoff` for ~weeks. That's correct, not broken. The header makes this self-explanatory.
- **Self-bypass via `Edit` + `git push` without `git commit`.** The hook only fires on commit. An agent that edits files and pushes via some non-commit path would bypass the standard. In a solo repo this is theoretical; in a team setup it might warrant a `pre-push` integration later.
