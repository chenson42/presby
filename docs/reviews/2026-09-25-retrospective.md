## Where defects escaped to, and why Phases 2/3/5 did not catch them

This is the central finding of the period, and it is almost entirely one pipeline: `docs/work-log/2026-09-24-lifecycle-affiliation-returns.md` (organization lifecycle / council affiliation / statistical returns / publication, D10/D19/D20/D21). Ten Phase 3 rulings, three Phase 4 passes beyond the original batches, two external post-merge review rounds (F47–F53, F54–F58), and one QA re-verification FAIL (QA-1/QA-2/QA-3) — all against **two commits that never left the `development` Neon branch** (`36a2bb8`, `422d894` are on `main` but unapplied to production). Reading Phase 5's original verdict against what the external reviewer found afterward answers the question directly.

**Phase 5 (QA) did its job correctly and still missed everything the external reviewer found.** The original Phase 5 report (line 4093 of the work-log) is a model verification pass: every named test-rls.sql section run and cited by line number, two failing-first proofs reproduced independently rather than taken on trust, grants read from `information_schema.role_table_grants` rather than from the migration text, cross-council function *bodies* read line-by-line rather than inferred from comments. It returned **PASS**, correctly, because every check the design specified was green. The external reviewer then found five more holes (F47–F52) that no test suite was asking about at all: a CHECK constraint with an inverted boolean (`publications_withdrawal_shape` — true when it should be false), a missing UNIQUE, four missing CHECKs on `organization_affiliations`, and — the pattern that recurs three separate times across both review rounds — **"revoke the grant" treated as sufficient closure for a table `getPlatformDb()` can still write as `neondb_owner`, which owns every table and bypasses every grant.** QA cannot fail a test that was never specified. This is not a QA gap; QA's mandate (CLAUDE.md Phase 5) is conformance-to-spec verification, and every one of these was a **spec completeness** gap, which is Phase 2/3's job.

**Why Phase 3 (tech-lead) didn't catch it either, and this is the more important half of the answer: the design discovered its own missing principle mid-pipeline and did not apply it backward.** Ruling B3 (line 1645, "Amendment after batches B and C," 2026-09-24 — *before* the first external review) already states the exact fact that would have prevented F47–F52: *"every claim in this pipeline of the shape 'X cannot happen because the grant forbids it' is false on the `getPlatformDb()` connection today, and the only real backstop there is a trigger."* That ruling was written and ratified, and then the pipeline continued specifying `organization_identifiers`, `organization_affiliations`, `statistical_returns`, and `publications` with grant-only closures anyway, because those tables' Phase 3 text had already been written before B3 was discovered and nobody re-audited it against the new rule. The round-two external review's own closing sentence names this precisely: *"if an immutable record represents an authorized act, creation must be guarded as strongly as mutation... It wasn't a different judgment; it was an incomplete application of a rule already adopted"* (line 4648). **The design defect was a missing checklist step, not a missing insight** — the insight existed, in the same work-log, before the vulnerable text shipped.

**Why Phase 2 (architect) didn't catch the CHECK-logic bug:** correctly out of scope. The architect's Phase 2 review operates at the level of placement, grant model, and invariant compliance (its eleven rulings, all correct and all still standing unchanged through ten Phase 3 loop-backs) — not at the level of "is this specific boolean expression backwards." Nothing in the architect's mandate or the six-phase pipeline currently owns constraint-shape review at the SQL-clause level; the external reviewer filled that gap by reading the exported DDL clause-by-clause, which no phase does today except by accident (a database-admin implementer reading their own SQL is not a second pair of eyes).

**The recurring shape, once for the schema pipeline and once for auth:** the security-review-highs work-log (`2026-09-25-security-review-highs.md`) shows the identical failure pattern in a completely different subsystem. The open-redirect fix that closed H1 on 2026-07-11 regressed because *"H1 was about a missing guard entirely; the fix added two prefix checks and the test suite was written to those checks, not to the WHATWG spec they approximate. A prefix-matching guard and a spec-conformance guard are different objects"* (line ~31 of that work-log). Two unrelated pipelines, five weeks apart, produced the same root cause: **a regression test that encodes the shape of the fix instead of the shape of the threat model it fixes will pass forever while the actual vulnerability class regresses.** This is worth a named rule, not just two isolated bugs (see Punch List item 3).

**Verdict on the escape pattern:** Phases 2/3/5 are each working exactly as specified. The gap is structural and sits between them — nothing in the pipeline currently re-audits already-specified surfaces against a design principle discovered later in the same pipeline, and nothing reviews constraint/trigger logic at the clause level except an ad hoc external reader. The external post-merge review (now a named CLAUDE.md process, added this period) is currently doing load-bearing work no phase gate does on its own.

## Cost/benefit of the ten-ruling loop shape vs. a fresh migration

The work-log's own framing answers this directly and I agree with it: every correction after the original Phase 4 passes landed as **"same files, same numbers"** (`drizzle/0043`–`0047` corrected in place) because the migrations were on `main` but never applied to production — CLAUDE.md's own rule ("An unreleased migration... may be corrected in place... once shipped, fix forward"). This was the right call, and the alternative (drizzle/0048 through drizzle/0053+, six more migration files layering fix-on-fix onto tables with zero production rows) would have been strictly worse: harder to read, harder to audit ("what does this table actually look like today" becomes a six-file join), and it would have obscured exactly the pattern this retrospective needed to see (a CHECK written wrong, then rewritten wrong differently, is a red flag when it's the same file; it looks like ordinary iteration when it's six different files).

The cost was concentrated somewhere else: **work-log size and read burden.** The single work-log is 5,228 lines. Reading it in full for this retrospective required three separate large reads and took a meaningfully larger share of this review's effort than any other single artifact. CLAUDE.md's rule against summarizing away judgment-agent output (added after the 2026-07-11 retrospective's own loop-back finding) is correct and I am not recommending it be weakened — the ninth-pass QA-1/QA-2 defects were only findable because the full history of what each guard was claimed to do, and when that claim was made, stayed in the document. But ten loop-backs in one file is close to the point where "preserve everything" and "stay readable" start trading against each other, and it is worth a named threshold rather than discovering it at loop-back fifteen on some future pipeline: **if a single work-log crosses roughly five Phase 3 loop-backs, split the *review history* into a linked appendix file while keeping the live Per-Phase Status table and current design text in the main file** — nothing here proposes losing any content, only moving settled rulings out of the primary read path once they've been ratified and are no longer active decision surface.

**Verdict: correction-in-place was the right mechanism for this pipeline and should stay the default for unreleased schema.** The real lesson is upstream of the loop-back count — see the previous section — not in how the corrections were packaged once found.

## "Judgment agents return text, orchestrator splices" — is it working?

Yes, on the evidence of this period, and I found no instance of information loss. Every judgment-agent section I read across all six pipelines examined in depth is explicitly labeled *"recorded verbatim by the orchestrator"* at the point it's spliced in (e.g. lifecycle work-log lines 4095, 4259, 4379, 4475, 5037; e2e-red-on-main's Phase 1 brief is labeled the same way), and cross-checking those sections against their own internal citations (line numbers, exact grant names, exact error strings) turned up nothing that reads like a paraphrase — the level of literal detail (e.g. QA's exact `sqlerrm`/`sqlstate` comparison methodology, the architect's eleven numbered rulings preserved with their original numbering across seven subsequent amendments) is not the kind of thing an orchestrator would reconstruct from memory; it reads as copied.

The one place the discipline showed real strain was **volume, not fidelity**: the same lifecycle work-log's Phase 3 row in the Per-Phase Status table is a single cell that, by the tenth loop-back, is one continuous paragraph summarizing nine prior amendments before describing the tenth — technically accurate and complete, but a reader arriving fresh has to reconstruct pipeline history from a run-on sentence rather than a structured list. This is a formatting observation, not a correctness one (see Punch List item 5).

**Verdict: the mechanism is sound. The failure mode it exists to prevent (an orchestrator quietly editing a QA FAIL into a PASS-shaped summary) did not occur once in 68 pipelines this period.**

## What parallel pipelines cost on a shared worktree and shared Neon branch

Workflow Rule 16 (added 2026-09-24) was exercised for the first time on 2026-09-25, on **one shared worktree and one shared Neon `development` branch** across five concurrent pipelines (lifecycle round-two hardening, brand-visual-parity, e2e-red-on-main, org-switcher-touch-target, platform-radius, security-review-highs) — which is explicitly *not* what Rule 16 prescribes (one worktree, one Neon branch per pipeline). The measured costs, all recorded live in the pipelines' own work-logs rather than reconstructed after the fact:

1. **Dev-server and `test-results/` contention.** Next 16 enforces one dev server per directory (`lockfile.js`); two pipelines running Playwright against the same tree fought over the lock and overwrote each other's `test-results/` traces (`docs/TODO.md:262`, `security-review-highs.md:777`). One pipeline's QA had to poll a bounded until-loop (~4 minutes) waiting for another pipeline's lock to clear before it could run its own verification (`e2e-red-on-main.md:286`).
2. **Build-artifact corruption across trees.** A sibling agent's `next dev` rewriting route manifests under a concurrently running `next start` produced a hard HTTP 500 on an unrelated page in a different pipeline's visual-parity run, which vanished entirely once that pipeline moved its build to a copy outside the repo (`brand-visual-parity.md:1021`) — a real false-positive defect signal that cost investigation time before being correctly attributed.
3. **Fixture pollution reading as a defect.** Two independent screenshot-diff findings in `platform-radius`'s QA pass turned out to be rows written by a concurrent pipeline's test fixtures, not the diff's own subject (`platform-radius.md:464`) — confirmed harmless only after tracing specific row content, not from the diff tool itself.
4. **The one-Neon-branch pattern is also this period's *recurring* root cause, not a new one.** `docs/TODO.md` already carries at least four independent prior entries for the same underlying problem (lines 56, 110, 120, 122, 263) — leaked fixture organizations, a leaked membership row that aborted `test-rls.sql`'s count assertions, 81 accumulated month-old vitest fixture users, and a real PII row from 2026-08-24 — all on the same shared branch, predating Rule 16 by weeks. Rule 16 was written in direct response to this pattern and then not actually followed the first time it had the chance to be, because — per the code review's own measurement — **the rule as written has no mechanical teeth and a real operability gap**: `docs/reviews/2026-09-25-code.md`'s R16-1 through R16-5 found five hot shared files missing from Rule 16's own exclusion list (`package.json`, `scripts/seed.ts`, `docs/product/functionality-map.md`, `src/lib/audit.ts`, `src/lib/org-portal/tiles.ts` — two of which Rules 7 and 14 *mandate* mid-pipeline edits to, directly contradicting Rule 16's integration-only intent for shared files), 181 of `test-rls.sql`'s 309 assertions are absolute fixture counts that any second pipeline's landed fixtures will break, and the 24-test-file fixture sweep the last schema pipeline needed is itself the largest collision surface a future parallel pair could hit.
5. **The one genuinely new, previously-unnamed hazard this period surfaced:** fixture orgs orphaned by a crashed test run become **permanently undeletable** once their `deletable_until` window passes, because `presby_guard_organizations_delete()` refuses unconditionally on every connection including the owner's (`docs/TODO.md:263`, round-two implementer Finding 4a) — a shared branch running crash-prone concurrent suites accumulates dead weight it can never remove without a manual guard-disable. This directly strengthens the case for branch-per-pipeline: it's not just isolation hygiene, it makes the accumulating-garbage problem literally disposable instead of literally permanent.

**Verdict: Rule 16 correctly diagnosed a real, pre-existing, recurring problem, and its first real-world exercise did not follow the rule's own prescription** — the same session that added the rule ran five pipelines on one worktree and one branch, immediately reproducing the failure modes the rule exists to prevent (at a lower blast radius than a genuinely uncoordinated run only because every pipeline's own QA was disciplined about attributing cross-contamination correctly rather than reporting false failures). `docs/TODO.md` already has an open item for the mechanics (line 116, citing R16-1 through R16-5); this retrospective's contribution is confirming, from live evidence rather than static analysis, that the gap is real and that "the orchestrator will just remember to use separate worktrees" is not sufficient — the same day the rule was written, it wasn't followed, by the same process that wrote it.

## QA's failing-first discipline — did it catch real things?

Yes, on both counts named, plus a third instance in the same period:

1. **Lifecycle pipeline, first Phase 5 FAIL** ("Amendment after Phase 5," 2026-09-24, line 1687): QA's Finding 1 — `organization_successions` was policy-mediated, not function-mediated, contradicting Phase 2 Ruling 1 — was confirmed real and routed to database-admin. Real defect, not a false alarm.
2. **Lifecycle pipeline, QA-1/QA-2/QA-3** ("Ruling on QA-1/QA-2 after hardening round two," line 4745): QA re-verified the round-two hardening build and found the design's own comments overclaimed what two guards actually did. QA-1 (the lifecycle-write GUC was a bare boolean, not bound to any specific act, so a later transaction could re-arm it against an already-committed event) was **confirmed as a real defect in the claim**, though ruled to have no live exposure today (`presby_app` holds SELECT-only on the tables in question). QA-2 (the withdrawal-write GUC on `congregation_statistics` gated nothing for `presby_app`, because a GUC is `set_config`-able by any role while the grant itself was never narrowed) was **confirmed as worse than the design's own comment stated** — QA's own failing-first proof reproduced the exact defect the design claimed was impossible (`test-rls.sql:4540-4549`'s "success" assertion, immediately contradicted by the design's prose three sections later). Both real. Tech-lead's ruling explicitly credits QA: *"Confirmed, and worse than the comment stated."*
3. **Security-review-highs pipeline**, Phase 5 FAIL then PASS on re-verification: QA's own postcondition check on the sanitizer's *output* (not just its accepted-input list) caught that the drafted fix passed every test the review specified while still permitting a second WHATWG bypass class (tab/newline stripping collapsing to `//`) the review's own draft hadn't enumerated — directly the same root-cause shape as the escape-pattern finding above, caught this time by QA rather than an external reviewer, one phase earlier than the analogous schema-pipeline miss.

**Tally: 3 QA-initiated FAIL/re-verification cycles this period, 3 for 3 confirmed real, 0 false-fails.** This is a small sample but a clean one, and it is the strongest evidence in this retrospective that the "QA does not write tests, QA re-runs and independently re-derives" design (CLAUDE.md Phase 5) is earning its cost — every one of the three FAILs required QA to independently execute something (a live repro, a postcondition on output rather than the input list the fix targeted, a grant-level probe distinct from the trigger-level one the implementer tested) rather than accept the implementer's report at face value. The discipline is explicitly what CLAUDE.md asks for ("QA is verification-only... a FAIL cannot be self-resolved") and this period is the first evidence, on presby's own code, that the design catches things a trusting read of the Phase 4 report would not.

## The DB-backed-suite CI gap

Confirmed, unchanged since the code review found it three days ago, and worth restating in a retrospective because of how it interacts with everything above: **`npm test` (the CI-shape command, `vitest run`, no flags) skips 765 of the DB-backed assertions on every run** (`docs/reviews/2026-09-25-code.md` C-1; independently reconfirmed in the lifecycle work-log's own Phase 5, "3893 total, 687 skip in CI shape"), and **the CI e2e workflow exists (`e2e.yml`, ephemeral Neon branch) but its result has apparently never been read** — the e2e-red-on-main work-log's own Source line states this as a fact discovered mid-investigation, not a hypothesis: *"nobody has been reading its result."*

The consequence, stated plainly: **the only DB-backed and e2e verification presby's schema and auth work receives is whatever a QA agent chooses to run by hand, locally, against a shared branch, in the same session it is reviewing.** Every green `npm test` on this project's CI is, today, silent about roughly a fifth of the assertion suite by count and about all of the isolation-invariant suite (`scripts/test-rls.sql` runs nowhere in CI either, same finding). This is not a new discovery this period — it is already `docs/TODO.md:114`'s C-1 and already has a named fix (a `db-tests` job on an ephemeral Neon branch, modeled on the existing `e2e.yml` pattern) — but it belongs in this retrospective because it is the mechanical explanation for *why* the post-merge/human-review numbers above are so high: there is currently no automated backstop between "an implementer's local run passed" and "an external human reader looking at raw DDL found five holes." Closing C-1 is the single highest-leverage item this retrospective can point at, because it would convert some future share of `human-review`/post-merge findings into `automated-test`/Phase-4 findings — cheaper, faster, and not gated on an operator's initiative.

## Punch List — concrete edits to agents and CLAUDE.md

1. **Add a Phase 3 checklist step: when a design principle is discovered mid-pipeline (a Ruling, an amendment), re-audit every already-specified surface in the same design against it before naming the implementer for the next batch.** This is the single most direct fix for the escape pattern found above — Ruling B3 existed in the same document, before the vulnerable text shipped, and nothing forced a backward pass. One line in `.claude/agents/tech-lead.md`'s Phase 3 section: *"A new rule discovered mid-design is retroactive within the same work-log — re-check every table/function already specified against it before advancing, not just the one that surfaced it."*

2. **Name "constraint-and-trigger clause-level review" as owned by someone, even informally, rather than leaving it to an ad hoc external reader.** Nothing in the current pipeline reviews a CHECK's actual boolean logic or a grant-vs-owner-connection claim except the external post-merge review (now a named CLAUDE.md process) or an implementer re-reading their own SQL. Recommend adding one line to `.claude/agents/database-admin.md`'s self-verification step: *"Before naming Phase 4 complete on a new CHECK/EXCLUDE/trigger, restate its logic in English and confirm the restatement, not the SQL, matches the design's stated intent — this is the check that would have caught `publications_withdrawal_shape`'s inverted boolean before an external reader did."*

3. **Name the regression-test-shape lesson explicitly, in both `qa.md` and `tech-lead.md`.** Two unrelated pipelines this period (schema hardening, open-redirect) produced the identical root cause: a regression test written to the shape of the fix, not the shape of the threat/spec the fix approximates, passes forever while the underlying class regresses. Recommend one sentence in `.claude/agents/qa.md`: *"A regression test that encodes the fix's own logic (a literal prefix list, a specific column set) rather than the property the fix is supposed to guarantee (spec conformance, a closed threat class) is a weaker regression guard than it looks — ask what a slightly different bypass in the same class would do before accepting the test as sufficient."*

4. **Workflow Rule 16 needs the mechanics `docs/TODO.md:116` already names, and this retrospective adds live confirmation, not just static analysis, that they're needed now, not eventually.** The rule was written 2026-09-24 and not followed 2026-09-25, the very next day it had the chance to be. Recommend the orchestrator treat `docs/TODO.md:116` (R16-1 through R16-5: shared-files list correction, `test-rls.sql` baseline-relative counts, pre-assigned Neon branch names, the fixture-sweep helper, a `check-shared-files.mjs` tripwire) as a blocking prerequisite for the *next* genuinely parallel pipeline pair, not a backlog item to get to eventually — the failure mode it prevents already cost real investigation time twice in one day (build-artifact corruption, fixture-pollution misattribution) even with disciplined agents on both sides.

5. **`docs/work-log/_template.md`: for a Per-Phase Status cell that will accumulate more than ~3 loop-backs, recommend a short structured list (loop-back number → one-line outcome) over a run-on prose paragraph**, so a reader can scan pipeline history instead of parsing a sentence that has grown to describe ten events. Content preservation stays absolute (CLAUDE.md's existing rule against summarizing away judgment output is correct and untouched); this is a formatting suggestion for the summary cell only, not the underlying sections.

6. **Commit Message Standards: tighten `Discovered-In: production`'s definition to mean the deployed environment only.** Three commits this period used it for pre-launch, operator-eyeballed-the-dev-server findings, which the escape-rate tool cannot distinguish from a genuine post-launch production catch. One sentence in CLAUDE.md's Commit Message Standards: *"`Discovered-In: production` means the deployed production environment specifically — an operator manually verifying a running dev/demo server (CLAUDE.md → Verify in a Browser) is `agent-review` or `human-review` depending on who did the verifying, never `production`, until the project has an actual production environment for the finding to have come from."*

7. **Run `test-coverage` standalone at the next release slot rather than inferring it from whatever Phase 5 reports happened to run this period** — this exact gap was flagged in the prior codebase's 2026-07-11 retrospective and recurred unchanged on presby. No agent-file edit; a note for the next release-slot session itself.

## Verdict

The six-phase pipeline is functioning as designed at the level it was designed to operate: 68 pipelines, zero trailer bypasses, zero evidence of orchestrator-introduced information loss between a judgment agent's verdict and what lands in a work-log, and three separate QA-initiated FAIL cycles this period, all three confirmed real defects rather than false alarms. The risk worth carrying forward is the same shape twice: **a defect class that is structurally invisible to Phase 5 because Phase 5 verifies against a spec, and the spec itself was the thing missing something** — found by an external reader on the schema side (F47–F58, ten Phase 3 rulings, two review rounds) and by QA's own postcondition discipline one phase earlier on the auth side. The fix is not more phases; it's a retroactive-recheck step inside Phase 3 and a test-shape discipline inside Phase 4/5, both cheap, both named above. Separately and independently: Rule 16, written this period specifically to prevent shared-branch/shared-worktree contamination, was not followed the first time it had the chance to be, on the same day it was written — its mechanics need to graduate from prose to a tripwire (`docs/TODO.md:116`) before, not after, the next parallel pair. And the largest single lever available for next period's escape-rate number is the one this retrospective didn't have to go looking for: the DB-backed suite and `test-rls.sql` still run nowhere in CI, so every post-merge/human-review finding above is, in a real sense, filling in for a CI job that doesn't exist yet.
