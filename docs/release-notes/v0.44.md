## 0.44.1 — 2026-10-25

**Polish: your two-factor code is checked as soon as you type the sixth digit.**

**Value:** Signing in with an authenticator app no longer needs a second step. Type the six digits, or paste or autofill the whole code, and it is checked straight away, on the sign-in screen and when you set up two-factor sign-in in your account settings.

#### What's Changed

- **The sixth digit sends the code.** There is no button to press. This works when you type the digits, and when you paste or autofill the whole code.
- **A wrong code is easy to retry.** The message is the same as before ("That code didn't match. Try again, or use a recovery code."), the six boxes are emptied, and the cursor goes back to the first box.
- **The Verify button is still there.** Use it whenever the code has not been sent for you.
- **A paste that doesn't fit waits for you.** If what you paste doesn't fit in the six boxes, for example seven digits, or a few digits typed and then a longer paste, the boxes fill and wait for you to press Verify, so a digit is never quietly dropped and sent.
- **Recovery codes still use the button.** Recovery codes vary in length, so there is no last character to react to.
- **While it checks,** the button reads "Verifying…" and the boxes cannot be edited, and a screen reader announces "Verifying your code."
- **Nothing about the security changed.** The code is checked by the same step on the server as before. The limit of ten tries a minute on the sign-in screen is the same, and each success or failure is recorded in the audit log as before.

**What this costs.** A mistyped last digit is sent immediately, with no chance to correct it first. It counts as one of the ten tries you get each minute and adds a failed-attempt entry to the audit log, so expect a few more of those entries from fast typing. Codes change about every 30 seconds, so a retry is quick. A keyboard suggestion or a drag that puts two digits into a box that already holds one can also send a code with a wrong digit, and costs one try the same way.

**Known gaps.** If the server fails unexpectedly while you set up two-factor sign-in in account settings, no message appears; the boxes become usable again and the Confirm button works. Setting up has no limit on tries, as before. The behaviour was tested in automated browser tests at phone width; the check on a real iPhone and Android phone, with their own code autofill, and with a screen reader, comes after this release.

**For the operator.** There is no migration, no setting and no flag. Once 0.44.1 is live, publish this short announcement at `/admin/whats-new`: "Your two-factor code is now checked as soon as you type the sixth digit. The Verify button is still there if you need it." It appears on `/home`, so it reaches people who sign in as members. Then run the real-phone check listed in `docs/TODO.md`.

**Technical:** `OneTimeCodeInput`'s `onComplete(code, { exact })` fires when a user edit leaves the code complete and changed, and a consumer submits only when `exact` is true (no delivered digit dropped). `/totp` calls `requestSubmit()` on the existing `<form action={verifyTotpAction}>` from an effect keyed on the code, so the 0.42.3 session grant still opens only inside the action; `/account/2fa` calls its existing handler. The boxes are cleared and refocused by remounting the input once an attempt settles, keyed on completion rather than the URL (F282, because two failures in a row redirect to the same URL). The one known hole in `exact` (a two-character non-paste edit into a filled, selected box) and the other accepted residuals are in DECISION-257; follow-ups are in `docs/TODO.md`. The e2e helpers no longer press Verify (`waitForTotpVerified`). Work-log: `docs/work-log/2026-10-25-totp-autosubmit.md`.

## 0.44.0 — 2026-10-25

### Feature: your congregation's website can show an events calendar

**Value:** Visitors to your public website can see your upcoming events as a month calendar on a computer and a simple list on a phone, kept up to date from the events your team already enters.

#### What's New

- **Nothing is public until someone chooses it.** Every event, old or new, starts with the new box "Show on our website's public calendar" unchecked. An administrator must also turn on the "Public events calendar" feature, which starts off.
- **It appears where your website's maintainer puts it.** Whoever maintains your website adds the calendar to a page, for example the events page.
- **Members-only and cancelled events are never shown.**
- **What visitors can read.** Anyone on the internet can read a shown event's title, description, location and event type. Search engines and web archives may keep copies, so taking an event off the website does not remove copies already made. Please leave private details out of these fields.
- **Repeating events.** A new "Website listing" section puts an event and all later ones on the website, or marks them off, in one step. Other edits to a repeating event still apply to one event at a time.
- **A box has changed.** "Visible on the public calendar" now reads "Open to everyone, not only members". Before this release it did not control anything on the website.
- **Not included yet:** subscribing from a phone or Google Calendar, and a separate page for each event.

**For the operator: deploy order.** Apply migration `0067` to production first, then merge and deploy, with a snapshot of production first. The new code reads a column that `0067` adds, so deploying the code first would make the events pages in the congregation portal show an error until the migration runs. Old code against the new schema is unaffected. Merging exposes nothing: no congregation has the feature turned on, no event is marked, and no website carries the calendar. Turning it on for a congregation is a separate step that needs a check on a real iPhone first. The runbook and verification queries are in `docs/deployment.md` under "Public events calendar (0067)".

**Technical:** migration `0067_presby_public_events_calendar`. `events.website_listed` (default false) with the CHECK `events_website_requires_public` (a listed event must be open to everyone), and the `SECURITY DEFINER` function `presby_public_events_calendar(p_slug)`, which always returns one row, checks the organization, the live site and the `org_portal.public_calendar` toggle (including the category axis) inside itself, and returns an allow-list of seven keys with no ids. The `eventsCalendar` live slot renders 14 pre-rendered months switched by a client island; nothing request-derived reaches the database. Every change to `website_listed` writes one audit row in the same transaction (`event.listed_on_website`, `event.unlisted_from_website`). DECISION-238-241 and findings F250-F256 are recorded (`docs/schema-design-2.md` §2ab); F250 and F253 are open and tracked. Work-log: `docs/work-log/2026-10-25-public-events-calendar.md`.
