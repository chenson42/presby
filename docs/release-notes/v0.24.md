## 0.24.0 — 2026-09-24

### A permanent record of every congregation, which presbytery it belongs to, and what it reported

**Background:** A presbytery's history involves far more congregations than it has today. The Presbytery of Scioto Valley has about 85 congregations now and roughly 172 across its 41 years of statistical records, because congregations merge, divide, close, or are dismissed to other denominations, and some move between presbyteries when boundaries are redrawn. The platform previously had only a single "parent" pointer for each organization and no way to say that a congregation once existed, or that its 1990 report went to a different presbytery than the one it belongs to now. It also had no fixed record of what a congregation actually submitted in a given year, separate from what its live membership roll implies today.

This release lays the database foundation for all of that. Nothing changes on any screen yet; the pages that will let clerks record these events come in later releases.

**Changes:**
- Every congregation, presbytery and synod now has a permanent, minuted history of the events in its life — organized, received, merged, divided, dismissed, dissolved — using the Book of Order's own words, and organizations are never deleted. When congregations merge or one divides, the record shows which bodies became which.
- Which presbytery a congregation belongs to is now recorded as a dated history rather than a single current pointer, so a report from 1990 can be attributed to the presbytery that actually received it, and a boundary change does not rewrite the past. Only a council with standing over both presbyteries can move a congregation between them.
- A congregation's annual statistical report is now stored as a frozen, attested document when it is submitted, kept separately from the live figures the roll implies, and separately again from historical reports imported from old spreadsheets, which are preserved exactly as they were reported and never "corrected."
- Publishing a report to the presbytery is now recorded as its own permanent event, with who published it, to whom, under which session minute, and whether it was later replaced or withdrawn. The presbytery reads exactly what was published to it, never the congregation's live records.
- Each organization can now carry its external identifiers, such as the denomination's church PIN, in one place that a presbytery can use when matching imported records.
- Security hardening found along the way: the application's database role had more write access to the organization table than intended and that access has been removed and is now checked by the test suite; several new tables can only be changed through narrow, audited database functions, never directly.
- A pre-existing bug in organization provisioning is fixed: the check that detected a duplicate web address never worked, so a race between two operators creating the same address would have surfaced as an unexplained error.

## 0.24.1 — 2026-09-24

### Database now enforces its own rules on affiliation, submission and publication

**Background:** A hardening pass on the congregation-lifecycle and statistical-reporting foundation (v0.24.0) closed several gaps an external review found in how the database enforces its own rules — who can change a congregation's presbytery affiliation, how a submitted report is frozen, and how a published report can be withdrawn. This release also corrects the review's own read of the rules in two places where the stricter version would have broken working, deliberately-designed behavior.

**Changes:**
- A congregation's external identifiers (such as its denomination PIN) and its presbytery-affiliation history can now only be changed through the narrow, audited database functions built for that purpose — not by any direct write, on any connection.
- A submitted statistical report is now guaranteed, at the database level, to carry a real submission timestamp and to never combine an unreconciled figure with a submitted status.
- Publishing a corrected or replacement report to a presbytery is now guaranteed to go to the same presbytery, for the same congregation and year, as the report it replaces — no publication can silently point at the wrong recipient, and no report can be replaced by two competing successors.
- Withdrawing a published report no longer hides it from the presbytery's read-back; it stays visible as a withdrawn historical record, consistent with how every other record in this system is kept rather than deleted.
- Two proposed rules were found to conflict with real, deliberately-recorded history and were not added: a rule requiring every affiliation record to state an exact start date (some congregations' presbytery ties predate any record of when they began) and a rule requiring every submitted report to name an attesting person (no such identity is captured by the automated publishing path yet).
- No functional change on any screen.

## 0.24.2 — 2026-09-25

### Crafted sign-in links can no longer redirect off the platform; sensitive values no longer reach the audit log

**Background:** The monthly security review found two problems. A crafted sign-in link could redirect a user to an external site right after they completed two-factor authentication, because the link-safety check reasoned about the text of the link rather than about where a browser would actually send it. Separately, recording a member's disability categories wrote the categories themselves into the platform's internal audit log, where any platform-level audit reader could see them, contrary to how every other sensitive field is logged.

**Changes:**
- The link-safety check now parses a redirect target the same way a browser does and validates the resulting destination itself, not just the link text, closing several ways a malformed link could slip past it.
- Audit-log entries for disability-category and guardian-relationship changes no longer include the changed values — only that a change occurred, and how many categories were involved.
- No functional change on any screen.

## 0.24.3 — 2026-09-25

### Creating an authorized record is now guarded as strongly as changing one

**Background:** A second external review of the lifecycle, affiliation and statistical-reporting foundation (v0.24.1) found that two table families still let a database-owner connection *create* a row that only an authorized act should produce, even though the previous release had closed the equivalent gap on *changing* one. The rule adopted here is the reviewer's: if an immutable record represents an authorized act, creation must be guarded as strongly as mutation.

**Changes:**
- A lifecycle event (a merger, a division, a dissolution) and the record of which bodies became which are now enforced as one immutable whole. A merger can no longer be recorded with no predecessors, and no extra predecessor can be attached to an already-minuted act afterwards.
- A submitted statistical return, its publication to the presbytery, and the presbytery's typed copy can now only be created together, through the one sanctioned publishing path. A raw database connection can no longer fabricate a "submitted" return that no clerk ever submitted.
- Withdrawing a published return is now an all-or-nothing operation at the database level rather than two independently reachable half-steps; the withdrawal function that performs it ships in a later release, and until then no withdrawal is possible at all.
- Creating an organization's external identifier (such as its denomination PIN) is now held to the same standard as changing one.
- Documentation now states precisely what the database can prove about a submission: that it was attested at a time, not yet by whom. Recording the attesting person waits on a platform-wide identity context.
- No functional change on any screen.
