## 0.49.1 — 2026-10-28

### Fix: a presbytery set up before automatic setup existed can now be sent a founding-administrator invitation

**Value:** An administrator can now send the first invitation to a presbytery that was created before the platform set up an organization's basics automatically. Before, that organization could not be sent one, and the page said it was missing its baseline setup.

#### What's New

- **The invitation can be sent.** A presbytery set up before automatic setup existed couldn't be sent a founding-administrator invitation; it now can. Applied directly to production on 2026-10-28.
- **What was added.** The same two things every organization gets when it is created today: its "Active Membership" group and the ordinary "Member" role, which lets members see the directory and the events calendar. Nothing else about the organization changed, and no other organization in production was touched.

**Notes for the operator:** the fix is migration `0082`, already applied to production (after a snapshot) and to `development` on 2026-10-28, so there is nothing to apply at deploy. The deploy itself carries no code change. If an organization ever has members but no "Active Membership" group, the migration stops rather than guess; production had none. See `docs/deployment.md`, "Organization baseline backfill (0082)".

**Technical:** migration `0082_presby_backfill_org_baseline.sql` (idx 82); data-only, idempotent, adds nothing to an organization that already holds a `member` role. Regression test `src/lib/db/domain/org-baseline-backfill.db.test.ts`. Work-log `2026-10-28-org-baseline-backfill`. No decision recorded; no what's-new post.

## 0.49.0 — 2026-10-28

### Enhancement: two-factor sign-in follows a person's role

**Value:** Until now every new account was asked to set up two-factor sign-in before it could do anything, so an ordinary member who signed in for the first time met a security step meant for the people who handle money and access. Now the people who hold those responsibilities are asked, and everyone else goes straight to their congregation.

#### What's New

**Two-factor sign-in now follows a person's role.** A new account is no longer asked to set up two-factor sign-in just for existing, so a member who signs in for the first time goes straight to their congregation. Church administrators and treasurers are still asked: so is anyone who works with giving, creates roles, gives roles to others, or manages a congregation's website addresses. A platform administrator is asked from the moment the role is given in the application. A congregation can still require it for everyone it has. An administrator can switch a person's own setting on or off, but switching it off does not excuse anyone whom a role or a congregation requires. The two-factor page in the admin area now lists everyone who is required and has not set it up, and says why. Accounts that already exist keep exactly the setting they had, and on release day, no existing account was newly asked to set up two-factor because of this change. Not every administrator is always asked: roles that cover none of the things above, such as roles for people or events, are not asked unless the congregation turns the requirement on. A platform role or platform-administrator flag set directly in the database, rather than through the application, does not turn the setting on, and nothing in the database prevents that; only review of the application's code does. Someone given a role while they are signed in is asked at their next sign-in. A brief database problem at sign-in can leave a person whose only reason is a role or a congregation without the prompt until their next check. Setting up two-factor on your own, when nothing requires it, does not start asking you for a code at sign-in.

- **The admin user page** shows the person's own setting ("Own setting: not required" when it is off) and says that a role or a congregation's policy may still require two-factor. The "2FA exempt" marker on the users list is gone.
- **Force-reset** now says what happens next: if something still requires two-factor of the person they are asked to set it up again at their next sign-in, and if nothing does they are not asked.
