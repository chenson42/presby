## Verdict

**Approved with suggestions.** The suggestions below are binding on Phase 3. The direct upgrade is the right shape. Two of the risks are silent: neither typecheck nor the current tests would catch them. Phase 3 has to design for both.

## Placement

- **Directory placement:** no new directories or modules. Every change is an edit in place to the 50 files that import zod or the resolver, plus `package.json` and `package-lock.json`. The guard test (Notes, item 6) sits next to the existing source-scan tests.
- **Server vs Client split:** unchanged. Schema files stay pure so the `'use client'` forms and the `'use server'` actions keep sharing them. No file changes runtime.
- **Dependencies:** no new package. It is a major bump of an existing one, checked against the criteria:
  1. *Already solved?* Yes. This is the same dependency.
  2. *Maintained and compatible?* zod 4.6.7 is the current release. All three things that depend on zod accept v4: `@hookform/resolvers@5.9.1`, `eslint-plugin-react-hooks@7.1.1` and `zod-validation-error@4.0.2` all declare `^3.25.0 || ^4.0.0`. So the lockfile can hold one shared copy of zod 4.6.7 with no `overrides`.
  3. *Edge?* `src/proxy.ts` doesn't import zod. Not applicable.
  4. *Bundle size:* zod 4 classic is no larger than 3.x. Stay on the classic `zod` entry. Do not adopt `zod/mini`, which is a different API.
  5. *License:* MIT, unchanged.
  - **`@hookform/resolvers`:** 5.9.1 detects v4 schemas at runtime (it checks `'_zod' in schema`), so no bump is required. 5.9.2 is fine to take. 6.0.0 is a separate major release and out of scope.

### Ruling 1: the upgrade path

**Bump straight to `zod@^4.6.7` and use the v4 API everywhere. The `zod/v3` compatibility subpath is rejected.**

- zod 4.6.7 still ships `zod/v3`, but I checked it and it does not carry the fix:
  - In the 4.6.7 tarball, `src/v3` is byte-identical to 4.6.5.
  - Its `ZodArray._parse` still adds a `too_big` issue and then parses every element anyway.
  - The 4.6.7 fix (`capSize()` / `util.sizeCaps()`) exists only in `src/v4/core/schemas.ts` and `compile.ts`.
  - Upstream issue colinhacks/zod#6653, which reports the v3 behaviour, is open. The maintainer has said v3 is no longer published and that he doesn't consider this a vulnerability.
- `npm audit` matches on the installed package version. Code using `zod/v3` would therefore pass the audit gate while still exposed. The subpath would hide the advisory rather than fix it, so it is ruled out even as an interim step.
- The fix has a limit Phase 3 must design around. 4.6.7 only stops early on **size checks that come before every other check** (`_length`, `_size` or `_equals` checks at the front of the chain), and arrays with no bound are not covered. The one server-side array is `src/app/(admin)/admin/organizations/[id]/actions.ts:1038`: `z.array(z.string().regex(UUID_RE)).min(1).max(20)`. It is the exact shape from the advisory, and it is covered because both `min` and `max` are leading size checks. **Rule: on any collection schema, size checks come first, before any `.refine()`.** A refine placed ahead of `.max()` switches the early stop off.

4. **Default messages changed.** See Ruling 3.
5. **`.email()` is deprecated and its pattern changed slightly:** `src/app/(admin)/admin/organizations/[id]/actions.ts:711`. Copy is unaffected, because failures return the fixed string at `:837` and `:882`. Use `z.email()` after `.trim().toLowerCase()`, keeping that order.
6. **Things that need a test rather than a code change:**

### Ruling 3: user-visible error messages

zod messages reach the UI by three routes:
- RHF `formState.errors.*.message`.
- The giving `invalidInput()` → `zodFieldErrors()` path (`src/lib/giving/field-errors.ts:13`), which also runs client-side at `offline-gift-form.tsx:79`.
- `issues[0]?.message` at `filings/actions.ts:121` and `designation-holder-copy.ts:64`.

Almost every check users can actually trigger already has its own message. **The one default a user can reach is `src/app/(org)/o/[slug]/admin/staff/position-schema.ts:40-41`.** It is `.max(200)` with no message, shown at `add-staff-position-form.tsx:301-303` and `:320-322`; the inputs have no `maxLength`. On v3 it reads "String must contain at most 200 character(s)"; on v4 it would read "Too big: expected string to have <=200 characters".

The remaining defaults can only be reached by tampering with the request:
- UUID fields with no message, in the giving actions and filings.
- `z.enum` with no message. Every form defaults the field to a valid value: `add-group-member-form.tsx:33`, `add-officer-term-form.tsx:33`, `record-appointment-form.tsx:40`, `statistics-submit-form.tsx:133`.

**How to keep the copy stable:**
- **Give each user-reachable check an explicit message, pinned to the string it shows today.** "No user-visible change" is the exit criterion; improving that copy is an optional follow-up.
- **No global error map** (`z.config({ customError })`). It is a side effect at module load that would have to run before the first parse in both the server and client bundles, and it fails silently if any bundle misses it.
- Wording changes on tamper-only paths are accepted. Phase 3 lists them by file:line in Edge Cases.

### Ruling 5: test strategy

What proves "no user-visible change" is **characterization tests, committed before the bump**. Commit 1 adds them and they pass on zod 3.25.76. Commit 2 bumps zod and converts the code; the tests stay unedited and must still pass. QA confirms the order from the commit history. The tests are:

1. **Golden messages per schema.** For every exported schema, feed representative bad input and assert the exact first message for each path, using the same functions the UI uses (`zodFieldErrors`, `issues[0]?.message`, the RHF resolver result). Cover:
   - `position-schema.ts:40-41` at 201 characters.
   - `connection-input.ts` with `NaN`, `undefined`, `1.5` and out-of-range values.
   - The cross-field issues from `event-schema.ts` together with a field-level failure.
   - `gift-input.ts` for each donor mode.
2. **Parsed output for valid input.** Deep-equality on `parsed.data` for valid input, including missing optional keys: the `"US"` default in `donor-input.ts:61`, the null normalizations, and the intersection at `fund-input.ts:64`.
3. **Non-RFC ids still accepted.** Every id schema accepts `00000000-0000-0000-0000-000000000005` and `d9100000-0000-0000-0000-000000000010`, and rejects `not-a-uuid`.
4. **Advisory regression.** `revokeHolderFieldsSchema` given a 100,000-element `expectedGrantIds` returns exactly one `too_big` issue, well inside a time budget. This one is expected to fail on 3.x and pass on 4.6.7, so it belongs in commit 2. It proves the early stop actually applies.
5. **Gate.** `npm run test`, `typecheck`, `lint`, `check`, the full Playwright suite (the seeds are where the UUID risk lives), and both hydration lanes (`test:e2e:prod` included, because every form root's resolver changes). Also `npm ls zod` showing exactly one copy at ≥ 4.6.7, and `node scripts/ci/audit-prod.mjs` passing with the GHSA entry removed.
6. **Auth smoke not required.** No zod importer is under `src/auth.ts`, `src/proxy.ts`, `src/app/(auth)/`, `src/app/api/auth/` or `src/lib/auth/`, so the MFA running-server smoke doesn't apply. QA should confirm this from the final diff.
