**Facts I verified, since the rest of this review leans on them:**

  - Purpose Statement.
  - Nine Guidelines for Use: Support the Church's Mission; Practice Transparency; Keep Human Responsibility Central; Respect the Limits of Ministry; Protect Privacy and Security; Rely on Expertise; Use with Restraint; Be Watchful of Bias; Stay Rooted in Faith.
  - Implementation: annual review, training, designated individuals or committees, prayerful discernment before adopting new tools, sharing experience.

## Flows

**Flow 1: Run the trainer (public).** Entry is a site page where the site maintainer placed the live slot, or the platform-owned URL (the `careers` / `give` precedent: `/site/<key>/learn/spot-the-scam`, and `/learn/spot-the-scam` on a church's own domain). The visitor reads an intro, then message 1 of N. They choose; the reveal says Right/Not quite, the tells and the lesson; they tap Next. After the last message they see "x of N correct" and the rules, with "Practice again".
- Failure: the toggle is off, the org has no serving site, or the key is unknown. All three give the site's one neutral 404, byte-identical, so a toggle state never reveals which congregations are tenants (DECISION-040, as `/careers` does).
- Failure: JavaScript is off. A `<noscript>` block plus a static, printable "five rules" card (the prototype has no no-JS path for the trainer; its own decision-030 admits this).
- Failure: the island fails to load or hydrate. The static rules card is still the fallback.

**Flow 2: Run the trainer (portal).** Entry is the portal tile, then `/o/<slug>/…learn/spot-the-scam`. The page shows the same trainer plus a leader panel: the public URL to share or print in the bulletin, and a "use this together" note. If the org has no serving public site, the panel says so plainly ("Your public website isn't live yet, so there is no public link to share") instead of showing a link that 404s.
- Failure: toggle off shows the honest off state with a pointer to Features. A viewer who is not in the org gets the standard four-way miss response.

**Flow 3: Turn features on.** Features page, then toggle. "Spot the scam" is listed for every org type. "AI policy" is listed for a congregation or NWC only. For a presbytery or synod it is absent from the list, `invalid_key` on a forged post, and `false` in the resolver.
- Failure: a non-holder gets the existing forbidden state.

**Flow 4: Adopt and record a policy (portal).**
1. Entry is the AI policy tile, which opens an overview. The empty state is: what RUS-08 and its sample policy are, "advisory, not binding" as the first block, "Build our policy".
2. **Choose.** The organization name comes from the organization record, not typed. The nine Guidelines, Implementation and Conclusion are fixed text. The local choices are who is accountable (a role or a name), the review interval, and a few optional "local additions" (staff use, labeling practice, data handling). The page marks local additions as "added by us, not PC(USA) text".
3. **Review.** The server composes the full document and shows it, printable.
4. **Record.** The fields are:
   - the date the Session acted (not in the future);
   - a minute reference (optional, bounded);
   - "Show on our website" (default off).
   The button reads "Record adoption".
5. Success shows the record: adopted on, recorded by, template version, review-by date, and Print.
- Failure: validation errors are inline and human. A database failure says "We couldn't save this. Nothing was recorded. Try again." The user's choices are kept in the form. A double submit records once.
- Failure: the feature is turned off mid-flow, or a newer template version has appeared while the tab was open. The action refuses with a specific message.

**Flow 5: Re-adopt, supersede, void.** A later adoption supersedes the earlier one. The earlier row is kept and shown in history with its dates. A mistake is corrected by voiding with a required reason and re-recording. There is no edit and no delete. The current policy is the latest non-voided record; if the latest is voided, the previous one is current again.
- Failure: a back-dated adoption earlier than the current one is refused with a message, because a clerk would otherwise silently rewrite history.

**Flow 6: Public display of the adopted policy (Part B).** A live slot (name for Phase 3) on a site page shows the current adopted policy, only when the toggle is on and the record's "show on our website" is set. Otherwise it shows nothing and gives a neutral 404 on any platform-owned route. A site with no placed slot shows nothing.

**Flow 7: PC(USA) revises the sample.** Code gains a new template version. Existing records keep their own snapshot. The overview nudges "A newer version of the sample policy is available. Review and re-adopt if your Session chooses." Nothing changes automatically.

## Permissions & Flags

- **Permissions.** The trainer needs none: it is public content, and the portal tile and page are permission-blind like every tile (DECISION-162). The policy needs one new tenant permission, "record an adopted AI policy". Phase 3 names the key; this is a new tenant authorization key, so the resolver and its bundles are touched (architect should note this).
  - It should sit in the founding-administrator bundle and in a Clerk of Session derived grant. A clerk of session office already exists (`clerk_of_session`).
  - Viewing the adopted policy and its history should be broader (any member of the org with portal access). The adopted policy is the church's witness, not a tier-2 or tier-3 secret, so it is tier 1.
  - The recorder holds no more authority than their role gives. A presbytery administrator cannot record for a member congregation, and a platform admin has no path at all. State both in the design.
- **Toggles, not flags.** There is no global flag (operator rule: no new platform flags pre-live). Two entries in `ORG_FEATURE_CATALOG`, both `flag: null`, `provisionedOn: false` (missing row means off) and `operatorEnabled: false` (self-service by the `org_features.manage` holder):
  - **Spot the scam:** `orgTypes: null`, so all four organization types.
  - **AI policy:** `orgTypes: ["congregation","new_worshiping_community"]`. The tile `orgTypeScope` must be set-equal to it (the pinned `tiles.test.ts` rule).
- **The anonymous read has to compose the toggle in SQL** (the `presby_public_careers` / `presby_worship_enabled` precedent), because an anonymous request has no `personId`. So even the no-data trainer needs a small migration (the pre-assigned 0087) for the public enabled check, and `*-toggle.test.ts` pins to the catalog entry.
- **Rollback.** Turning the toggle off hides every surface, deletes nothing, and the records persist. There is no flag, so the toggle is the whole rollback. Phase 3 should state that for the whole org population: to pull the feature everywhere at once there is no switch other than a deploy. That is accepted under the operator rule, but it should be a stated residual.
- **Tile placement** (for Phase 2 and 3): `DOMAIN_LABELS` has no "Learn" domain. Either add one (which touches the category axis, `org-feature-categories` and tests) or place trainer under `communications` and policy under `governance`. Not decided here.

## Gaps the Request Didn't Address

**Part A: Scam trainer**

- **A1. The #1 fear in the operator's own research has no scenario.** The research check-in says voice cloning and deepfakes are what older members most fear. The prototype's six scenarios are all email or text, with no phone call and no voicemail. A trainer built "for older adults" without the grandchild-in-trouble or pastor's-voice call misses the point of building it. Resolution: add at least one voicemail or phone-call scenario, shown as a transcript with a "voicemail" channel variant, and one new rule ("agree a family code word; hang up and call back on a number you already have"). Content authoring is the operator's call; if it is deferred, say so explicitly and track it.
- **A2. Real-looking data in the scenarios.** The public repo may not carry any of these (No Real Data):
  - `Routing: 044000037 · Account: 7729918260`. 044000037 is a real, checksum-valid bank routing number. Replace both with obviously fictional values.
  - Two of the prototype's sender domains look like real organizations' domains (named only in the private prototype). The look-alike domains (`gmail-mail.co`, `presbytery-payments.net`, `mailbox-quota-alerts.com`) may be registered.
  - The named people ("Pastor David Miller", "Rev. Susan", "Carol") should be invented.
  - The tripwire (`scripts/check-secrets-pii.mjs`) treats emails off the safe-domain allowlist as soft findings, but that is not a safe place to rest. Use one fictional church throughout, with `.invalid`/`example.*` domains and look-alikes made by a one-character or hyphen swap of that fictional domain. This teaches the same lesson without a real domain.
  - `877-908-3360` (the AARP Fraud Watch helpline) is not in the trainer or its page. It is in the prototype's resource hub list (`hub-list.tsx`), which is Increment 2. When it lands, the phone regex (`\(?\b\d{3}\)?[-. ](?!555\b)\d{3}[-. ]\d{4}\b`) will flag it as a soft finding. It is a real public number of a real organization, so annotate it `// leak-ok: public helpline of a national nonprofit` and keep it out of seeds and fixtures. Phase 3 of Increment 2 should own that. Increment 1 should not add it.
  - The prototype's `614-555-0187` is fine (the 555 exchange convention).
- **A3. Content must be organization-neutral.** The prototype names "the synod" and "the presbytery" in genuine-email scenarios. In PresbyPortal the same text renders on a congregation's, an NWC's, a presbytery's or a synod's site. Each scenario's sender should read correctly on any of them, or the fictional church should be the sender everywhere. No per-organization personalization in v1 (a "genuine" training email using the real org name is itself a spoofing aid).
- **A4. Dead link.** The result screen links to `/learn/ai-basics` (Increment 2). It must not ship as a dead link. Use no link, or the "five rules" print card.
- **A5. Nothing stored, and that must be a tested acceptance criterion, not an omission.** Score is in the tab only. No cookies (a custom host has no cookies), no localStorage, no `fetch` after load, no analytics or aggregate counts, even anonymized (the prototype's own policy-builder Phase 1 put this in writing). The intro's claim ("private, nothing you click can hurt you") must remain true, so scenarios must contain no live links: the "KEEP MY ACCOUNT ACTIVE" button and the phone number must not be `<a>`, and phone-number auto-detection on iOS should be considered.
- **A6. Accessibility.** The older-adult bar the prototype claims (17px base, serif, 44px targets) is stated in the Intent but is partly a property of the prototype's own theme. Inside a PresbyPortal site, the brand cascade decides fonts and colours. Requirements for Phase 3:
  - the trainer sets its own minimum type size and 44px targets, and does not inherit them from a site's brand;
  - contrast holds under any org's brand tokens (the correct/not-quite states must never be colour-only; the prototype has the words "Right."/"Not quite.", good);
  - the reveal is announced (it is not today: the prototype swaps a `<div>` with no `aria-live` or focus move, so a screen-reader user gets silence after tapping);
  - keyboard operable;
  - works at 360px (the grid is `sm:grid-cols-2`, so fine);
  - no motion dependence.
- **A7. Print.** The prototype's trainer has no print stylesheet (only the builder does). The Intent lists print as a design property. The one thing worth printing is the "five rules" card, for bulletins and fridge doors. Include a printable rules card; do not print the interactive trainer.
- **A8. Per-organization scenarios, and "who do I call at our church".** Out of Increment 1 (see Out of Scope). Worth noting: an org's own contact phone, as the careers slot already reads, would make the result screen's "call the number you already have" concrete. Defer, but name it.
- **A9. Content ages.** AI-era scam patterns change. Give the scenario set a version and a "last reviewed" date, and add a TODO line to review it. Updates ship to every org at once because content is platform-owned.

- **B3. "Adopt and record" has no existing mechanic (operator question Q1).** My recommendation, for the operator to confirm:

  - Reasons: the roll-approval machinery is purpose-built (roll-specific definers and freeze triggers); there is no generic motion or minutes feature; and building an in-app Session vote would imply PresbyPortal can verify the Session acted, which it cannot.

  - template id and version (a closed catalog of versions in code, not free text);
  - the validated choices;
  - **the full composed text as adopted, as a snapshot** (a policy that was adopted must stay reproducible after the code or the catalog moves; and so that a later template version never silently changes an adopted record);
  - adoption date (the Session's action), minute reference (bounded), accountable text, review-by date;
  - recorded-by user and person, recorded-at;

  Append-only and immutable once written, except the soft-lifecycle fields. No hard delete (operator rule: all deletes are soft).

Rewrite it truthfully: nothing is saved until you press Record. I recommend no server-side draft: the inputs are three or four choices, and the Record step is the persistence. Say so, so a session timeout mid-form is a known, accepted residual. The anonymous builder (for churches not on PresbyPortal) belongs in the embed (Increment 3), not here.

A policy not shown publicly is still visible to org members; that is the intended default.

## Adversarial pass

- **Redirect targets.** Neither feature takes a `next`, `callbackUrl` or `redirect` parameter. Confirm in the design that the policy overview and trainer have none, and that any "back to the website" link comes from `SiteUrls` or the database row, never the request (a source-scan test already bans hand-built `/site/${…}`). Addressed by design if that holds.
- **Enumeration (public routes).** The trainer and public policy routes answer one neutral 404, byte-identical, for toggle-off, category-off, no-serving-site, unknown key and, for the policy, unpublished. A "published policy exists but is hidden" state must not be distinguishable from "no policy". Timing as well, per DECISION-040. Gap until pinned in Phase 3 tests.
- **State-machine shortcuts.** The record action must work from a direct post, so it re-validates everything (version, choices, dates, toggle on, permission) and never trusts that the Review step ran. A stale tab after a new template version is refused, not silently recorded against the old version.
- **Input boundaries.** Server-side length caps and trimming on accountable text, minute reference and void reason. Reject or normalize control characters, zero-width and bidi-override characters (an RTL override in a name could reorder printed or published text). Render as plain text everywhere, in the page, print and public slot: no HTML or markdown. Do template substitution in one pass over the template, not sequentially over a result, so a value containing `{{…}}` cannot inject into a later substitution. The org name comes from the database, not the form.
- **Self-targeting and authority.** A platform admin has no path (Two Hierarchies). A presbytery admin cannot record for a member congregation. Someone not in the org gets the four-way miss response. A recorder who is also the only Session member is permitted, and the record says "recorded by", never "approved". Because this is not an approval, `selfApproved` does not apply, but the copy must not imply the Session approved. Gap if Q1 comes back as "Session members affirm".
- **Replay and concurrency.** Two clerks record at once, or a double click: define the current record by a deterministic rule and make a retry idempotent. A void racing a re-adoption must not leave zero or two current records.
- **Misattribution.** B5 above: server-composed text only, with the version id from a closed catalog.
- **Trainer content safety.** No live links, `tel:` or `mailto:` in scenarios (including auto-linking by mobile browsers), so the "nothing you click can hurt you" claim stays true.
