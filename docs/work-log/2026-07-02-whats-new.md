## Phase 1 — Functional Refinement — 2026-07-02

**Owner:** analyst
**Status:** complete

### Summary

Shape decision: **Option (b) — `whats_new_entries` table**. The existing `docs/release-notes/*.md` files are explicitly developer-facing (v0.4 covers upstream-sync; v0.5 covers commit-message hooks and `stats:escape`) and would confuse members of any real fork. Even if a fork replaces the release notes with their own content, the release-notes format is designed for implementation-level detail, not member-facing announcements. The clean teaching-artifact lesson is option (b): an admin explicitly publishes short entries for members; nothing surfaces accidentally. Scoped minimally — no per-user seen-marker in V1, no feedback linkage in V1, no draft/schedule mechanism in V1. Rule 12 gains an advisory addendum only.

### What I did

**Shape decision rationale (required before Pass 1)**

Option (a) was evaluated and rejected on three grounds:

1. Content is not member-safe. v0.5 discusses the commit-message hook, `stats:escape`, and Conventional Commits — developer tooling. v0.4 discusses upstream-sync for fork maintainers. Even v0.1–v0.3 describe admin shell wiring, TOTP schema, and route-protection internals. No member of a real fork's app should see this.
2. The curation problem is structural. A fork that replaces these files with their own release notes still faces the same issue: release notes conventionally contain implementation context ("Root Cause: the middleware was importing a node-only module…") that members should not see. Requiring forks to maintain a second, parallel "member-safe" section inside their release notes is a bad teaching artifact.
3. The admin docs viewer already gates release notes behind `admin.release_notes` — there is no current member-facing render path and adding one requires the same amount of work as option (b), minus the clean separation.

Option (b) is the correct teaching artifact: the `whats_new_entries` table cleanly separates "what the developer tracks" from "what the member sees." Huddleup's implementation is production-proven. The starter strips `minVersion` (no native app) and the `whatsNewSeenAt` per-user marker (deferred to V2 — adds meaningful DB-write complexity for marginal V1 value).

**Pass 1 — User Verbs**

Surfaces and verbs:

Authenticated member (no roles required):
- Member reads a "What's new" card on `/home` showing the latest 3 entries
- Member clicks "See all" from the home card → navigates to `/whats-new`
- Member reads the full entry list at `/whats-new`, newest first

Admin (requires `admin.whats_new` permission):
- Admin navigates to `/admin/whats-new`
- Admin clicks "New entry" → fills form (emoji optional, title, body) → submits
- Admin clicks edit on an existing entry → form pre-populated → submits
- Admin clicks delete on an entry → confirms in a dialog → entry removed

No anonymous-visitor verbs. `/whats-new` lives in the `(member)` route group (authenticated-only); unauthenticated users are redirected to sign-in by the proxy.

**Pass 2 — Flow Audit**

Flow 1 — Member reads home card
Entry: authenticated member loads `/home`.
Step 1: server fetches latest 3 entries from `whats_new_entries` ORDER BY `publishedAt` DESC LIMIT 3.
Step 2: zero entries → card is not rendered (do not show an empty "What's new" card on the home page; keep it clean).
Step 3: 1–3 entries → card renders with entry list and "See all" link.
Success: member sees the most recent updates in a compact card.
Failure — DB unavailable: home page renders without the card (graceful degradation; the card fetch should not block the rest of the page).

Flow 2 — Member reads full list
Entry: member clicks "See all" or navigates directly to `/whats-new`.
Step 1: page fetches all entries ORDER BY `publishedAt` DESC.
Success: full list, newest first. Empty state: "No updates yet — check back soon."
Failure — DB unavailable: error state with retry prompt, not a blank page.

Flow 3 — Admin creates entry
Entry: admin navigates to `/admin/whats-new`, clicks "New entry."
Step 1: form renders; fields: emoji (optional, ≤2 Unicode code points), title (required, ≤100 chars), body (required, ≤500 chars, plain text only).
Step 2: admin fills and submits.
Step 3: server action validates; on error, returns inline field errors.
Step 4: inserts row with `publishedAt = NOW()`; writes audit event `WHATS_NEW_ENTRY_CREATED`.
Success: toast "Entry published." Entry appears in admin list and is immediately visible to members on `/home` and `/whats-new`.
Failure — validation: inline field errors; no row written.
Failure — DB: toast "Unable to save entry — please try again."

Flow 4 — Admin edits entry
Entry: admin clicks edit on an existing entry.
Step 1: same form, pre-populated.
Step 2: submit → server action validates and updates row (`publishedAt` is NOT changed on edit — the entry keeps its original publication order); writes `WHATS_NEW_ENTRY_UPDATED` audit event.
Success: toast "Entry updated."
Failure — validation: inline field errors.
Failure — entry not found: toast "Entry not found — it may have been deleted."

Flow 5 — Admin deletes entry
Entry: admin clicks delete.
Step 1: shadcn `AlertDialog` confirmation: "Delete this entry? Members will no longer see it. This cannot be undone."
Step 2: confirm → server action; hard-delete; writes `WHATS_NEW_ENTRY_DELETED` audit event.
Success: toast "Entry deleted." Removed from member view immediately.
Failure — DB: toast "Unable to delete — please try again."

**Pass 3 — Permissions & Flags**

- New `FEATURES.ADMIN_WHATS_NEW = "admin.whats_new"` — no existing key covers admin CRUD for this table.
- Default role: admin only (same as all other `admin.*` keys).
- Seed: add to `FEATURE_CATALOG`; bind to admin role.
- Member read access (`/home` card and `/whats-new`): no permission gate — any authenticated user. The proxy gates on authentication, not on a feature.
- Feature flag: not needed in V1. The home card's zero-entries empty state is the natural "off" state — if no entries have been published, the card simply does not render. There is nothing to roll back.

Audit: all three admin mutations (create / update / delete) write audit events. These are admin content-management actions; while not strictly security-sensitive in the same tier as role changes or TOTP mutations, they touch user-visible content and should be audited for accountability.

**Pass 4 — Edge Cases**

- 2FA gate: member users are not subject to 2FA by default; admin users are. The proxy handles this before any page renders. No special case needed for this feature.
- Empty state (zero entries): the `/home` card must not render. The `/whats-new` page must show a helpful empty state, not a blank list.
- Empty state (fresh install): the seed script does not create any `whats_new_entries` — this is correct. The "no entries" state is the default.
- Immediate publish: there is no draft state in V1. Creating an entry makes it visible to members immediately. An admin who wants to time a publication must coordinate manually. This is a known limitation to document in Phase 3.
- Editing does not change `publishedAt`: the entry keeps its position in the list. An admin who edits a 6-month-old entry does not surface it as "new" again. This is the correct behavior.
- Body content safety: body is plain text — no markdown, no HTML. Must be rendered as JSX text nodes only (no `dangerouslySetInnerHTML`). Server action must reject (not strip) HTML in the body.
- Emoji validation: `[...emoji].length <= 2` (Unicode code-point spread), not `emoji.length` — multi-codepoint glyphs (family emoji, skin-tone modifiers) would bypass a `.length` check.
- Mobile: the home card and `/whats-new` list must work at 360px. The body field (≤500 chars) can run long on mobile. Design must account for this.
- Member on `/access-pending`: authenticated users with no roles can reach `/access-pending` but not member routes. The `/whats-new` page lives in the `(member)` route group; the proxy redirects no-role users before they reach it. Confirmed — no gap.
- Admin's "Got it" / dismiss: no dismiss in V1. The home card always shows the latest 3 entries. This is intentional scope-containment.

**Pass 5 — Adversarial**

- XSS via body field: a malicious admin submits `<script>alert(1)</script>` as body. If rendered via `dangerouslySetInnerHTML`, this executes for all members. Defense: render as JSX text nodes (`<p>{entry.body}</p>`), which escapes HTML automatically. Server-side: the action must not accept or store HTML-encoded content uncritically, but since we're storing plain text and rendering as text nodes, the render path is safe.
- Emoji field length bypass: `"👨‍👩‍👧‍👦"` (family emoji) is 1 visible character but has `.length === 11` and `[...emoji].length === 7`. A server that validates with `.length <= 2` would reject it correctly; one that uses `emoji.length <= 2` would allow strings that render as 1 character but store 11 bytes. The validation must use `[...emoji].length`.
- Admin privilege required for write: the create/update/delete actions re-check `FEATURES.ADMIN_WHATS_NEW` inside the action body. A user who loses the permission mid-session is rejected at the action layer, not just the page layer.
- Self-targeting: no self-targeting concern — the entries are not per-user.
- `/whats-new` URL direct access by unauthenticated user: redirected to sign-in by the proxy (same as all `(member)` routes).

**Ruling 1 — Option (b) table decision: ENDORSED**

The three reasons are grounded in the actual release-notes content. v0.5 discusses the commit-message hook, `stats:escape`, and Conventional Commits — none of which is member-facing content. v0.4 discusses upstream-sync for fork maintainers. A clean `whats_new_entries` table that admins populate explicitly is the correct teaching artifact. Option (a) is closed.

**Ruling 2 — Schema shape**

The analyst's sketch is approved with two adjustments:

1. `updatedAt` Drizzle convention: the project convention (established in `emailQueue` at schema.ts:326–328 and `users` at schema.ts:33–36) is `.$onUpdate(() => new Date())` — not a bare `.defaultNow()`. The `defaultNow()` only fires on INSERT; `.$onUpdate()` fires on every subsequent UPDATE. The `whats_new_entries` table must follow this pattern:
   ```typescript
   updatedAt: timestamp("updated_at", { withTimezone: true })
     .notNull()
     .defaultNow()
     .$onUpdate(() => new Date()),
   ```
2. `updatedBy`/`updatedAt` retention: KEEP both. The audit event captures the actor for accountability review; `updatedBy` on the row itself supports quick DB queries ("who last touched this entry?") without joining `audit_events`. Low-cost, consistent with the admin surface pattern. Both remain nullable (`uuid NULL REFERENCES users(id) ON DELETE SET NULL`).

Plain-text body constraint: the server action must REJECT (not strip) HTML. A body containing `<script>` or any HTML tag structure must return a validation error, not a sanitized version. Rendering plain text nodes in JSX is safe, but silent stripping at the action layer produces a misleading stored value. HARD REQUIREMENT — see Ruling 6.

`publishedAt` as ordering key: ENDORSED. Set on INSERT via `defaultNow()`. NOT changed on edit — enforced by never writing `publishedAt` in the UPDATE statement. The index `ix_whats_new_published ON (publishedAt DESC)` (note: DESC for the hot-path query) is required in migration 0007.

**Ruling 3 — Migration sequencing: TWO SEPARATE MIGRATIONS**

Two concurrent pipelines are touching the schema. RULING: separate migrations, each in its own numbered file, generated in pipeline order:

- **Migration 0006** — email-observability: five delivery timestamp columns + `ix_email_queue_provider_message_id` index on `email_queue`.
- **Migration 0007** — whats-new: `whats_new_entries` table + `ix_whats_new_published` index.

Combining them into one migration is rejected: it would couple independent features, reduce rollback granularity, and require coordination between two Phase 4 implementers on a single file.

**Generation-order constraint (MANDATORY):** `npm run db:generate` generates the next sequential SQL filename based on what already exists in `drizzle/`. If both pipelines run `db:generate` concurrently, they produce colliding filenames (two files both named `0006_*.sql`). The tech-leads for both pipelines must coordinate:

> The database-admin for email-observability (Phase 4) must run `npm run db:generate`, commit migration `0006_*.sql`, and push BEFORE the database-admin for whats-new generates migration `0007_*.sql`. Whats-new Phase 4 must not run `db:generate` until the email-observability migration is committed.

This constraint must appear in BOTH Phase 3 design docs and be listed as a prerequisite in the whats-new Phase 4 section.

**Validation Helper Spec**

`src/app/(admin)/admin/whats-new/validate.ts` — pure, zero-DB, unit-testable:

```typescript
export type WhatsNewValidationInput = {
  emoji: string;   // may be empty string (optional field)
  title: string;
  body: string;
};

export type WhatsNewValidationResult =
  | { ok: true }
  | { ok: false; errors: Partial<Record<keyof WhatsNewValidationInput, string>> };

export function validateWhatsNewEntry(
  data: WhatsNewValidationInput,
): WhatsNewValidationResult
```

Validation rules (all are HARD REQUIREMENTS from Phase 2 Ruling 6):

1. **emoji** (optional): if non-empty, `[...data.emoji.trim()].length > 2` → `"Emoji must be 2 characters or fewer."` Use Unicode code-point spread — never `emoji.length`. An empty string is valid (emoji is optional).
2. **title**: `data.title.trim().length === 0` → `"Title is required."` | `data.title.length > 100` → `"Title must be 100 characters or fewer."` | `HTML_TAG_RE.test(data.title)` → `"Title must be plain text — HTML is not allowed."`
3. **body**: `data.body.trim().length === 0` → `"Body is required."` | `data.body.length > 500` → `"Body must be 500 characters or fewer."` | `HTML_TAG_RE.test(data.body)` → `"Body must be plain text — HTML is not allowed."`

HTML rejection regex: `const HTML_TAG_RE = /<[^>]+>/;` — matches any string containing an HTML-like tag structure. This catches `<script>alert(1)</script>`, `<b>`, `<img src>`, `</p>`, etc. Rule: REJECT (return validation error) not strip. Stored values are always unmodified if they passed validation; the render path (JSX text nodes) is safe regardless.

```typescript
export const whatsNewEntries = pgTable(
  "whats_new_entries",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    emoji: text("emoji"),                             // nullable; ≤2 Unicode code points, validated server-side
    title: text("title").notNull(),                  // ≤100 chars, plain text, validated server-side
    body: text("body").notNull(),                    // ≤500 chars, plain text, validated server-side
    publishedAt: timestamp("published_at", { withTimezone: true })
      .notNull()
      .defaultNow(),                                  // set on INSERT only; UPDATE actions MUST NOT touch this column
    createdBy: uuid("created_by")
      .references(() => users.id, { onDelete: "set null" }),
    updatedAt: timestamp("updated_at", { withTimezone: true })
      .notNull()
      .defaultNow()
      .$onUpdate(() => new Date()),                   // per Phase 2 Ruling 2 ($onUpdate convention, not bare defaultNow)
    updatedBy: uuid("updated_by")
      .references(() => users.id, { onDelete: "set null" }),
  },
  (t) => [
    index("ix_whats_new_published").on(t.publishedAt.desc()), // hot-path query: ORDER BY published_at DESC
  ],
);
```
