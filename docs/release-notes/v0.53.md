## 0.53.0 — 2026-10-31

### Feature: Write to the PresbyPortal team

**Value:** About a dozen help sentences ended with "ask the person who invited you". That is a dead end for someone nobody invited: a church thinking about joining, or someone who cannot sign in. The only other way in was a public GitHub issue. Anyone can now send the PresbyPortal team a short message from the help site, without an account.

#### What's New

**The contact form.** `/help/contact` asks what the message is about, for an email address and the message itself, and optionally for a name and a congregation. Sending it gives one plain answer: the message was sent, it was not sent (try again), the form is busy (try again later), or the form isn't available right now. A sent message gets no automatic reply and no promised response time. If someone replies, a person writes the email. The form says this before you send. Messages are kept with the details you typed, but not your IP address or browser details. The form is checked by Cloudflare Turnstile and rate limits, so a person or a script can send only a few messages an hour. A message about signing in or lost codes never resets anything by itself; the team checks with the account's own email address first. The form exists only on the PresbyPortal site, never on a church's own domain.

- **Help pages that pointed nowhere now point here.** Pages read by members, treasurers or people who cannot sign in now say "ask the person who invited you, or send the PresbyPortal team a message". Pages read by administrators say to file a ticket first, because a ticket carries who you are and a reply thread, and to use the form if you cannot file one. "Getting help" now lists four ways to get help. "How a congregation gets started" no longer sends prospective churches to GitHub. The privacy policy says what the form keeps and that you can ask for your message to be cleared. Every help page's footer links to the form.
- **The team's inbox.** Platform operators who work tickets see new messages at `/admin/messages`, with a "Contact messages" card on the admin dashboard. They can read a message, mark it handled or spam, move it back to new, and clear its details. Clearing removes the name, email address, congregation and message text for good and keeps only the topic, dates and status. Messages are never deleted. Each message shows "Not verified. Anyone could have typed this address." beside the email address. Operators get one email, with no message content, at most once an hour when new messages arrive.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `admin.tickets` | Read and triage contact messages, see the dashboard card, receive the notification (existing key; no new key) |

The form needs no sign-in and no permission. There is no new platform flag and no per-congregation toggle.

#### New Routes

- `GET /help/contact` — the public contact form (static; its Server Action is the help site's only database-reaching file)
- `GET /admin/messages` and `GET /admin/messages/<id>` — the operator inbox

**Help:** `getting-help`, `how-a-congregation-gets-started`, `privacy-policy`, `using-your-code`, `setting-up-two-factor` and `accepting-your-invitation` were rewritten and walked against this release. `first-day-as-administrator`, `why-cant-i-see-this`, `turning-features-on-and-off`, `roles-who-can-do-what`, `your-congregations-website`, `events-and-the-calendar`, `signing-in`, `who-is-asked-for-a-code` and `reimbursements-for-treasurers` changed only their contact sentence.

**For the operator.** The form must work in Production before this code is deployed, because the help pages link to it. The runbook is `docs/deployment.md` "Help contact form (0083)".
1. Set `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` and `HELP_PRIVACY_CONTACT_EMAIL` in the Production scope, using a real Cloudflare widget for the production hostname. Never use Cloudflare's test keys there. `RATE_LIMIT_DISABLED` must be absent. **These same variables turn the Turnstile check on at sign-in, forgot-password and the public giving form**, so if any are new, walk those three after the deploy. Without `HELP_PRIVACY_CONTACT_EMAIL`, the privacy policy points clearing requests at a public GitHub issue.
2. Apply `0083` to production (additive: one table, guard triggers and one function; nothing reads it until the code ships), then run the catalog checks in the runbook.
3. Deploy, then send one marked test message, watch the card and the one notification, reply by hand, mark it handled, and clear it.
4. Preview deployments show "The contact form isn't available right now". That is expected, because the keys are Production-only.

**Known limits, recorded and accepted.** A message is a claim, not proof of who sent it. The per-address limit is a courtesy until it is confirmed that Vercel's `cf-connecting-ip` cannot be faked (F407); Turnstile and the overall and database ceilings are the real bound. A Cloudflare outage lets messages through unchecked, inside the same ceilings. Switching the form off quickly means revoking one function grant (in the runbook); removing the variables takes effect only at the next deploy. Whether Vercel forwards a Server Action posted to a church's own domain the same way it does locally has not been measured yet; a preview replay is tracked. Other Server Actions outside the church sites can still be reached through a church's domain until F416 lands (severity Low: no data crosses between churches and no cookie is set). Messages from strangers are kept until an operator clears them; there is no timed sweep yet.
