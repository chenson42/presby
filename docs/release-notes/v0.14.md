## 0.14.0 — 2026-08-26

### Feature: Org-branded sign-in

**Value:** A member following a link from their own congregation's live public site into `/signin` landed on generic platform-blue chrome — no visual continuity between "the church's own website" and "the church's own portal." This closes that gap without opening any new way to discover which congregations are configured tenants: the brand shown is always information the org already publishes anonymously on its own public site.

#### What's New

- `/signin` renders the destination organization's logo, brand colors, and type pairing when reached via a `callbackUrl` naming an org whose public site is already live. Every other case — no live site, a malformed slug, a DB error mid-lookup — collapses to the byte-identical platform-default page, so this never becomes a new tenant-enumeration oracle (DECISION-094, amending DECISION-047).
- The Google sign-in button is pinned to platform colors regardless of the surrounding brand, so the one third-party-styled control on the page can never be mistaken for a phishing look-alike wearing someone else's colors.
- `/totp`, `/forgot-password`, and `/reset-password` stay platform-chrome in this increment — a branded `/signin` handing off to a platform-chrome `/totp` mid-flow is an accepted, named tradeoff, not an oversight.

#### Permissions

No new permission — public, unauthenticated surface.

#### Flags

| Flag key | Default | Gates |
|----------|---------|-------|
| `ui.branded_signin` | off | Whether `/signin` reads and renders the destination org's brand at all |

### Feature: Per-organization light-only brand mode

**Value:** A congregation's real-world brand doesn't always have a dark identity — First Presbyterian Church of Westerville's teal-and-white palette was rendering muddy and unintended under a visitor's dark-mode preference. An organization can now opt all the way out of dark mode rather than living with an approximated dark variant nobody asked for.

#### What's New

- A new toggle on a congregation's brand editor (`/admin/organizations/[id]`) forces the light palette on both the public site and the member portal, even when a visitor's OS or browser prefers dark.
- Off by default and per-organization: every existing branded congregation keeps its dark variant unless an admin opts it out.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `admin.organizations` | Setting light-only mode at `/admin/organizations/[id]` — no new key, reuses the existing admin surface |

### Feature: A fourth curated font pairing — Contemporary (Montserrat / Open Sans)

**Value:** Every congregation's brand fonts, until now, had to approximate one of three curated pairings even where a church's real, printed identity used something else entirely. This pairing gives an admin an exact match for a genuinely common combination instead of a closest-guess substitute — discovered while matching FPCW's real, live stylesheet font-for-font.

#### What's New

- "Contemporary" (Montserrat / Open Sans) joins Classic, Modern, and Warm in the brand editor's type-pairing picker — same self-hosted, build-time-only `next/font/google` mechanism as the other three, so no runtime request to Google Fonts ever leaves a member's browser.
- Open font selection — letting any admin pick any two Google Fonts at configuration time — was weighed and explicitly deferred (DECISION-093); it would require either a much larger ongoing curation cost or a runtime fetch that reverses that guarantee.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `admin.organizations` | Choosing a type pairing at `/admin/organizations/[id]` — no new key |

### Feature: Portal home v2 and directory v2 — search, households, deacons

**Value:** A congregation's own portal home was a static stub, and its directory was a flat, unsearchable list with no notion of households or of who a member's own deacon is. This rebuilds both as real, tenant-facing surfaces — the first capabilities a congregation's own staff, not a platform admin, can act on inside `/o/<slug>`.

#### What's New

- **Portal home** (`/o/<slug>`): a time-aware greeting, a find-a-person search that jumps straight to a single match, and a "Yours" household zone that only renders when the signed-in member actually has one — nothing shows where there's nothing to show.
- **Directory** (`/o/<slug>/directory`): a searchable card grid (name, email, phone), a households view, and dedicated person and household detail pages, all sharing one privacy predicate so no reader can see more or less than any other.
- **Deacon linkage**: a household's deacon is now derived directly from the officer roster (`officer_terms.org_unit_id`) instead of a hand-editable field, so it can never point at someone who isn't actually serving and stays in sync with service dates automatically. A new parishes view lists every district's deacon for members holding elevated directory visibility, with lock badges marking exactly which fields that visibility unlocks.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `directory.view` | The directory itself (existing) |
| `directory.view_hidden` | Parishes view and privacy-hidden fields elsewhere in the directory (new — bound to the derived diaconate group and `stated_clerk`) |

#### Flags

| Flag key | Default | Gates |
|----------|---------|-------|
| `org_portal.home_v2` | off | The rebuilt portal home; off renders the original stub |
| `org_portal.directory_v2` | off | Search/grid/households/parishes; off renders the original flat list (rides the existing `org_portal.directory`) |

#### New Routes

- `GET /o/<slug>/directory/[personId]` — person detail
- `GET /o/<slug>/directory/households` and `GET /o/<slug>/directory/households/[householdId]` — households view and detail
- `GET /o/<slug>/directory/parishes` — deacon roster, `directory.view_hidden` only

### Feature: Org-identity portal header + persistent menu

**Value:** Inside a congregation's own portal, the header still read "presby" — nothing distinguished the space as the congregation's own — and every page beyond the home tile grid was reachable only by typing a URL. Refined twice this release: once at initial ship, once against direct feedback from using the shipped chrome ("we should use the organization logo at a reasonable size... logo should take you back to the public site").

#### What's New

- The platform wordmark inside `/o/<slug>` gives way to the organization's own logo — the un-cropped wordmark, not a cropped icon; the first cut sliced most of an uploaded logo away — linking to the congregation's own public site rather than the portal home. The organization switcher renders the org's name as screen-reader-only text once a real logo is present, so nothing duplicates it visibly.
- A persistent, flag-filtered menu row (Home, Directory, Administration, Tickets, Give feedback) now runs under the header on every portal page, wraps cleanly at mobile widths, and marks the active route.
- A "Members" tile was added to the portal-home tile grid, wired for the member-management surface — that surface ships separately and isn't live yet, so the tile stays invisible until its own flag is seeded.

#### Flags

| Flag key | Default | Gates |
|----------|---------|-------|
| `org_portal.chrome_v2` | off | The org-identity header and persistent menu |
| `org_portal.feedback` | off | The "Give feedback" menu entry — split off from the tickets flag it previously borrowed, so rolling back tickets can no longer silently take feedback with it |

### Security: Credentials sign-in could bypass the 2FA gate on a direct callbackUrl

**Problem:** A member enrolled in two-factor authentication could reach `/admin` or `/o/<slug>` — fully inside the app — without ever completing the TOTP challenge, if they signed in via a credentials `callbackUrl` pointing directly at a protected destination (the redirect a session-expiry bounce produces is one real path into this).

**Root Cause:** Next's Server-Action redirect-inlining optimization soft-navigates straight to a same-hop `callbackUrl` with no actual HTTP request — so `src/proxy.ts`, the Edge gate that enforces the 2FA challenge, never ran at all for that navigation. Found while building this release's org-branded sign-in feature and its own mandatory MFA login smoke test.

**Fix:** Credentials sign-in now evaluates the same two-factor predicate the session itself relies on before it ever redirects, and issues its own redirect — to `/totp` when required, straight to the destination otherwise — so a 2FA-required member always passes the challenge exactly once, regardless of entry path. Fails closed on any user-row lookup miss.

**Testing:**
- [x] Regression spec asserting on observed network requests — the only kind of check that would have caught the original bug
- [x] Confirmed failing before the fix, passing after, independently re-verified

### Infrastructure: Public-site parity batch — SEO surfaces, embed CSP, page fixes

**Background:** Hands-on fidelity testing of the FPCW public site against the real church website (the visual/behavioral parity work itself lives in the external `presby-site-kit`/`site-fpcw` repos) surfaced several small, independently low-risk presby-repo gaps.

**Changes:**
- Every public congregation site now has its own crawlable entry point: a `robots.txt` that allows `/site/` while the rest of the pre-release platform stays disallowed, and a per-organization `/site/<slug>/sitemap.xml` — previously there was one static platform-wide `robots.txt` and no sitemap at all.
- Every public-site page now sets its own real browser-tab title (the content-authored title, or the organization's name) instead of falling through to the platform's default "presby" title; the read behind it is now request-memoized instead of hit twice per page view.
- The Content-Security-Policy's `frame-src` now allows the two trusted video-embed hosts (`youtube-nocookie.com`, `player.vimeo.com`), so an embedded sermon or promotional video isn't silently blocked.
- A site's member-login nav link can now fold into a content-authored navigation group (e.g. "Connect") instead of always rendering as its own top-level item.

This reads as a stale test fixture rather than a routing defect (the route's own 404 and content-type behavior both still pass), but it is a real, currently-failing test on `main` as of this release and needs a fast follow-up.
