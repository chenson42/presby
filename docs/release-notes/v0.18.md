## 0.18.1 — 2026-08-27

### Defect Fix: Credentials tile shown to congregations

**Problem:** With the credentials feature enabled, every congregation's portal showed a Credentials tile (in the tile grid, the navigation row, and the footer) that led to a dead end — a permission-denied page advising members to "ask your stated clerk," which no congregation role can ever satisfy, since ministry credentials is a presbytery-level tool by design.

**Root Cause:** The portal tile registry filtered tiles by category and feature flag only; it had no notion of organization type, and the flag is platform-wide.

**Fix:** Tiles can now declare which organization types they serve; the Credentials tile is scoped to presbyteries and disappears from all four rendering surfaces everywhere else. Visiting the page directly at a non-presbytery organization now shows an honest "this is a presbytery-level tool" note instead of misleading permission language.

**Testing:**
- [x] Regression tests written failing-first: congregation excluded (even with the flag on), presbytery included, synod/GA excluded, filter-order pinned, direct-URL state verified without reaching the data layer
- [x] Verified live at a congregation and a presbytery, desktop and 360px

### Defect Fix: Inconsistent form-input backgrounds

**Problem:** Text inputs looked white on some screens and gray on others — most visibly, form fields inside white panels didn't match the search fields and dropdowns next to them.

**Root Cause:** The generated Input and Textarea primitives kept the upstream shadcn `bg-transparent` default instead of the app's documented `bg-background` control standard, so each input took on the color of whatever surface it sat on; a few screens had patched it per-use, deepening the inconsistency.

**Fix:** The two primitives now carry `bg-background` natively (recorded as a deliberate divergence from upstream), the per-use patches were removed, and the UI standards doc now says so — every input, textarea, and select renders the same surface everywhere.

**Testing:**
- [x] Independent sweep of all 359 component files — zero remaining background overrides on the primitives
- [x] Computed-style verification across branded and platform-palette pages, plus a dark-mode check (a pre-existing dark-mode variance was found, tracked separately, unchanged by this fix)

## 0.18.0 — 2026-08-27

### Feature: Children's ministry — roster and guardian links

**Value:** Congregations run Sunday school, nursery, and youth programs, but until now there was no way to see the congregation's children in one place or record who a child's guardians and emergency contacts are. This is the staff-facing foundation; guardian self-service, consent/medical intake forms, and program check-in follow as later increments.

#### What's New

- A new Children roster (linked from the Members tools) lists everyone under 18 with their age and grade, computed from the birthdate already on file — a child with no recorded birthdate won't appear until one is added.
- Each child's record gains a Guardians & contacts section where staff can link parents/guardians/emergency contacts — preferring a link to an existing directory person (so their phone and email come along), with a free-text name as the fallback for contacts not in the system.
- A new `children.roster` permission gates all of it, bound to a new Children's Ministry Administrator role — deliberately separate from the medical-information permission, so a Sunday-school coordinator can hold the roster without automatically seeing allergy or medical data.
- The roster shows each child's full birthdate to permission holders even when it's hidden from the congregation directory — age is the roster's whole point — and the permission's own description says so plainly, so an org admin granting it knows exactly what it unlocks.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `children.roster` | The children's roster and guardian-link management |

#### New Routes

- `GET /o/<slug>/admin/members/children` — the roster
- `GET/POST /o/<slug>/admin/members/<id>/edit/guardians` — guardian-link management

### Feature: Events calendar (admin)

**Value:** Congregations schedule recurring worship services, committee meetings, and program events, but presby had no notion of an event at all — children's-ministry check-in, the public site calendar, and future RSVP features all need one. This ships the events model and the staff-facing admin surface; check-in and the public calendar build on it as separate increments.

#### What's New

- A new Events tool (its own tile and nav entry) where staff can create a one-time event or a recurring series — "This event repeats" reveals weekly and monthly-by-weekday patterns, bounded to at most 52 occurrences per series.
- A series is materialized as real events on real dates, so cancelling one occurrence (say, the meeting that falls on Christmas) never touches the rest — and extending a series adds occurrences going forward without ever moving or rewriting the events already on the calendar.
- Events cancel rather than delete: a cancelled event stays visible with its history, and its edit/cancel controls disappear so it can't be modified by accident.
- Each event carries a "Visible on the public calendar" setting, ready for the public site calendar to consume in a later release — checking it today has no visible effect yet.
- A new `events.manage` permission gates all of it. It ships with no default role binding — each congregation decides who schedules.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `events.manage` | Viewing the admin events list and creating, editing, cancelling, or extending events |

#### New Routes

- `GET /o/<slug>/admin/events` — the events list
- `GET/POST /o/<slug>/admin/events/new` — create an event or series
- `GET/POST /o/<slug>/admin/events/<eventId>` — event detail, edit, cancel, extend series

*The whole surface ships behind the `org_portal.events` flag, seeded off — no congregation sees it until the flag is enabled.*

### Feature: Presbytery credentials & pastoral appointments

**Value:** A presbytery's stated clerk keeps the authoritative record of who is ordained, their current standing, and which congregation each minister serves — but until now the platform had no way to record any of it. This is the first feature built specifically for presbyteries rather than congregations.

#### What's New

- A new Credentials tool (presbytery portal) where the clerk records a minister's ordination and manages it over time. Ordination is lifelong, so the page separates two very different acts: **Change status** records current standing (active, honorably retired, on leave, and so on) without ever ending the ordination, while **End ordination** is reserved for removal — and each dialog says so in plain language.
- Pastoral appointments: record who serves as pastor of which member congregation, and end an appointment when the call concludes. The congregation picker only offers the presbytery's own member congregations — an appointment can never point outside the presbytery.
- A minister must already hold membership at the presbytery before either record can be created; the forms say exactly that and link to Members when the person isn't there yet.
- Every action writes an audit event (ordination recorded, status changed, appointment recorded, appointment ended), so the credentials record has a complete trail.
- A new `credentials.manage` permission gates all of it, and a new **Presbytery Stated Clerk** template role — the first role template scoped to an organization type — carries it. Congregations never see or adopt the presbytery-only template.

#### Verified presbytery portal support

Alongside the new feature, the generic org portal (directory, members, groups, officers, feedback, branding) was verified end-to-end for a presbytery organization. It works as-is; four spots where page copy assumed a congregation ("your congregation", congregation-flavored empty states) were reworded to fit both.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `credentials.manage` | Viewing the credentials page and recording/updating ordinations and appointments |

#### New Routes

- `GET /o/<slug>/admin/credentials` — ordinations and pastoral appointments for the presbytery
- Server actions on the same route for record ordination, change status, record appointment, end appointment

*Ships behind the `org_portal.credentials` flag, seeded off.*
