## The Eight Errors — Intended Behaviour and Idiomatic Fix

**#1–2, the two `set-state-in-effect` cases.** I read both components. Neither is subscribing to a browser API or an external store — both are the textbook "adjust state when a prop changes" pattern React's own docs (linked in the rule's own error text) address directly, and both should be fixed the same family way: **replace the effect with a `key`-forced remount**, not an `eslint-disable`.

- `branding-form.tsx:98-101` — the effect re-seeds `seedHex`/`typePairing`/`lightOnly` from `initialSeedHex`/`initialTypePairing`/`initialLightOnly` whenever those props change after a `revalidatePath()`-driven re-render (this is the deliberate fix for the platform `BrandForm`'s stale-state bug per the component's own header comment). Intended behavior to preserve: **a successful save must show its own persisted value without a full navigation.** The React-idiomatic replacement: since the component's own header already notes `ExistingTenantBrand` "carries no `updatedAt` to key a remount off," the fix is for the parent Server Component to pass a derived key (even a cheap one — e.g. a hash/join of the three initial values, or a real `updatedAt` if one can be added cheaply to the read) as `key={...}` on `<BrandingForm>`. A prop-driven remount re-runs the `useState` initializers with the fresh values and needs no effect at all. This is a one-line change at the *call site* (the page/layout that renders `BrandingForm`), which the implementer will need to locate — Phase 4 should confirm which file renders it.
- `portal-nav-links.tsx:86-89` — the effect closes the mobile-nav overlay on every route change. Same pattern, same fix family: split the `open`/`setOpen` state into an inner component keyed by `pathname` (`<PortalNavMenu key={pathname} entries={entries} />`), so navigating remounts it and `open` resets to its `useState(false)` default without a synchronous `setState` in an effect. Intended behavior to preserve: **the mobile menu must not stay open across a navigation.**

Both fixes are small, structural (an extra `key` prop / one extra inner component), not `useSyncExternalStore` — neither effect reads an external/browser API, so that hook doesn't apply here; I'd flag that alternative in the work-log as a red herring for this specific pair.

**#3–7, the five `react/no-children-prop` cases.** I read `children-roster-list.tsx`. This is **not** a real "children passed as a prop instead of nested" bug — the component's prop interface literally names a domain data prop `children: ChildRosterEntry[]` (a list of child-person roster rows), which collides with JSX's reserved `children` attribute name and trips the rule on every call site (`<ChildrenRosterList slug="..." children={[...]} />`), in the test file four times and in `page.tsx` once. Intended behavior to preserve: **the roster list receives an array of `ChildRosterEntry` and renders the empty state / rows exactly as today** — nothing about actual JSX nesting needs to change, because these were never React children. The idiomatic fix is a **rename**, not a JSX restructure: rename the prop (e.g. `childEntries` or `children` → `roster`) in `children-roster-list.tsx`'s destructured signature and its five call sites (4 in the `.test.tsx`, 1 in `page.tsx`). No behavior change; purely a naming fix that removes the collision with React's reserved name.

**#8, `statistics-grants.ts:362`.** I read `revokeStatisticsGrant()` and its call chain (`revokeStatisticsGrantAction` in `.../admin/reports/actions.ts` → `RevokeGrantButton` in `grants-table.tsx`, which passes `result.error` straight into `toast.error(...)`). `submittedAt` is `timestamp("submitted_at", { withTimezone: true })` — a real **instant**, not a bare calendar date, per `FormattedDate`'s own doc comment distinguishing the two. Two things matter here:

1. **`<FormattedDate>` genuinely cannot be used** — `statistics-grants.ts` is a plain server-side lib function returning a `string` (`message: `This grant was already used to file a return on ${...}``), not JSX; `<FormattedDate>` is a client component with its own `useEffect`/mount lifecycle and can't be embedded in a template literal.
2. **No lib-safe explicit-timezone helper exists yet.** I grepped the whole `src/` tree for `Intl.DateTimeFormat` and it returns zero hits outside this one call site — this is the only `toLocale*()` violation in the codebase, and there is no existing small utility to reuse. Phase 3/4 needs to *create* one: an explicit-timezone formatter (e.g. `Intl.DateTimeFormat("en-US", { timeZone: "UTC", dateStyle: "medium" }).format(date)`, or a tiny shared `formatDateUTC()` helper if other lib call sites are expected to need this later) rather than the bare `toLocaleDateString()`, which silently depends on the Node process's server locale/timezone — exactly the SSR mismatch the rule exists to prevent, just manifesting in a toast string instead of rendered markup. Intended behavior to preserve: **the revoke-grant error message states the date the return was filed** — since the value is an instant, a UTC-explicit rendering is an acceptable, deterministic choice for a one-line error toast (it will not vary by which server handled the request), even though it's not "the viewer's local day" the way `<FormattedDate>` would give a rendered page. Flagging this precision loss as a note, not a blocker — it's an error toast, not a report figure.

## CI Step Order

Read `.github/workflows/ci.yml` in full and confirmed step-level results directly from a live failed run (`gh run view 36190103693 --json jobs`): **Typecheck succeeds, Lint fails, and Build / Tripwire checks / Dependency audit / Unit tests are all reported `skipped`** — not "not run," GitHub Actions' own per-step status literally says `skipped`, on every push since 2026-08-26. `Lint` is a bare `run:` step with default `continue-on-error: false` in the single `ci` job, third in the sequence (Typecheck → Lint → Build → Tripwires → npm audit → Unit tests) — a failure there halts everything after it in that job.

**Recommendation: move Lint to run last in the job, after Unit tests**, not `continue-on-error: true` and not a separate job. Reasons:
- `continue-on-error: true` would make the job report green even with lint errors present, defeating the point of gating — the original ask is "lint failure no longer hides the others," not "lint stops failing the build at all."
- A separate job would run in parallel and give an independent status, but this repo's `ci` job doesn't use path filters or matrix — splitting adds a second `npm ci` (cache-shared, so cheap, but still a second `actions/setup-node`/`npm ci` cycle) for one extra `run:` line's worth of isolation. Not wrong, just more moving parts than the problem needs.
- Reordering within the existing job (Typecheck → Build → Tripwires → npm audit → Unit tests → **Lint last**) is the minimal change: every other check still reports its own true pass/fail even when lint is red, and the job's overall conclusion still correctly goes red on a lint failure. This is the same "cheap-first, but don't let a stylistic gate blind you to a substantive one" tradeoff — except here typecheck (Step 5) is already cheap and first, so moving lint to last doesn't sacrifice fail-fast on the expensive stuff; it just stops lint from being the single point that blinds four other checks.

   ```ts
    * Lib-safe, explicit-timezone date formatting for contexts <FormattedDate>
    * cannot reach — plain strings (error messages, audit descriptions, email
    * bodies) built outside JSX, where there is no mount lifecycle to swap an
    * SSR fallback for a client-local render. Always UTC, always deterministic
    * regardless of which server (or which developer's laptop) runs it — the
    * exact SSR-timezone-mismatch guarantee `no-restricted-syntax` bans
    * `toLocale*()` to protect, just enforced by construction instead of by
    * hydration. TRADEOFF, not a defect: the rendered date is the UTC calendar
    * day, which can read one day off from the viewer's own local day for an
    * instant near midnight UTC. Acceptable for a one-line error toast or log
    * line; NOT a substitute for <FormattedDate> in anything rendered to a
    * page, where the viewer's own local day is the correct answer.
    */
   export function formatDateUTC(date: Date): string {
     return new Intl.DateTimeFormat("en-US", {
       timeZone: "UTC",
       dateStyle: "medium",
     }).format(date);
   }
   ```

Phase 5 FAILed the original ruling for fix #1 on two counts, both re-read

Re-ruling below, per the three options QA named.

### Mechanism chosen: React's sanctioned adjust-state-during-render pattern

**Not** "key only the field subtree" and **not** "hoist the action result
above the key." Both of those keep a remount somewhere and only relocate the
risk — they would still require splitting `BrandingForm` into a
banner-holding wrapper plus a keyed field-subtree child (a real structural
change: the `<form action={formAction}>` element wraps the fields today, so
either the form tag itself has to live inside the remounted child while
`formAction`/`isPending`/`result` are threaded down as props, or the fields
move out of the form the banner sits beside), for no benefit over removing
the remount entirely — a `key` derived from brand data would still exist
somewhere, still one future refactor away from drifting back into wrapping
the wrong subtree.

**Chosen: no remount at all.** Track each of the three server-derived
fields' *previous* incoming value in its own small piece of state, and when
the incoming prop no longer matches what was last seen, correct the
corresponding field state **during render** (not inside an effect) — the
exact "Adjusting some state when a prop changes" pattern React's own docs
describe for this precise shape (a derived-from-props value that needs to
reset when the source changes, without losing sibling state). Calling
`setState` conditionally in the render body, not inside `useEffect`, is
allowed and does not trip `react-hooks/set-state-in-effect` — the rule
matches calls inside an effect hook, not calls in the component body; the
condition becomes false as soon as it fires, so there is no infinite loop
(React discards the in-progress render and re-renders once more immediately,
before committing — the documented, non-remounting shape). Net result: the
same `BrandingForm` instance survives every save, `result` never resets, the
banner persists through both the success and partial-save paths, and there
is no `key` anywhere in this fix for a future edit to accidentally widen the
remounted subtree around.

### Investigation

Read `@next/eslint-plugin-next`'s `no-html-link-for-pages` rule source
directly (`node_modules/@next/eslint-plugin-next/dist/rules/no-html-link-
for-pages.js`) rather than guessing from the message text. Its logic: it
looks for a `pages`/`src/pages` directory AND an `app`/`src/app` directory;
it only emits the "Pages directory cannot be found" `console.warn` (a
runtime notice, not a reported lint problem) and skips all checking when
**both** are absent. This repo has `src/app/`, so that early-return path
never fires — **this was not a config misfit**. The rule was doing exactly
what it does in every App Router project: building a regex of every real
route under `src/app/` and flagging any literal `<a href="...">` whose
target matches one of them.

Confirmed by counting unique warnings vs. total: 190 reported warnings
collapsed to **19 unique `file:line:col` locations** across 5 files — the
duplication is the rule matching a single literal href against every
dynamic-segment route file under `src/app/(org)/o/[slug]/**` that resolves
to a URL pattern the literal path satisfies (e.g. `/o/alder-creek` matches
the pattern generated by every file under `o/[slug]/`), so one real anchor
produces up to 10 duplicate reports. All 19 are the identical pattern:

```tsx
<a href="/o/alder-creek">Back to portal</a>
```

(or `/o/alder-creek/admin/officers` → "Back to officers",
`/o/alder-creek/admin/roles` → "Back to roles") — every one inside a
`describe("... — unsaved-changes guard (H3)")` block, standing in for a
real link elsewhere in the admin shell (`GlobalNav`/`PortalNavLinks`,
already `next/link`-based in production) so the test can assert
`useUnsavedChangesGuard`'s document-level click interception fires on it.
**Case: real internal anchors, not a config misfit.** None are external
links or carry a `download` attribute — the rule's own early-returns for
those cases (`target="_blank"`, an external `http(s)://` href, a
`download` attribute) don't apply to any of the 19.

## Findings

### Finding 1 — DEFECT: the keyed remount destroys the save-result banner that E-c1/E-c2 require to persist

`branding-form.tsx:135` holds the save outcome in `useActionState`, and `:176` renders it as the inline `role="status"` banner. The file's own comment at `:158` states the contract:

```
// Toast is a SUPPLEMENT here, not the record — the inline banner below is
// what E-c1/E-c2 require to persist ("never a toast that vanishes").
```

`useActionState` state is per-instance. `setOrgBrandAction` writes, then calls `revalidatePath('/o/${slug}/admin/branding')` (`actions.ts:171`); the page re-reads the brand, `updatedAt` has advanced, `brandKey` (`page.tsx:130`) changes, and React unmounts the instance holding `result` and mounts a fresh one with `result === null`. The green **"Brand saved."** banner is destroyed — and so is the amber **partial-save** banner (E-c2: colour/pairing committed, logo failed), because that path writes too and therefore also bumps `updated_at`. Only a *total* failure leaves the banner standing, because nothing was written.

This is a dilemma, not a maybe: if `revalidatePath` reaches the client with new props — the premise the entire staleness fix rests on — the remount fires and the banner goes. If it doesn't reach the client, the staleness fix doesn't work at all. No test distinguishes the two cases, and this is a **regression introduced by this pipeline**: before the change, the same component instance survived the revalidate (the deleted effect re-seeded the fields in place), so the banner persisted.

It is exactly the class of bug that needs a browser to see, and neither the implementer nor I have a browser tool — which is itself a reason to route this back rather than wave it through.

### Finding 2 — GAP: fix #1 has no regression coverage at all

`branding-form.test.tsx:267` and `:398` were correctly retitled and now pass differing `key`s, so they no longer assert the *opposite* of the fix — Phase 3's instruction was followed to the letter. But they have **no revert-detecting power**:

- The file imports only `./branding-form` (line 57). `key={brandKey}` lives in `./page.tsx`. Deleting it fails nothing in this file.
- `page.test.tsx` renders the real page but never inspects the key — `grep -rn "brandKey" src/` finds it only in `page.tsx` and in comments. Its new `updatedAt` fixture (`page.test.tsx:192`) is for realism only, as Phase 3 itself predicted.
- A keyed remount re-running `useState` initializers is React semantics, true of *any* component. Both specs would also pass with the deleted `useEffect` restored.

So the mechanism protecting a bug `docs/TODO.md` names as live is guarded by nothing. Net, this pipeline **reduced** regression coverage for that bug: the old specs at least exercised the in-place re-seed they were written for.

`branding-form.test.tsx:314` is now a tautology — it dirties an input and asserts the value it just set, with no re-render in between. Harmless, but it no longer earns its name.
