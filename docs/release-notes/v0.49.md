## 0.49.0 — 2026-10-28

### Enhancement: two-factor sign-in follows a person's role

**Value:** Until now every new account was asked to set up two-factor sign-in before it could do anything, so an ordinary member who signed in for the first time met a security step meant for the people who handle money and access. Now the people who hold those responsibilities are asked, and everyone else goes straight to their congregation.

#### What's New

**Two-factor sign-in now follows a person's role.** A new account is no longer asked to set up two-factor sign-in just for existing, so a member who signs in for the first time goes straight to their congregation. Church administrators and treasurers are still asked: so is anyone who works with giving, creates roles, gives roles to others, or manages a congregation's website addresses. A platform administrator is asked from the moment the role is given in the application. A congregation can still require it for everyone it has. An administrator can switch a person's own setting on or off, but switching it off does not excuse anyone whom a role or a congregation requires. The two-factor page in the admin area now lists everyone who is required and has not set it up, and says why. Accounts that already exist keep exactly the setting they had, and **[DEPLOY-DAY COUNT — orchestrator fills from R8 Query 1 `newly_required_not_enrolled` on production just before the apply. If 0: "on release day, no existing account was newly asked to set up two-factor because of this change." If not 0: say the number, e.g. "on release day, N existing accounts were newly asked to set up two-factor because of this change." Delete this bracket.]** Not every administrator is always asked: roles that cover none of the things above, such as roles for people or events, are not asked unless the congregation turns the requirement on. A platform role or platform-administrator flag set directly in the database, rather than through the application, does not turn the setting on, and nothing in the database prevents that; only review of the application's code does. Someone given a role while they are signed in is asked at their next sign-in. A brief database problem at sign-in can leave a person whose only reason is a role or a congregation without the prompt until their next check. Setting up two-factor on your own, when nothing requires it, does not start asking you for a code at sign-in.

- **The admin user page** shows the person's own setting ("Own setting: not required" when it is off) and says that a role or a congregation's policy may still require two-factor. The "2FA exempt" marker on the users list is gone.
- **Force-reset** now says what happens next: if something still requires two-factor of the person they are asked to set it up again at their next sign-in, and if nothing does they are not asked.
