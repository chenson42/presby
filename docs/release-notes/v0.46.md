## 0.46.2 — 2026-10-26

### Fix: two-factor setup shows the key that was saved

**Value:** When you set up two-factor sign-in for the first time, the key on
the page is now always the one that was saved, so a correct code from your
authenticator app is accepted.

#### What's New

- **Fixed an occasional problem when setting up two-factor sign-in. The setup
  page could show a key that was not the one that had been saved, so a correct
  code from your authenticator app was refused. The page now always shows the
  saved key.**

#### Things to know

- Reloading the setup page, or opening it in a second tab, shows the same key
  as before, so an authenticator entry you have already added keeps working.
- A code can still be refused for other reasons, such as a mistyped code, a
  phone clock that is off, or setup taking longer than its 10 minutes. Nothing
  else about the setup page changed.

**For the operator.** No migration and no new setting; nothing needs to be
applied before deploying. There is no what's-new post: nothing a member sees
changes except that the occasional refusal stops.

**Technical:** DECISION-290; finding F342 (`docs/schema-design-2.md` section
2af). `getOrCreatePendingEnrollment` in `src/lib/totp-pending.ts` is now one
conditional upsert (`on conflict (user_id) do update … where expires_at <=
now() returning`) with a read-back of the stored ciphertext on every return
path, bounded to three attempts and then a constant error. Its only caller is
`/account/2fa`. Tests: `src/lib/totp-pending.test.ts` (database-backed, red on
the old helper), `src/lib/totp-pending.exhaustion.test.ts` and
`e2e/totp-enrol-concurrency.spec.ts`.

## 0.46.1 — 2026-10-26

### Fix: your website no longer serves files it never published

**Value:** Your congregation's public website now hands out only the images
it actually uses, so a stored file that was never meant to be public cannot
be fetched by its web address.

#### What's New

- **Only published images are served.** A congregation's website now serves
  its page images, its logo, and the photos of people who are currently
  listed on a public staff, officer or committee list. Any other stored file
  now answers "not found", the same as a file that doesn't exist.
- **What this closes.** Before this change, a stored file belonging to a
  congregation (a support-ticket screenshot, a contribution statement, the
  website's own content file) could be fetched by anyone who already knew its
  exact, random web address while the website was live. At the time of this
  change, production held no ticket attachments, no contribution statements
  and no person photos, so none of those could have been fetched this way.
  The website's content file could have been.
- **Hidden photos stay hidden.** A person who has chosen to hide their photo
  in the directory no longer has it shown on public lists, even when they are
  listed. No person photos are stored in the platform today.
- **Photos on public lists are kept for about a day.** Browsers hold them for
  about a day instead of a year, so an un-listed person's photo stops showing
  sooner.
- **No action needed.** Nothing to re-publish, and the website looks the same.

#### Things to know

- A listed person's photo can still be fetched by its exact link while the
  staff or committee list is switched off on the website.
- An image removed from your website can still be fetched by its exact link
  until a follow-up change.
- Copies already saved by browsers, search engines or web archives cannot be
  recalled.
- The staff, officer and group "show on website" confirmation now says a
  photo appears only if one is on file and the person hasn't hidden it.

**For the operator.** This release has a migration, `0072`, and it must be applied to production **before** the code is merged: the new code calls a database function that does not exist until the migration runs. The steps, the checks to run afterwards and the rollback are in `docs/deployment.md`, "Public asset audience (0072)". It was rehearsed on a copy of production on 2026-10-26. Between applying it and merging, do not push to a congregation's site repository, upload a logo or attach a file to a ticket. Leave `GIVING_STATEMENTS_ENABLED` unset until the checks pass. There is no what's-new post: nothing a member sees changes.

**Technical:** DECISION-277; findings F289, F340 and F341 (`docs/schema-design-2.md` section 2ae); migration `0072_presby_blob_audience.sql`. `blob_assets.audience` (`public_site` or `private`, default `private`, immutable by trigger, image types only for `public_site`); `presby_public_site_asset()` is the only door and the asset route's only reader; `ticket_messages` and `giving_statements` pin `private` with a three-column composite foreign key; the dedup key is now `(organization_id, audience, content_hash)`; both public roster functions withhold the photo of a person with `hide_photo`. `getBlobStore()` calls take a required audience literal, pinned by `src/lib/storage/audience-callsites.test.ts`.

## 0.46.0 — 2026-10-26

### Feature: developer portal, first step

**Value:** The Developer page now has a proper home and a frame around it, and it asks for your two-step sign-in code like the rest of the platform pages. This is the first step only: who can open it has not changed.

#### What's New

- **A proper home.** The Developer page now has a header with your account menu and a way back to PresbyPortal, a menu that works on a phone, and a start page with two sections.
- **Data model.** The old list of tables is now called Data model. Every existing link to a table or a diagram still works.
- **Documentation.** A new Documentation page lists the guides we plan to bring into the portal and says where each one lives today. Nothing there is built yet.

#### What has not changed, and what comes later

- **Access is the same as before.** Only a platform administrator whose account was flagged by hand can open the Developer pages. Nobody else can yet, and there is no screen for granting it.
- **Later steps.** A `developer` role that can be given to a person in any organization, and an API page (an inventory of the platform's internal endpoints and scheduled jobs, which says plainly that PresbyPortal has no public API), come in later releases. This release is not the finished developer portal.

#### Fixes

The Developer pages did not ask for your two-step sign-in code when your account requires one. They do now. 58 of the 105 tables were filed under "platform" with no diagram; every table is now filed under its real heading, and a test keeps it that way. The list of rules the system relies on was missing six of the project's principles and still carried a note that is no longer true. It now includes all six, and a test fails if one of the project's listed principles has neither an entry nor a recorded reason for being left out. Two working practices, No Real Data and Verify in a Browser, are deliberately left off, and the page says so. The wording of each entry is written by hand and is not checked. If the Developer page cannot check your access, for example while the database is unreachable, it now says so and offers Try again, instead of showing a technical error page or sending you somewhere else.

**For the operator.** No migration and no new setting; nothing needs to be applied before deploying. There is no what's-new post, because only a hand-flagged platform administrator can see these pages. Reading the Developer pages is not recorded in the audit log.

**Technical:** DECISION-258 and DECISION-261; findings F283, F284, F285 and F288 (`docs/schema-design-2.md` section 2ad). `src/proxy.ts` challenges `/developer` by path segment (so `/developerx` is not challenged) and the page gate repeats the check; `/developer/schema.json` answers JSON `401`, `403` and `503` itself. The admin console's header and navigation moved to `src/components/shared/console-*` and are used by both consoles. New: `src/lib/developer-portal/` (navigation, labels and the documentation rows as plain data, and the pure access decision), `src/lib/dev-docs.test.ts` (every table classified, every Key Invariants heading listed or excused) and `shell-boundaries.test.ts`. No `loading.tsx` exists under `(admin)/developer`, for the same reason as `/admin` (DECISION-251).
