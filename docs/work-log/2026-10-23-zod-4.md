### Ruling 1: the upgrade path

**Bump straight to `zod@^4.6.7` and use the v4 API everywhere. The `zod/v3` compatibility subpath is rejected.**

- zod 4.6.7 still ships `zod/v3`, but I checked it and it does not carry the fix:
  - In the 4.6.7 tarball, `src/v3` is byte-identical to 4.6.5.
  - Its `ZodArray._parse` still adds a `too_big` issue and then parses every element anyway.
  - The 4.6.7 fix (`capSize()` / `util.sizeCaps()`) exists only in `src/v4/core/schemas.ts` and `compile.ts`.
  - Upstream issue colinhacks/zod#6653, which reports the v3 behaviour, is open. The maintainer has said v3 is no longer published and that he doesn't consider this a vulnerability.
- `npm audit` matches on the installed package version. Code using `zod/v3` would therefore pass the audit gate while still exposed. The subpath would hide the advisory rather than fix it, so it is ruled out even as an interim step.
- The fix has a limit Phase 3 must design around. 4.6.7 only stops early on **size checks that come before every other check** (`_length`, `_size` or `_equals` checks at the front of the chain), and arrays with no bound are not covered. The one server-side array is `src/app/(admin)/admin/organizations/[id]/actions.ts:1038`: `z.array(z.string().regex(UUID_RE)).min(1).max(20)`. It is the exact shape from the advisory, and it is covered because both `min` and `max` are leading size checks. **Rule: on any collection schema, size checks come first, before any `.refine()`.** A refine placed ahead of `.max()` switches the early stop off.

### Ruling 3: user-visible error messages

zod messages reach the UI by three routes:
- RHF `formState.errors.*.message`.
- The giving `invalidInput()` → `zodFieldErrors()` path (`src/lib/giving/field-errors.ts:13`), which also runs client-side at `offline-gift-form.tsx:79`.
- `issues[0]?.message` at `filings/actions.ts:121` and `designation-holder-copy.ts:64`.

Almost every check users can actually trigger already has its own message. **The one default a user can reach is `src/app/(org)/o/[slug]/admin/staff/position-schema.ts:40-41`.** It is `.max(200)` with no message, shown at `add-staff-position-form.tsx:301-303` and `:320-322`; the inputs have no `maxLength`. On v3 it reads "String must contain at most 200 character(s)"; on v4 it would read "Too big: expected string to have <=200 characters".

The remaining defaults can only be reached by tampering with the request:
- UUID fields with no message, in the giving actions and filings.
- `z.enum` with no message. Every form defaults the field to a valid value: `add-group-member-form.tsx:33`, `add-officer-term-form.tsx:33`, `record-appointment-form.tsx:40`, `statistics-submit-form.tsx:133`.

**How to keep the copy stable:**
- **Give each user-reachable check an explicit message, pinned to the string it shows today.** "No user-visible change" is the exit criterion; improving that copy is an optional follow-up.
- **No global error map** (`z.config({ customError })`). It is a side effect at module load that would have to run before the first parse in both the server and client bundles, and it fails silently if any bundle misses it.
- Wording changes on tamper-only paths are accepted. Phase 3 lists them by file:line in Edge Cases.

# Phase 3 — Technical Design (tech-lead)

## Summary

Upgrade `zod` from 3.25.76 to `^4.6.7` on the classic API, convert the call sites that v4 breaks or changes silently, and prove "no user-visible change" with characterization tests written first, on zod 3. The upgrade closes GHSA-mrhx-c7xc-m3w5 (the memory-exhaustion advisory) and lets the temporary CI exception come out. The work is mechanical but wide: 50 files import zod or the resolver, 9 of them carry the `.uuid()` calls, and the three silent risks from Phase 2 (strict UUIDs, removed error parameters, default message wording) each get a named conversion and a named test.

Phase 3 verified its own claims against zod 4.6.7 and zod 3.25.76 side by side in a scratch directory outside the repo (46 representative inputs through the real giving and event schemas, plus the email, NaN/undefined, array and `z.guid` cases). Results are quoted where they matter. The one place the verification changed Phase 2's shape is `connection-input.ts` (see "Phase 3 refinements" and proposed F229).

**Phase 3 refinements to the Phase 2 rulings (the architect should see these; none reverses a ruling).**

1. **`connection-input.ts` does not use `.int()`.** A plain port with `error:` and `.int()` is not first-message-identical to v3: in v4, `.int()` also fails integers beyond ±2^53, so `1e20` in a rate field would say "must be a whole number." where v3 said "must be between 0 and 1000." (the first message is the one the user sees). Using `.refine((n) => Number.isInteger(n), { message })` in `.int()`'s place, in the same position in the chain, matched v3's first message on every input tried (25 inputs including NaN, ±Infinity, 1e20, 2^53, 2^60, MAX_VALUE). The architect expected "no change" here; this is proposed finding F229.
2. **`revokeHolderFieldsSchema` moves into `src/lib/onboarding/designation-holder-copy.ts`.** It is a non-exported `const` in a `"use server"` file, and a `"use server"` file can export only async functions, so the advisory regression test (Ruling 5.4) cannot reach it where it is. `designation-holder-copy.ts` is the existing pure module that already holds `reasonSchema` and is shared by the action and the library. This is an edit in place across two existing files, not a new module, but it is a structural move Phase 2 did not name. It lands in commit 0, before any behavior changes.
3. **One-commit-one-prefix splits Ruling 5's "commit 1".** Commit 0 (`refactor`: the schema move and one `export` keyword) precedes commit 1 (`test`) and commit 2 (`fix(deps)`). Tests still land before the bump, on zod 3, and commit 2 leaves them unedited.
4. **Characterization tests pin message text only where a user can reach it.** Tamper-only paths keep their default wording change (Ruling 3, accepted); their tests assert failure and path, not the message. If they pinned wording, commit 2 would have to edit them, which the commit order forbids.

**DECISION-224 — zod 4 conversion rules: parity at the first message, ids through `z.guid`, tests that pin only what a user can see.**
- Decision: (1) Id inputs are `z.guid(message?)`, the top-level form, keeping any message; (2) a bounded whole-number field is `z.number({ error })` plus `.refine(Number.isInteger)`, not `.int()`, because v4's `.int()` also rejects integers beyond ±2^53 and changes the first message; the `error` function maps `undefined` to the "is required" copy and every other type failure to the "whole number" copy; (3) a trimmed, lower-cased email is `z.string().trim().toLowerCase().pipe(z.email().max(320))`; (4) `code: "custom"` replaces `z.ZodIssueCode.custom`; (5) a check a user can reach through a form carries an explicit message pinned to today's string, and a tamper-only default may change wording; (6) the characterization tests assert exact text only for the former and path-and-failure for the latter, and stay in the tree as permanent regression coverage; (7) a schema private to a `"use server"` file that a test must reach moves to the existing pure module that already shares its sibling schema (`revokeHolderFieldsSchema` to `designation-holder-copy.ts`).
- Why: v4 changes defaults without a compile error; the first message is the one every route shows; tests that pinned tamper-only wording would force edits in the same commit as the bump and stop proving "unchanged".
