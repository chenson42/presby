## 0.10.0 — 2026-08-19

### Feature: The Post-Login Router (P0 of the backbone program)

**Background:** sign-in landed everyone on `/home` regardless of who they were, and there was no concept of *which organization you are in* — the org switcher's data source had been built months ago and never wired to anything. This is the first pipeline of the backbone program, designed across a full agent-run pipeline (analyst Phase 1, architect Phase 2 plus a revision after the operator played the spec back, tech-lead Phase 3) and recorded in `docs/work-log/2026-08-18-backbone-and-org-sites.md` with ten decisions, 034–045.

**What changed for a person signing in:**

- **`/launch` is the single post-authentication target.** It shows nothing on the happy path — it computes a destination from a nine-row matrix and forwards. One congregation goes straight in; several get the chooser; a platform admin with none goes to `/admin`; someone connected to nothing gets a page that says so and offers two doors.
- **`/orgs` is the chooser and never auto-forwards.** That is deliberate: if it forwarded a one-org user it would also forward a zero-org platform admin straight past the Developer card they were meant to reach.
- **`/` never redirects a signed-in user.** It stays the anonymous front page, because a signed-in person is entitled to read it, and because a custom domain will make the meaning of `/` host-dependent later.
- **Organization URLs are `/o/<slug>`, and the slug is now immutable** — renaming a congregation changes its name, never its address. Enforced by a DNS-label CHECK constraint, because the same token becomes a subdomain when custom domains land.
- **A humane, named access-denied page** replaces an anonymous 404 for a congregation you can see but cannot enter — while staying **byte-identical** across managed, invited, and unmanaged organizations. PC(USA) publishes which congregations exist; it does not publish which ones bought this software.
- **The header is two controls now**, on Google's model: an avatar for identity (account, platform surfaces when entitled, sign out) and an organization switcher for context. A pastor changes context many times a session and identity never.

### The tenant gate had never worked

`withOrgContext()` — the function that enforces tenant isolation — rejected every legitimate member. The membership check runs before setting the org GUC, which is correct, but `memberships` is `FORCE ROW LEVEL SECURITY` keyed on that same GUC, so it read zero rows every time. Latent since the resolver landed because nothing had ever called it; the first page that did, broke.

This is finding **F26** in its purest form and the third occurrence of that pattern in this schema. Fixed with a narrow `SECURITY DEFINER` probe rather than by setting the GUC first, which would have inverted the one ordering CLAUDE.md names as an invariant.

### Light mode had never worked either

`globals.css` nested `@theme` inside `@media (prefers-color-scheme: dark)`, and Tailwind v4 hoists `@theme` out of media queries — so the dark values applied unconditionally. Proven by rendering `/` and `/signin` in both schemes and getting byte-identical PNGs. **Every light-preferring visitor had been served the dark palette on every page** since the tokens were written.

Fixed, with a regression spec that fails on the old file and passes on the new. Dark renders are byte-identical before and after, so nothing changed for anyone who was already seeing what they expected.

### The design system, finally taken delivery of

`class-variance-authority`, `clsx`, `tailwind-merge` and `@radix-ui/react-slot` were all already installed — but `src/lib/utils.ts` and `components.json` had never been created. Now added, with exactly four generated primitives (`button`, `card`, `badge`, `dropdown-menu`) and the token set expanded while keeping every existing token name working. **Zero new runtime dependencies**, twice verified by md5 against the lockfile, because the shadcn registry now tries to install the entire Radix umbrella on every `add`.

`--primary` moved from blue-500 to blue-600: white on blue-500 is 3.7:1 and fails AA. The first visual decision in this codebase made on a measurement rather than on taste.

### Also

- **A membership can no longer end while an officer term is open at that organization.** Two triggers, failing loudly and naming the term rather than silently ending a minuted act. A seated officer was previously able to lose their access on a date with no corresponding write.
- **`presby_available_organizations` became `presby_user_organizations`**, returning platform status and end date and filtering neither — policy moved into TypeScript where it is testable and visible in a diff.
- **Dates stopped shifting a day.** A `date` column arrives from the driver as midnight local, which renders as the *previous day* west of the deployment — on the one screen whose job is to state when someone's access ended. Fixed in SQL, then fixed again a layer up where `<FormattedDate>` reconstructed the same bug.
- **`loading.tsx` silently downgrades a redirect to a 200** and a `notFound()` to a 200. Removed from those segments, with the rule written into CLAUDE.md.
- **Test fixtures got memorable addresses** (`admin@presby.invalid`, `org1@presby.invalid`, …) and `docs/testing.md` explains how to sign in and what to look for.

### Verified

505 → 559 unit tests · 63 → 84 e2e against a real dev server · 39 → 59 isolation assertions as `presby_app` · typecheck, lint, build, and both tripwires green. The access-denied byte-identity property was checked programmatically rather than by eye.

**Phases 5 and 6 are deferred on this pipeline** by operator decision (DECISION-045) — the foundation will be verified as a whole once it is coherent enough to judge. The outstanding items are listed under **Verification debt** in `docs/TODO.md`.
