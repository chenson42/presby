## 0.35.0 — 2026-10-20

### Feature: Church-domain websites (the mechanism, not yet the cutover)

**Value:** A congregation's public website lives at a PresbyPortal address today. Most congregations already have, and want to keep, their own web address. This release builds the part that lets a congregation, presbytery or synod prove it controls a domain name and have its public site shown there, with the platform's own sign-in and admin pages kept off that domain entirely. **It is not switched on for anyone yet.** The connection to the hosting service that would actually put a domain online is deliberately not configured in production, so today a claim can be made and proven but cannot go live. This release is the first of two parts; church email on the church's own domain is the second and is **not** part of it.

#### What's New

**A Domains page for the congregation.** Under the congregation's admin area, a person who holds the new domain permission can add a domain and is given a plain checklist of the exact records to add at whoever runs the congregation's domain name (a registrar, a web company, a volunteer). Each record shows whether it is found, wrong or missing, with copy buttons, a "copy everything" button, and a prepared email the congregation can send to whoever manages its DNS. The page has a **Check now** button, a short explanation when something looks wrong (for example a record set up in a way that blocks the connection), a way to choose the primary address, a checklist for leaving the platform, and a recent-activity list of what happened to the congregation's domains. It works on a phone.

**How a domain is proven.** The congregation first publishes a one-line verification record. Until the platform sees it, nothing is connected and the hosting service is never contacted. The proof covers the name typed in and its `www` form together. A congregation can hold up to three web domains. Two congregations cannot hold the same name: whoever proves it first holds it, and a later claimant is told only that the name is already connected, never by whom. An unproven claim expires after seven days.

**What visitors see.** Once a domain is connected and confirmed reachable, the congregation's public site (home page, pages, images, sitemap, the give page and the contact form) is served on it. The congregation's old PresbyPortal site address then forwards to the primary domain. Any domain that is not connected, not yet proven, paused or released shows the same plain "page not found" as a name nobody ever claimed, so a visitor cannot tell which names belong to a congregation. A congregation's domain carries none of the platform: no sign-in, no admin, no member portal, and the platform sets no cookies there.

**Keeping the proof alive.** Every few minutes the platform re-checks that the verification record is still published. If it disappears for long enough, the domain is marked lapsed and the congregation is told. A lapsed or removed domain stays attached but dark for 30 days before it is released, so a DNS slip or a change of mind can be fixed without starting over.

**For the platform operator.** A Domain features card on each organization (turns the whole feature on for that organization; nothing is on by default), a Domains section on the organization page, and a list of every domain across organizations at **Admin > Organizations > Domains**. An operator can record a web claim on a congregation's behalf (the DNS proof is still required), check a domain, pause or dispute it, and release it with a recorded reason. An operator cannot turn on church email and cannot set a congregation's office email.

**Emails.** Starting a claim, changing the primary address and removing a domain each send a notice to every person who can manage domains and to the platform operators.

#### What changes for people using the platform today

- The platform's sign-in, home, admin and member pages are unchanged and still work on `presbyportal.org`, `www.presbyportal.org` and the temporary hosting address.
- The old `/orgs` address still forwards to `/home`, now only on the platform's own addresses.
- A site's contact form no longer carries the congregation's short name in the page; the platform works it out on its own side. The give page's "return" step shows "page not found" instead of a generic panel when its address does not match a real site.
- Any domain already attached to the platform's hosting project, other than the platform's own, will now show "page not found" until it is claimed and proven. The operator should list the project's domains before this is deployed.

#### What this release does not do, and what you should know before using it

- **This is not the cutover.** No congregation's real domain is connected by this release. The first customer's go-live and any cutover of an existing website still need three things that do not exist yet: the hosting connection (a project-limited access token and settings in production), a trial run on a spare domain the operator owns, and a redirect map from the old website's page addresses so search results and bookmarks keep working. Until the trial run, **nothing here has been verified against the real hosting provider, the real Cloudflare, or real DNS answers**, and no real domain should be pointed at the platform yet, because a name that is not attached would show the hosting service's own error page.
- **Until the hosting connection exists, a claim can be proven but not connected.** The page says "Connecting is temporarily unavailable. Your DNS changes are safe to make." That is the expected end of the road for now. The operator will receive a daily "failing" alert for any such claim after the first day, which is noise while the connection is deliberately absent; removing it is on the follow-up list. A claim that an operator force-releases in this state waits for a connection that does not exist and keeps the name held; that is also on the follow-up list.
- **Church email is not in this release.** The "church mail domain" switch exists on an organization but does nothing, and no church email is sent from a church domain.
- **A removed domain can leave a loose end.** The 30-day dark period reduces the chance that someone else claims an old DNS record, but it cannot remove it. A congregation that leaves should also delete the records at its registrar.
- **A lapsed primary address darkens the others.** If a congregation's primary domain lapses, its other connected domains go dark too, until the congregation chooses "make primary" on one that still works. This is deliberate (the platform will not silently re-point visitors during a DNS wobble), and the page shows a prompt.
- **A gift in progress can lose its way.** A donor who is partway through paying when the congregation's domain lapses is returned to a "page not found" page. The gift itself is handled by the payment service as usual.
- **A congregation's site shows the platform's browser-tab icon**, not its own, on its own domain.
- **Diagnosis is partial.** The page can explain many mistakes (a missing record, a record pointing to the wrong place, extra IPv6 or CAA records, a Cloudflare proxy in the way, a domain-security setting that blocks the lookup), but its recognition of some of them is incomplete, the list of Cloudflare addresses and the wording of the hosting service's error messages were written by hand and have not been checked against the real services, and one kind of domain-security problem is not detected at all.
- **The recent-activity list shows only the congregation's own domains, enforced by the database.** The wording of each line is still written by the application. That limit is small and noted.
- **One internal routing detail is unconfirmed.** The platform adds an internal routing header that echoes only the visitor's own address and path; whether the hosting service passes it along is unknown until the trial run. It reveals nothing about any other site.
- **No one holds the new permission yet in production.** Existing organizations have no founding administrator, so the new domain permission is held by no one until the operator designates one for an organization. The operator's on-behalf claim covers that gap.

#### Permissions

| Permission | Required for |
|------------|--------------|
| `domains.manage` (tier 1, delivered by the founding-administrator bundle, not requiring a second sign-in step of its own) | starting, checking, re-connecting and removing a congregation's domains, choosing the primary address |
| `org_portal.domains` (a per-organization switch only a platform operator can flip, not a permission) | the Domains page and everything behind it for that organization |
| `ADMIN_ORGANIZATIONS` (platform) | the Domain features card, the organization Domains section, the cross-organization list, on-behalf claim, pause or dispute, release |

#### New Routes

- `GET /o/<slug>/admin/domains` — a congregation's Domains page
- `GET /admin/organizations/domains` — the operator's list of every domain
- `GET /api/cron/domains` — the five-minute background check (proof, connection, reachability, lapse)
- Any host that is not one of the platform's own is routed to that congregation's public site (or to "page not found") instead of the platform
