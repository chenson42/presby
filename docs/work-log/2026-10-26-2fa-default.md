# Phase 1 — Functional Refinement (analyst) — F343, bug-fix variant (brief)

## VERDICT

**READY WITH NOTES.** The default flip is correct and small, but it exposes two coverage gaps that the "role-based only" ruling assumes are not there. Phase 3 must resolve both. One question goes to the operator (see Open Questions).

## How the requirement is computed today

- **`computeEffectiveTwoFactor(raw, userId)`** (`src/lib/auth/local-login.ts`) works as follows.
  - It returns `column OR presby_two_factor_required(user)`, then ANDs the `auth.require_2fa` flag.
  - It runs in the jwt callback on every authenticated request (`src/auth.ts:320`), so it is recomputed live.
  - If the flag read fails, it keeps the resolved requirement.
- **`organizationRequiresTwoFactor()`** returns false on any DB error. Previously the column short-circuited this for every default-true account. After the flip it is the sole source for role holders. See Gaps, item 4.
- **`presby_two_factor_required()`** (`drizzle/0055:2682`) has two arms.
  - Arm A is a congregation's `organization_settings.require_two_factor`.
  - Arm B is any `permissions.requires_two_factor` key held directly, through a group, a commission or a delegation, at any active membership.
- **Only three keys carry `requires_two_factor`:** `giving.view`, `giving.record` and `giving.manage`. `0055:104-112` says extending it to tier-3 keys is "a tracked follow-up (S2)".
- **The founding-administrator bundle carries none.** Its keys are `people.manage`, `roles.manage`, `role_grants.manage`, `groups.manage`, `officers.manage`, `org_features.manage`, `tickets.file`, `staff.manage`, `domains.manage`, plus `congregation_oversight.manage` for a presbytery (`0059:534`). None is flagged.
- **The treasurer bundle carries the giving keys,** so a treasurer stays required.
- **No tier-2 or tier-3 key outside giving is flagged.**
- **`/admin/2fa` and the dashboard card** use `STRANDED_WHERE` in `src/lib/admin/two-factor-stranded.ts`. That predicate is the column OR arm A only. It has no arm B. This is the second gap.
- **The per-person toggle** is `setTwoFactorRequired` on `/admin/users/[id]`, shown in `two-factor-card.tsx`. It writes only the column.
- **The proxy** gates `/admin`, `/developer` and `/o/*` on the cookie claim `twoFactorRequired && !twoFactorVerified` (`src/proxy.ts:158`). `/admin/layout.tsx:40` and the invitation accept action (`(invite)/actions.ts:225`) re-check on Node.

## Gaps the request didn't address

1. **Platform admins lose 2FA (highest severity).**
   - A platform admin holds no tenant membership, so arms A and B never apply to them.
   - Today their only protection is the column. It is true by default for each of these paths:
     - the `INITIAL_ADMIN_EMAILS` first sign-in, where Google creates the row and `ensureDefaultRole` (`src/auth.ts:65`) grants `ADMIN_ROLE`;
     - `assignRoleAction` granting the admin role (`src/app/(admin)/admin/users/actions.ts`);
     - a hand-set `is_platform_admin`.
   - After the flip, every newly created admin reaches `/admin` and `/developer` with no challenge, and nothing flags it.
   - Production has 2 required users, probably the existing admins. They stay required, and this is a go-forward defect.
   - This is "role-based" in the operator's own sense, because it is a platform role. The fix must make platform roles require 2FA. Two shapes for Phase 3 to choose between:
     - **(a) Derive it:** add a platform-role term to `computeEffectiveTwoFactor`, meaning `ADMIN_ROLE`, `FEATURES.ADMIN_DASHBOARD`, or live `users.is_platform_admin`. This is robust to every grant path, but the per-person toggle cannot turn it off. Say so in copy.
     - **(b) Write it:** set the column true at the grant points, audited. This is simpler and the toggle still works, but a hand-set `is_platform_admin` is missed.
   - I lean to (a), because the requirement then cannot drift from the role. The derived term must also be added to `STRANDED_WHERE` (see item 2).
   - This also needs a test that fails if the platform-role term is removed.

2. **`/admin/2fa` and the dashboard card under-count after the flip.**
   - `STRANDED_WHERE` ignores arm B and any platform-role term, so a treasurer or a new admin who is required but not enrolled will not appear.
   - It was mostly masked by the column. After the flip it hides real accounts.
   - The "Required by" label is `CASE WHEN column THEN 'this user' ELSE 'congregation'`. It will mislabel role-required people as "congregation".
   - Fix: make the predicate agree with the sign-in computation, for example by calling `presby_two_factor_required(u.id)` plus the platform-role term.
   - Add a source value such as "their role" and add an agreement test. This is the same agreement discipline as `src/lib/giving/two-factor-agreement.test.ts`.
   - The module is the recorded exception (DECISION-252, F276), so changing its predicate must stay inside `boundaries.test.ts`.

3. **Copy that becomes false.**
   - `/admin/2fa/page.tsx:86`: "Two-factor is opt-in per congregation. A member is required if their own record requires it or any congregation they belong to does." This was already incomplete, because it omits the giving keys. After the flip it is wrong for role holders and platform admins. It needs a rewrite naming role, congregation and per-person record.
   - `docs/testing.md:62-63` and the e2e comment `invitation-new-account.spec.ts:129`.
   - Check `docs/deployment.md:476`, which already says holding any giving key forces 2FA. It is true and should stay true.
   - On `/admin/users/[id]`, the card badge "2FA not required" (amber) is driven only by the column. A person required by role or congregation would read "not required" while the proxy challenges them. Show the effective state, or say "Not required by their own record".
   - The toast "2FA requirement disabled" is true only for the column. A role-required person is not released by it.
   - `/admin/users/page.tsx:138` flags `!twoFactorRequired` per row. After the flip it will mark nearly every account, so it becomes noise. Re-think or drop that marker.
   - No member-facing "everyone must set up 2FA" copy turned up in `(account)`, `(auth)` or `(invite)`.

4. **Sole-source DB-blip behaviour (document as an accepted residual).**
   - `organizationRequiresTwoFactor()` fails to false, per DECISION-026's rule against newly imposing a challenge on someone who never enrolled.
   - Before, a default-true treasurer was immune to a blip in that one call. Now a blip during that call can leave a role holder unchallenged for that request.
   - The jwt callback recomputes on the next request, and the giving pages re-check from a fresh `auth()`, so exposure is transient and self-healing.
   - It should be written into DECISION-291 and not silently inherited.
   - Do not change the failure posture in this pipeline.

5. **Founding administrator and tenant-admin keys are not 2FA-required (operator question below).**
   - After the flip, a newly invited founding administrator who holds `roles.manage` and `role_grants.manage` can grant roles, and has `domains.manage`.
   - That person is not required to use 2FA unless a congregation sets the policy. Production currently has 0 organizations that require it.
   - The ruling "the permission rules still force it where needed" is only true for the three giving keys today.
   - This is not a regression in code. It is a regression in practice: invited founding administrators were required and now will not be.
   - It is not in scope to extend `requires_two_factor` without the operator's say-so, because it changes who is challenged.

6. **Mid-session role changes.**
   - Grant: the requirement appears at the next jwt callback, which runs on every authenticated Node request. The proxy reads the cookie claim, which refreshes only when a server action or route handler re-signs it.
   - The invitation accept re-signs the cookie (`(invite)/actions.ts:243`). Other grant paths, such as an administrator granting a giving key to an existing member, leave the proxy claim stale until the member's next sign-in or action.
   - Giving pages and actions already re-check Node-side, so tier-2 data is protected. This was true before the flip and is now reachable for many more accounts.
   - State it as an accepted residual and add one test that a grant followed by a fresh `auth()` reads required.
   - Revoke: the requirement drops at the next computation. A revoked person who is enrolled keeps their enrolment, and nothing is forced.
   - Voluntary enrolment under the new default: a user who enrols at `/account/2fa` while the column is false is never challenged, because the challenge fires on the claim, not on enrolment. That is the same as any existing column-false account, so say so in copy and do not "fix" it here.

7. **Session projection default `twoFactorRequired ?? true`** (`src/lib/auth/session-projection.ts`).
   - It applies only when the token carries no claim. The jwt callback always writes a boolean, so the column default does not feed it.
   - It does not matter for this fix. Keep it unchanged; it is the safe direction.

- **Pass 4, edge cases.**
  - 2FA gate: mid-enrolment behaviour is unchanged.
  - Audit: none for the default itself. If shape (b) of Gap 1 is chosen, writing the column on a role grant must audit.

- **Pass 5, adversarial.**
  - Self-targeting: a platform admin using the per-person toggle on themselves to switch off their own 2FA. This already exists and is audited. With shape (a) it no longer works for platform roles, which is an improvement.
  - Escalation chain: `role_grants.manage` lets a founding administrator grant themselves a giving key. That makes them required at their next computation. It never removes a requirement, so there is no bypass.
  - Open registration: any Google-verified address creates a row with no role. After the flip it is not required. It reaches no 2FA-gated surface, so there is no loss.
  - No user-controlled redirect or input is touched.

**R2. Where the platform-role write lives, and how it is written**

### Notes (Phase 3 must honor)

**Proposed DECISION-291 text:**

> **DECISION-291 — Two-factor is role-based: `users.two_factor_required` defaults to false; the platform-admin grant points set it true (audited, still switchable); `roles.manage`, `role_grants.manage` and `domains.manage` carry `permissions.requires_two_factor`.**
>
> **Rule.** Migration 0080 changes the column default to false and issues no `UPDATE users`; existing accounts keep their value. A new account is required only by:
> (a) its own column;
> (b) a congregation's `require_two_factor` (arm A);
> (c) holding any key flagged `requires_two_factor` (arm B), now six keys: the three giving keys plus `roles.manage`, `role_grants.manage` and `domains.manage`.
>
> **Platform admins.** When a person gains `ADMIN_ROLE`, or any role bound to `admin.dashboard`, through `ensureDefaultRole` (`INITIAL_ADMIN_EMAILS`) or `assignRoleAction`, one helper in `src/lib/auth/` sets the column true in the grant's own transaction. It writes `user.2fa_required.changed` with `cause: platform_role_granted` only when the value changed. Removing the role does not clear it, and the per-person switch can still turn it off (operator ruling 2026-10-26). There is no derived platform-role term in `computeEffectiveTwoFactor`. Any future writer of `is_platform_admin` or of `user_roles` for a platform role must call the same helper.
>
> **Commission and delegation.** Flagging the administration keys needs no DECISION-175-style refusal trigger. That guard exists for giving privacy; a 2FA flag only adds a challenge. Arm B's commission and delegation arms already require 2FA at every org where `withOrgContext()` lets the key be used. This supersedes the 2026-10-19 T7 rationale and closes TODO S3.
>
> **`/admin/2fa`.** The stranded predicate calls `presby_two_factor_required(u.id)`, so the list and the dashboard card agree with sign-in by construction, and the platform-tier exception narrows to a per-account boolean.
>
> **Accepted residuals (`paper`):**
> 1. **SQL-set platform rights.** `users.is_platform_admin`, `user_roles` or `role_features` set by SQL or the seed bypass the helper, and the account is not required. No application writer of `is_platform_admin` or `role_features` exists today.
> 2. **Database blip.** For an account whose only source is a role or a congregation, a database error in `organizationRequiresTwoFactor()` yields "not required" for that computation (DECISION-026). If the blip coincides with a cookie re-sign, the proxy's claim stays false until the next Node-side re-sign or sign-in, not merely for one request. Node-side re-checks (`/admin` layout, giving pages, invitation accept) recompute on every request. Before this decision the column masked this for every default-true account.
> 3. **Mid-session grants.** A key granted to someone else mid-session reaches their proxy claim only at their next re-sign or sign-in. Node-side re-checks cover tier-2 data.
> 4. **Per-request cost.** New accounts no longer short-circuit on the column, so each of their authenticated requests pays the definer call (2.5 to 3.4 ms). `/admin/2fa` costs about 3 ms per active unenrolled account; revisit at about 1,000 accounts.
> 5. **Voluntary enrolment.** Enrolling while not required brings no challenge, the same as for any column-false account today.
>
> **Production impact.** Existing holders of the three keys become required at their next computation. The count was taken read-only before deploy and is stated in the release note.
>

with k(key) as (values ('roles.manage'),('role_grants.manage'),('domains.manage')),
me as (select p.user_id, p.id as person_id, m.organization_id as org_id

    join role_grants rg on rg.organization_id = me.org_id and rg.person_id = me.person_id

  union all
  select me.user_id, 'group' from me
    join role_grants rg on rg.organization_id = me.org_id and rg.group_id is not null
     and rg.starts_on <= current_date and (rg.ends_on is null or rg.ends_on > current_date)

    join app_roles r on r.id = rg.role_id

  union all

    join group_memberships gm on gm.person_id = me.person_id
     and gm.starts_on <= current_date and (gm.ends_on is null or gm.ends_on > current_date)

    join app_role_permissions rp on rp.role_id = r.id join k on k.key = rp.permission_key

  select me.user_id, 'delegation' from me

     and od.starts_on <= current_date and (od.ends_on is null or od.ends_on > current_date)

select count(distinct u.id) as active_holders,
