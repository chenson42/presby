One **new MEDIUM** finding surfaced while tracing the M2 fix end-to-end: `/admin/2fa` (`src/app/(admin)/admin/2fa/actions.ts`) is a second, live, actively-linked TOTP-management surface parallel to `/account/2fa` (both are reachable from `admin/layout.tsx`'s own nav — this is intentional "manage your own 2FA from the admin shell" UX, not dead code). Its four server actions check only `session?.user`, never `hasFeature(..., FEATURES.ADMIN_DASHBOARD)`. **This is not a broken access-control boundary** — `src/proxy.ts`'s generic `/^\/admin/` rule already gates the route itself to `ADMIN_DASHBOARD` before any request reaches the page or its actions, and no other code path calls these actions directly (verified: no callers outside `admin/2fa/page.tsx` and its own test file). Every admin subpage checks independently") of every admin `actions.ts` re-checking a feature flag inside the action body as defense-in-depth against a proxy misconfiguration or an internal refactor that weakens the edge gate. Rated medium, not high: today there is no exploitable path, but the missing second layer is exactly the kind of gap that turns into a real vulnerability the next time someone touches `proxy.ts`. See M5 below.

## MEDIUM

### M5(new) — `/admin/2fa` server actions have no independent permission check; parallel implementation of `/account/2fa`

**Files:** `src/app/(admin)/admin/2fa/actions.ts` (all four exports), `src/app/(account)/account/2fa/actions.ts` (parallel implementation), `src/proxy.ts:16-21,79-85`

`confirmEnrollmentAction`, `regenerateRecoveryCodesAction`, `resetEnrollmentAction`, and `clearFreshCodesCookieAction` in `admin/2fa/actions.ts` check only `session?.user` (e.g. `if (!session?.user) redirect("/signin")`). Every other admin `actions.ts` file in the codebase independently re-checks `hasFeature(session.user.features, FEATURES.ADMIN_*)` or role membership inside the action body — see `admin/flags/actions.ts:13` (`ADMIN_ROLE`), `admin/whats-new/actions.ts:32` (`ADMIN_WHATS_NEW`), `admin/users/actions.ts:87` (`ADMIN_USERS`), `admin/email-queue/actions.ts:31` (`ADMIN_EMAIL_QUEUE`). This file is the sole outlier and is inconsistent with CLAUDE.md's own Server Actions invariant: "always re-check session and permissions inside the action body."

**Verified this is not an exploitable bypass.** Next.js Server Actions submit via a POST back to the *same route* that rendered the form (not a separate, unguarded `/api/*`-style endpoint), and `src/proxy.ts`'s matcher (`config.matcher`, line 79-85) is a broad catch-all that only excludes static assets (`_next/static`, `_next/image`, `favicon.ico`, image extensions) — it does not special-case or exempt POST requests or server-action invocations. A POST targeting `admin/2fa/actions.ts` therefore still passes through the proxy's pathname check for `/admin/2fa`, which resolves to the unanchored `/^\/admin/ → FEATURES.ADMIN_DASHBOARD` rule (line 20) before the request reaches the action. A grep for callers of these four exports outside `admin/2fa/page.tsx` and its own test file found none. So today, a non-`ADMIN_DASHBOARD` member cannot reach this action set at all — the proxy gate is sufficient in the current codebase.

The actual risk is architectural, not present-tense: this file is the only admin mutation surface in the codebase relying *solely* on the edge proxy for authorization, with no defense-in-depth re-check. The instant `proxy.ts`'s matcher, `PROTECTION_RULES` ordering, or the `/admin` fallback rule is touched by an unrelated future change (a new public admin sub-route, a matcher regex edit, a refactor that moves this action to a shared file), this is the one file with no independent second gate to catch the regression. That is exactly the failure mode the codebase's own convention (see the feedback page's comment: "the admin layout gate covers session but not per-page features. Every admin subpage checks independently") exists to prevent everywhere else.

Separately: since the M2 fix (2026-05-17 finding) redirected the canonical unenrolled-user flow to `/account/2fa` (`totp/actions.ts:39`), `admin/2fa/actions.ts` and `account/2fa/actions.ts` are now two parallel implementations of materially the same TOTP self-enrollment feature — both call the same `@/lib/two-factor` helpers, write the same `AUDIT_ACTIONS.TOTP_*` events, and use the same fresh-recovery-codes cookie pattern, differing mainly in the cookie `path` string and the missing permission check. `admin/layout.tsx` and `admin/page.tsx` link to `/admin/2fa` as "Your 2FA," so this is live, intentional UX (manage your own 2FA from within the admin shell), not dead code — but maintaining two copies of security-sensitive TOTP logic means a future fix to one (a rate limit, a new invariant) can silently miss the other.

**Fix:** Add `hasFeature(session.user.features, FEATURES.ADMIN_DASHBOARD)` to all four actions in `admin/2fa/actions.ts`, matching the codebase-wide convention — cheap, and closes the defense-in-depth gap regardless of duplication. Separately (lower priority, a product decision not just a security one): consider whether `/admin/2fa` and `/account/2fa` should be consolidated into one implementation with two entry points, to stop the two TOTP action sets from drifting apart over time.

## LOW

### L1 — `changePassword` still has no rate limit on failed attempts

**File:** `src/app/(account)/account/actions.ts:198-234`

Unchanged from the prior review. An attacker with a stolen session token can brute-force the current-password check without triggering `checkRateLimit`, which is applied to other auth-adjacent actions (signin, TOTP verify, password reset request) but not here. bcrypt's `compare()` is used (not a fast-fail short-circuit), so this is not a timing issue — it's a missing throttle.

**Fix:** Add `checkRateLimit(`changepw:${session.user.id}`, { max: 5, windowSeconds: 900 }, ...)` at the top of the action, mirroring the pattern in `src/auth.ts`'s credentials `authorize()`.

### L2 — `changeEmail` still interpolates raw `newEmail` into HTML without escaping

**File:** `src/app/(account)/account/actions.ts:152`

```
<p>You requested to change your sign-in email address to <strong>${newEmail}</strong>.</p>
```

The regex at line 86 (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) still permits `<` and `>`, so `<img src=x onerror=...>@domain.com` passes validation and reaches the HTML body unescaped. This is the exact finding from 2026-05-17 — what changed is that the fix ingredient (`escapeHtml()`) now exists in the codebase (`src/lib/email/escape-html.ts`) and is correctly used in the newer feedback-notification email path, but it was never applied to this original site. Impact is unchanged and still low: the email is sent only to `newEmail` itself, so the attacker injects into their own inbox (phishing-content risk, not app-side XSS).

**Fix:** Wrap `newEmail` with the existing `escapeHtml()` helper at the interpolation site — this is now a one-line fix since the helper is already in the codebase and unit-testable pattern is already established at the feedback call site.

### L3 — `assignRoleAction` / `removeRoleAction` still accept unvalidated UUID strings

**File:** `src/app/(admin)/admin/users/actions.ts:31-33, 53-56`

Unchanged. `userId` and `roleId` are taken raw from `formData`. SQL injection remains impossible (Drizzle parameterizes) and a FK constraint catches non-existent IDs, but a malformed string can still produce a raw DB error surfaced (however indirectly) to the admin UI.

**Fix:** Validate both as UUIDs (regex or a shared `isUuid()` helper) before the DB call; return an `ActionResult` error instead of letting a malformed value reach Drizzle.

### L4 — NEW: `CRON_SECRET` compared with `!==` instead of a constant-time comparison

**File:** `src/app/api/cron/maintenance/route.ts:11-23`, `src/app/api/cron/email-queue/route.ts:3-19`

Both cron routes correctly require `CRON_SECRET` to be set (returning a disabled/no-op response otherwise) and check the `Authorization: Bearer <secret>` header before doing any work — this part is sound. However the comparison is a plain `!==` string check, not `crypto.timingSafeEqual`. This is inconsistent with the standard the codebase itself sets in `src/app/api/webhooks/resend/verify-signature.ts`, which explicitly uses `timingSafeEqual` for HMAC comparison and documents why. A network timing attack against a bearer-token compare is impractical in this deployment shape (Vercel edge/serverless jitter dwarfs any signal, and the secret is high-entropy), so this is rated low, not medium — but it's a needless inconsistency given the safer pattern already exists two files away.

**Fix:** Use `crypto.timingSafeEqual` (length-checked first, as `verify-signature.ts` already models) for the cron bearer-token comparison in both route handlers.

### I2 — Turnstile fails open on verification-API error (intentional, documented)

**File:** `src/lib/turnstile.ts:14-36`

Two related, deliberate behaviors: (1) a true no-op (`return true`) when `TURNSTILE_SECRET_KEY`/`TURNSTILE_SITE_KEY` are unset — matches the CLAUDE.md claim of "complete no-op until two env vars are set"; (2) fails **open** (`catch { return true }`) if the Cloudflare verify API call itself errors or times out. This is an availability-over-strictness tradeoff, explicitly documented in DECISION-026 with a one-line fail-closed change path for operators who want it. Not a defect — flagged here only so it stays visible at the next review; a fork handling higher-value targets (financial transactions, etc.) should reconsider the default.

### I3 — Report-only CSP with `unsafe-inline` (intentional, tracked, per CLAUDE.md)

**File:** `next.config.ts:23-45`

`Content-Security-Policy-Report-Only`, not enforced; contains `'unsafe-inline'` in both `script-src` and `style-src`. Justified by an inline TODO comment documenting the exact 4-step tightening path (nonce-based scripts, Tailwind extraction, drop `unsafe-inline`, flip header to enforced). `frame-src`/`connect-src` are correctly scoped to Cloudflare Turnstile only. This matches the CLAUDE.md-documented posture exactly — working as designed, not a gap. Re-flagged only as a standing reminder that "report-only" is a starting point, not an end state, for any fork going to production with user-generated content beyond what exists today.

## New Surface Reviewed (clean — no findings)

- **Lockout enumeration-safety** (`src/auth.ts:141,146,152`) — `authorize()` returns a generic `null` for rate-limited, missing-password/inactive, and locked-account cases alike (verified all three branches directly). A locked-out account is indistinguishable from a wrong password to the client. bcrypt `compare()` still runs on the credentialed path; no fast-fail bypass.
- **Session/JWT claim hygiene** (`src/auth.ts:238-330`) — `jwt()` callback re-queries the DB every request for `isActive`, `twoFactorRequired`, roles, and features rather than trusting stale token claims; deactivated/deleted users get an empty token (forced sign-out) on next request. Full grep of `token.` assignments in `src/auth.ts` confirms no `password` hash or TOTP `secretCiphertext` is ever assigned onto the token/session object.
- **Webhook signature verification** (`src/app/api/webhooks/resend/verify-signature.ts`) — `crypto.timingSafeEqual()` for HMAC comparison, explicit ±300s replay window with a `Number.isFinite` NaN guard, multi-signature `v1,`-prefixed entry parsing for key rotation, and a length-mismatch guard before `timingSafeEqual` (avoids a throw on mismatched lengths). Exemplary — no findings.
- **Admin route proxy coverage for new subpages** (`src/proxy.ts:16-20`) — `/admin/whats-new`, `/admin/feedback`, `/admin/email-queue`, `/admin/audit` (all new since May) are not individually listed in `PROTECTION_RULES` but are correctly caught by the unanchored 4th rule `/^\/admin/` → `FEATURES.ADMIN_DASHBOARD`. Each page additionally enforces its own fine-grained feature (`ADMIN_WHATS_NEW`, `ADMIN_FEEDBACK`, `ADMIN_EMAIL_QUEUE`, `ADMIN_AUDIT`) independently — correct two-layer defense-in-depth, not a coverage gap.
- **Email-queue claim query** (`src/lib/email/queue.ts:319-341`) — the CTE `UPDATE ... FOR UPDATE SKIP LOCKED ... RETURNING *` uses the `sql` tagged template with only `${limit}` (a number) interpolated; properly parameterized, not string-concatenated. `check:sql-date` and `check:audit` both pass clean (`npm run check` — verified directly).
- **`retryEmailAction` audit-exemption** (`src/app/(admin)/admin/email-queue/actions.ts:1-49`) — no `recordAudit()` call, but explicitly and correctly marked `audit-exempt` (file-level and inline comment) per the tripwire's own exemption mechanism; the prior permanent-failure event is captured separately by the worker via `EMAIL_QUEUE_PERMANENT_FAILURE`. Deliberate, not a silent gap.
- **Feedback privacy invariant** (`src/app/(admin)/admin/feedback/page.tsx:66-81`) — the admin triage query joins `feedback` to `users` only (`leftJoin(users, eq(feedback.userId, users.id))`) and selects `users.name` only — no `email` column selected. Matches the schema comment and CLAUDE.md's stated invariant exactly.
- **Token hashing at rest** (`src/app/(account)/account/actions.ts`, `src/app/(password-reset)/*/actions.ts`) — both email-verification and password-reset tokens are generated via `randomBytes(32)`, hashed with `createHash("sha256")` before insert, and looked up by hash (not raw compare) on consumption. This directly confirms M1's fix at the implementation level, not just the schema comment.
- **FK `onDelete` choices** (`src/lib/db/schema.ts`, all 16 FK declarations) — every user-owned join/data table (`accounts`, `sessions`, `userRoles`, `userTotp`, `userTotpPendingEnrollments`, `userTotpRecoveryCodes`, `emailVerificationTokens`, `passwordResetTokens`, `feedback`, `feedbackPromptState`) correctly cascades on user deletion. History/audit-preserving tables (`auditEvents.actorUserId`, `whatsNewEntries.createdBy`/`updatedBy`) correctly use `set null` so historical rows survive actor deletion instead of being silently destroyed. No misconfigured FK found.
- **Audit coverage of new mutation surfaces** — `whats-new` CRUD (`create`/`update`/`delete`) all call `recordAudit()` with dedicated `AUDIT_ACTIONS.WHATS_NEW_ENTRY_*` keys (`src/app/(admin)/admin/whats-new/actions.ts:53-149`). Feedback status transitions and email-queue retry were checked above.

## Observational — Not a Finding

**Text-column "enum" convention has no DB-level CHECK constraint.** Status/category-like columns (`feedback.status`, `feedback.category`, `emailQueue.status`, `emailQueue.templateKey`) are typed as plain `text`, with validity enforced only in application code (server actions), per an explicit, repeated schema-comment convention ("text, not pgEnum — consistent with project convention"). A grep of `docs/decisions.md` found no dedicated ADR documenting this as a considered tradeoff versus an unreviewed default — it appears to be inherited convention rather than a deliberate decision on record. This is not rated as a finding (no direct security impact under normal application code paths — Drizzle's application-layer checks are consistently applied at every write site reviewed), but if a future migration or ad-hoc admin SQL write bypasses application code, nothing at the DB layer would catch an invalid status value. Worth a documented decision (or a CHECK constraint) the next time `schema.ts` is touched for these tables, but not urgent enough to block anything.
