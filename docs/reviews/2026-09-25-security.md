## HIGH

### H-new-1 — `sanitizeCallbackUrl()`'s open-redirect guard has a live bypass via the WHATWG backslash-normalization rule; it regresses H1 (2026-05-17, believed closed since 2026-07-11)

**File:** `src/lib/auth/safe-callback.ts:17-20`

```typescript
export function sanitizeCallbackUrl(raw: string | undefined | null): string {
  if (!raw) return "/launch";
  return raw.startsWith("/") && !raw.startsWith("//") ? raw : "/launch";
}
```

The guard only rejects values starting with `//` or an absolute scheme. It does not know that every modern browser's URL parser (the WHATWG URL Living Standard, which Node's own `URL` class implements identically) treats a **backslash** the same as a forward slash when resolving a relative reference against a base origin, for every "special" scheme (`http`, `https`, `ws`, `wss`, `ftp`, `file`). A string like `/\evil.example` starts with a single `/` and is accepted unchanged — but a browser resolving it as a relative `Location` target does **not** treat it as a same-origin path. It treats the leading `/\` as "authority follows," and the browser navigates cross-origin. Verified directly, not asserted:

```
$ node -e 'console.log(new URL("/\\evil.example", "https://good.example").href)'
https://evil.example/
```

And reproduced against the actual shipped function (throwaway Vitest case, run once and deleted — no file left changed):

```typescript
const evil = "/\\evil.example";
expect(sanitizeCallbackUrl(evil)).toBe(evil);                          // passes — bug confirmed
expect(new URL(sanitizeCallbackUrl(evil), "https://presbyportal.org").origin)
  .toBe("https://evil.example");                                        // passes — browser target confirmed
```

Both assertions passed against the real, unmodified `src/lib/auth/safe-callback.ts`.

**This is exploitable on the single most universal path in the app.** `sanitizeCallbackUrl()` is the *entire* open-redirect defense (per its own doc comment) for four call sites, and the two that matter most feed a raw, unvalidated `redirect()` call with no second check:

- **`/launch?next=/\evil.example`** (`src/app/launch/page.tsx:59` → `src/app/launch/destination.ts`). `orgSlugFromPath("/\\evil.example")` splits on `/` and returns `null` (the backslash payload has no `/o/<slug>` shape), so `computeDestination()`'s `enterable` check short-circuits to `true` for a `null` slug (`src/app/launch/destination.ts` — `slug === null || …`) and the requested path is returned verbatim as `destination.path`. `redirect(destination.path)` in `launch/page.tsx:93` then sends the browser to `evil.example`. **`/launch` is the single post-authentication target for every sign-in on the platform (DECISION-034)** — this is reachable by any authenticated user who clicks a crafted link, with no further precondition.
- **`verifyTotpAction`** (`src/app/(auth)/totp/actions.ts:32,79`) — `redirect(callbackUrl)` on a successful TOTP code, where `callbackUrl` is `sanitizeCallbackUrl(formData.get("callbackUrl"))`. An attacker sends a 2FA-enrolled victim `https://presbyportal.org/totp?callbackUrl=%2F%5Cevil.example`; the victim enters a real, valid TOTP code (they believe they are completing their own sign-in) and is redirected to `evil.example` immediately after — the worst possible moment for a phishing redirect, since the user has just proven their identity and their guard is down.
- **`signInWithCredentials`** (`src/app/(auth)/signin/actions.ts:113`) — `redirect(input.callbackUrl)`, where `input.callbackUrl` traces back to `sanitizeCallbackUrl(sp.callbackUrl)` on `signin/page.tsx:47`. Same shape, one hop earlier: `https://presbyportal.org/signin?callbackUrl=%2F%5Cevil.example`.
- `/account/2fa/page.tsx:34` uses the same sanitizer for a rendered link rather than a `redirect()` call — lower severity (requires a click on the page, not an automatic 307), but the same payload survives and should be fixed by the same change.

**Exploit sketch:** attacker emails or messages a signed-in-likely target (a stated clerk, a presbytery admin — anyone with a presby account) a link of the form `https://presbyportal.org/launch?next=%2F%5C<attacker-domain>` or the TOTP variant above. Following it while authenticated (or completing a real, valid TOTP challenge) ends on `https://<attacker-domain>/`, which can render a pixel-perfect "session expired, please sign in again" page. Because the redirect fires from presby's own domain and the URL bar shows presbyportal.org right up until the 307 completes, this is a materially more convincing pretext than a bare phishing link — it inherits the user's trust in the real login flow they just completed.

**Fix.** Reject any candidate containing a backslash before the existing checks (cheapest, matches the actual browser behavior being defended against), or — more robust against future WHATWG edge cases — validate by parsing:

```typescript
export function sanitizeCallbackUrl(raw: string | undefined | null): string {
  if (!raw) return "/launch";
  if (!raw.startsWith("/") || raw.startsWith("//") || raw.includes("\\")) {
    return "/launch";
  }
  return raw;
}
```

Add a regression test with the exact payload above (`"/\\evil.example"` → `"/launch"`), plus the double-backslash and leading-backslash variants (`"\\/evil.example"`, `"/\\\\evil.example"`) — all three resolve off-origin per the Node repro. This is a `fix:` commit; per Workflow Rule on bug-fix trailers it needs `Caught-By: agent-review` / `Discovered-In: Phase-4` (this review), and a failing-then-passing regression test in `src/lib/auth/safe-callback.test.ts` before the fix, per CLAUDE.md's bug-fix variant.

### H-new-2 — `setPersonDisabilitiesAction`'s audit write puts tier-3 medical/pastoral data into the platform-wide `audit_events` table, readable by any platform admin with `ADMIN_AUDIT`

**Files:** `src/lib/person-sensitive.ts:695-702`, rendered at `src/app/(admin)/admin/audit/page.tsx:275,326-330`

```typescript
await recordAudit({
  action: AUDIT_ACTIONS.TENANT_PERSON_DISABILITY_SET,
  resourceType: "person_disabilities",
  resourceId: personId,
  metadata: { organizationId, categories: input.categories },   // <-- the leak
});
```

`input.categories: string[]` is the actual set of disability categories being recorded for a named person (`resourceId` is already the `personId` — the row is fully identifiable without the metadata at all). This is a **direct violation of the "No Role Carries a Wildcard" invariant** as CLAUDE.md states it verbatim: *"Tiers: 1 directory, 2 financial, 3 pastoral, demographic, medical — pastoral notes sit above financial data."* Disability status is squarely tier-3 (medical/demographic), and `/admin/audit` is gated by `FEATURES.ADMIN_AUDIT` — a **platform-shell** permission with no tenant scoping and no tier check of any kind. `admin/audit/page.tsx:275` reads `row.metadata` with no filtering and `:326-330` renders it verbatim as `JSON.stringify(meta, null, 2)` inside a `<details>` disclosure on every row. A platform admin — who, per the same document, "is not above a national admin" and gets nothing inside a congregation merely by platform position — can today read exactly which disability categories are on file for a named person at a named organization, with zero congregation-level permission of any kind.

**Confirmed as the sole outlier in its own file**, not a codebase-wide pattern: the three sibling functions in `src/lib/person-sensitive.ts` (`addPersonNote` at line 434, `setPersonDemographics` at line 513, `setPersonMedical` at line 614) all correctly write `metadata: { organizationId }` (or `{ organizationId, personId, visibility }` for the note, which carries no note *content*) — none of them put the actual sensitive value into the audit row. `setPersonDisabilities` is the one function in the file that does, and nothing in `src/lib/person-sensitive.test.ts` asserts on the metadata shape closely enough to have caught it (the test file only mocks `AUDIT_ACTIONS`/`recordAudit`, it never inspects the call's `metadata` argument for this action).

A lower-severity sibling of the same shape: `src/lib/children.ts:513,585` writes `relationship: input.relationship` (e.g. "parent", "guardian", "foster") into `TENANT_PERSON_RELATIONSHIP_ADDED` metadata — family-structure information, not medical/pastoral, so tier-1/2 rather than tier-3, but the same principle applies: a resourceId is sufficient to identify *that* something changed; the audit log does not need to say *what*.

**Fix:** Drop `categories: input.categories` from the `TENANT_PERSON_DISABILITY_SET` metadata (match the three sibling functions — `metadata: { organizationId }` is sufficient; `resourceId` already names the person). Do the same for `children.ts`'s `relationship` field as a lower-priority companion fix in the same pipeline. Add a unit test asserting the exact metadata shape for all four `person-sensitive.ts` audit writes (not just that `recordAudit` was called) so a future edit to this file can't reintroduce the leak silently. This is also a `fix:` commit (`Caught-By: agent-review`, `Discovered-In: Phase-4`) with a regression test.

## Forward-looking — assessed before being built

### F-1 — The planned unauthenticated statistics-submission endpoint (D16, Phase 2 Ruling 11): design is sound; two gaps to close before Increment 6 ships code

`docs/work-log/2026-09-24-lifecycle-affiliation-returns.md` Ruling 11 and `docs/schema-design-2.md` §6 pre-place (DDL not yet written — no `drizzle/0048` exists, no `statistics_submission_grants` table exists in `src/lib/db/domain/returns.ts` yet, confirmed by direct read) the platform's first write path with no session. Assessed against this review's usual checklist:

**Gets right, already, on paper:**
- Its own route group, not `(org)` — correctly modeled on `(password-reset)`/`(email-verify)`, unauthenticated by design, platform palette per DECISION-047 (a branded page would confirm tenancy to a prober holding a guessed token).
- `token_hash unique`, never the plaintext token at rest — correctly follows the `password_reset_tokens` precedent (contrast **F-2** below, where a *shipped* table got this wrong).
- Single-purpose, single-`(org, about, year)`, expiring, revocable grant — a partial unique index (`where revoked_at is null and submitted_at is null`) prevents two live grants for the same target, which is the right shape to prevent grant-confusion.
- The design document itself already names the right question: *"Rate-limit issuance and submission. An unauthenticated write endpoint scoped by a guessable (org, year) is exactly the surface … the security review should look at hardest."*

**Two gaps the pre-ruling leaves unresolved, to close in Increment 6's own design, not assumed later:**
1. **No rate-limiting shape is specified yet**, only flagged as needed. When this is built, the submission route needs at minimum a per-token attempt cap (a wrong attestation or a malformed payload against a real token should not be retryable without limit) *and* a per-IP cap (guards the token-guessing case even though `token_hash` entropy should make guessing infeasible on its own — defense in depth, matching how `checkRateLimit()` is layered with Turnstile on the credentials path today). Increment 6's design doc should name the exact `{max, windowSeconds}` pair and the audit key, not leave it to the implementer to improvise against `src/lib/rate-limit.ts`'s existing API.
2. **The actor-less audit write needs an explicit, named exemption**, the same way `SITE_CONTENT_INGESTED` (`src/app/api/sites/ingest/route.ts:244`) is explicitly called out as outside `check:audit`'s `actions.ts` scan (DECISION-084) with `actor: null`. A submission-grant write will have no `session.user.id` to attribute — that is correct and expected (attestation, not authentication, per the design) — but it should ship with the same explicit "this is a deliberate null actor, not a missed check" comment and a dedicated `AUDIT_ACTIONS` key from day one, so a future `check:audit` false-positive investigation doesn't have to rediscover why.

Neither gap blocks the current DDL-only state; both should be resolved in Increment 6's own Phase 3, which Ruling 11 already earmarks as needing "its own security pass."

### F-2 — `transfer_certificates.claim_token` is stored in plaintext; no application code exercises it yet, so nothing to exploit today, but the gap should close before it does

**File:** `src/lib/db/domain/roll.ts:153` (`claimToken: text("claim_token").notNull().unique()`), consumed only by `presby_link_person()` (`drizzle/0009_presby_rls.sql:198-243`, a `SECURITY DEFINER` SQL function).

This is a shipped table (D1's two-sided transfer mechanism, F9) with a real bearer-token column, stored as plain `text` rather than hashed — the exact class of gap M1 (2026-05-17) found and fixed for `email_verification_tokens`, and the class this review's own F-1 confirms the *newer* D16 design got right on paper. **Confirmed no application code path creates or claims a certificate yet**: a full grep for `transferCertificates`/`presby_link_person` outside `src/lib/db/domain/roll.ts` and the SQL migration itself turns up nothing under `src/app/` or any other `src/lib/*.ts` — only `presby_match_person()` (a different, minimal-disclosure fuzzy matcher) is called from app code today. So there is no live exploit: a database read exposes a token, but nothing yet lets an attacker who obtained one *use* it through the application, because no server action or route calls `presby_link_person(reason='transfer_certificate', ...)`.

This is exactly the shape of finding a "before it's built" review exists to catch. **Whichever pipeline first ships the issue/claim UI for transfer certificates should hash `claim_token` (SHA-256, looked up by hash, following the `password_reset_tokens`/D16 pattern) before wiring up a write path**, not retrofit it after a live exploit path exists. Flagging now rather than waiting, per this review's brief to assess bearer-token surfaces regardless of build status. This table is schema (database-admin's ordinary remit going forward), but the finding itself belongs on this list because the token *generation and consumption pattern* is an application-layer decision the first api-developer to touch it needs to get right, and the table already exists and is easy to miss precisely because it currently has no caller to draw attention to it.

#### B-H2 — `app_role_permissions` has no RLS and full tenant DML: one congregation can read and rewrite another congregation's role→permission bindings

`app_role_permissions` is the binding table behind `presby_effective_permissions()`
— it is the authorization layer's storage. It has **no `organization_id`
column**, so `drizzle/0009`'s `tenant_tables` loop never touched it: no
`ENABLE`/`FORCE ROW LEVEL SECURITY`, no `tenant_isolation` policy. It is
tenant-owned only transitively, through `role_id -> app_roles(id)`. Its parent
`app_roles` **is** correctly policed (`app_roles_select` even gets the
`OR organization_id IS NULL` global-row case right, which is the pattern B-M4
below wants copied elsewhere). The child was missed.

Catalog:

```
$ select relname, relrowsecurity, relacl from pg_class where relname='app_role_permissions';
 app_role_permissions | f | {neondb_owner=arwdDxtm/neondb_owner,
                             presby_platform=arwd/neondb_owner,
                             presby_app=arwd/neondb_owner}
$ select conname, pg_get_constraintdef(oid) from pg_constraint where conrelid='app_role_permissions'::regclass;
 app_role_permissions_role_id_app_roles_id_fk | FOREIGN KEY (role_id) REFERENCES app_roles(id) ON DELETE CASCADE
```

Live probe as `presby_app` (`NOBYPASSRLS`), org context set to Alder, whole
thing rolled back:

```
begin;
select set_config('app.current_org_id','22222222-2222-2222-2222-222222222222', true);
select count(*) from app_roles;                                    -->  15   (own + global, correctly filtered)
select count(*) from app_role_permissions;                         -->  71   (NOT filtered)
select count(*) from app_role_permissions arp
  where not exists (select 1 from app_roles r where r.id = arp.role_id);  -->  43
rollback;
```

**43 of the 71 visible binding rows belong to `app_roles` rows the same
connection cannot see** — i.e. to other tenants' roles. And `presby_app` holds
`arwd`, so those 43 rows are not merely readable, they are **writable**: a
tenant-context query can `insert into app_role_permissions (role_id,
permission_key)` against another congregation's role id and thereby grant that
congregation's role-holders a permission their session never voted — including
a tier-2 or tier-3 key. Nothing in the database prevents it; no trigger exists
on this table.

This violates *Isolation Is a Database Property* and *No Role Carries a
Wildcard* simultaneously, and it is the only finding in this half with a
demonstrated cross-tenant **write** path rather than a read or a
defense-in-depth gap. It is rated HIGH rather than CRITICAL because reaching it
requires a raw-SQL path on the tenant connection (no shipped server action
writes this table with a caller-supplied `role_id`) and another org's `role_id`
UUID, and because Section A's SQL-injection checklist row passed — so there is
no known route from user input to this table today.

**Fix.** Policy, on the `visible_via_membership_*` model already used for the
`people` family — a `SELECT` arm that admits global rows, and write arms that
never do:

```sql
alter table app_role_permissions enable row level security;
alter table app_role_permissions force  row level security;

create policy app_role_permissions_select on app_role_permissions for select
  using (exists (select 1 from app_roles r where r.id = role_id
                   and (r.organization_id = presby_current_org()
                        or r.organization_id is null)));

-- writes: own-org roles only; a tenant may never edit a global role's bindings
create policy app_role_permissions_insert on app_role_permissions for insert
  with check (exists (select 1 from app_roles r where r.id = role_id
                        and r.organization_id = presby_current_org()));
-- ...matching update (using + with check) and delete arms
```

Note the `EXISTS` subquery reads `app_roles`, itself `FORCE ROW LEVEL
SECURITY` — inside a policy that is correct and wanted (it inherits the
caller's context), but it must **not** later be refactored into a
`SECURITY DEFINER` helper without re-deriving the org check, or F26 inverts
into an over-permission. Owes a `test-rls.sql` section asserting the 43-row
count above goes to zero, proven failing-first by dropping the policy.

Audit the same shape elsewhere while fixing: `app_role_permissions` is the
only *authorization* table in this class, but the check "tenant-owned only via
a FK, therefore no `organization_id`, therefore no policy" is worth running
across the schema.

#### B-M1 — `presby_apply_affiliation_to_org_tree()` arms the affiliation guard-bypass GUC before any authorization or existence check, and is granted to `presby_app`

```

CREATE OR REPLACE FUNCTION public.presby_apply_affiliation_to_org_tree(p_subject_org_id uuid, p_as_of date DEFAULT CURRENT_DATE)
 RETURNS void LANGUAGE plpgsql SECURITY DEFINER AS $function$
...
begin
  perform set_config('presby.affiliation_trigger_active', 'true', true);   -- FIRST STATEMENT
  select o.path, replace(o.slug,'-','_') into v_old_path, v_label from organizations o where o.id = p_subject_org_id;
  if v_label is null then return; end if;                                  -- early return AFTER the arm
```

The GUC is transaction-local, and `organization_affiliations_guard`'s function
is a bare read of exactly it:

```
CREATE OR REPLACE FUNCTION public.presby_guard_organization_affiliations() RETURNS trigger AS $$
begin
  if coalesce(current_setting('presby.affiliation_trigger_active', true), '') <> 'true' then
    perform presby_deny_affiliation_change();
  end if; ...
```

So one call to `presby_apply_affiliation_to_org_tree()` — with **any** org id,
including a nonexistent one, since `set_config` precedes the early return —
disarms `organization_affiliations`' `UPDATE`/`DELETE` guard for the remainder
of the transaction. The function is `SECURITY DEFINER`, performs no
`presby_current_org()` check (unlike `presby_transfer_affiliation()`,
`presby_set_organization_identifier()`, `presby_effective_permissions()` and
`presby_list_published_returns_to_me()`, all of which do), and
`drizzle/0044:750` grants `EXECUTE` on it to `presby_app`.

`presby_app` holds `SELECT` on `organization_affiliations` and nothing else. That

warns against, here applied to the tenant role instead of the owner — and on
`getPlatformDb()` (= `neondb_owner`, which *does* hold DML and which ownership
exempts from grants entirely) the disarm is real. Any platform-side code path
that calls this function and then writes `organization_affiliations` in the same

subject-exists lookup; add the `presby_current_org()` standing check the sibling

`src/` finds the name only in comments, never in a call, so the grant is
unused. Longer term the arming belongs in the caller
(`presby_transfer_affiliation()`, `presby_apply_affiliation_row()`), scoped to
the statement that needs it, not in a callee any grantee can invoke.

#### B-M2 — 28 of 35 `SECURITY DEFINER` functions carry no `SET search_path`; the 7 that do prove the convention exists

```
$ select proname, proconfig from pg_proc p join pg_namespace n on n.oid=p.pronamespace
   where n.nspname='public' and p.prosecdef;
-- WITH search_path=public (7):
   presby_membership_is_active, presby_person_unclaimed_or_own_org,
   presby_public_committee_roster, presby_public_staff_roster,
   presby_published_site, presby_two_factor_required, presby_user_organizations
-- WITHOUT (28), including every guard/freeze/apply trigger function and:
   presby_publish_sasr_snapshot, presby_transfer_affiliation,
   presby_set_organization_identifier, presby_effective_permissions,
   presby_link_person, presby_match_person, presby_reconcile_current_roll, ...
```

`SET search_path` is the standard `SECURITY DEFINER` mitigation: without it, a
role that can create an object in a schema earlier in the caller's
`search_path` can shadow a table or operator the function resolves unqualified,
and the shadowed call runs as the owner.

**Not exploitable on this database today**, and the reason is worth recording
rather than assuming:

```
$ select has_schema_privilege('presby_app','public','CREATE');   --> false
$ select has_database_privilege('presby_app',current_database(),'CREATE'); --> false
$ select nspacl from pg_namespace where nspname='public';
  {pg_database_owner=UC/pg_database_owner, =U/pg_database_owner,
   presby_app=U/pg_database_owner, presby_platform=U/pg_database_owner}
```

Neither application role can create a schema or an object anywhere, so there is
nowhere to plant a shadow. Rated MEDIUM rather than LOW because the protection
is a single `CREATE` privilege away from evaporating, the mitigation is one
clause per function, and the inconsistency is itself the hazard — seven
functions carry it, so a reader cannot tell whether an omission is a decision
or an oversight.

**Fix.** `alter function … set search_path = public` (or `= pg_catalog, public`)
on all 28, in one migration, and add the rule to `database-admin.md`'s
`SECURITY DEFINER` checklist so new functions get it by default. A `test-rls.sql`
assertion that `pg_proc.proconfig is not null` for every
`prosecdef and proname like 'presby%'` makes it permanent in four lines.

`pg_constraint`, restricted to FKs where both ends carry an `organization_id`:

$ select conname, pg_get_constraintdef(oid) from pg_constraint where contype='u' and ...;
 events_id_org_key        | UNIQUE (id, organization_id)

```

**`roll_actions.voids_action_id` is the one that matters most.** *The Roll Is
the System of Record* says an approved action is corrected only by recording a
`void`. A plain FK lets a `void` in org B name an approved action in org A as
its target. RLS filters the read; it does not filter that write, which is F2's
whole point — and the correction would land against another congregation's
permanent record. `publications.supersedes_id` is the same shape on the D21
publication chain and shipped in `drizzle/0047`, i.e. in the most recent wave,

global case. The `app_roles_select` policy already models the intent
(`organization_id = presby_current_org() OR organization_id IS NULL`); the FK
needs the equivalent, most likely a `CHECK`-plus-trigger pair asserting that the
referenced row is either own-org or global. Worth doing for `role_grants` in
particular — it is the authorization path, and it is the same table family as
B-H2.

**Fix.** One migration for the four mechanical cases (add
`unique (id, organization_id)` where missing, drop the single-column FK, add the
composite); a short design note for the two nullable-parent cases; a
`test-rls.sql` section per fix, proven failing-first by attempting the cross-org
write and confirming it currently succeeds.

select count(*) from groups;                                              --> 4
select count(*) from group_types;                                         --> 0
select count(*) from groups g join group_types t on t.id = g.group_type_id; --> 0
select count(*) from app_roles;                                           --> 15   (same problem, solved correctly)
rollback;
```

All 14 live `groups` rows reference a `group_types` row the tenant connection
cannot read. `app_roles` has the identical global-row requirement and handles it
properly — `app_roles_select` carries `USING (organization_id =
presby_current_org() OR organization_id IS NULL)` — so the fix is a known,
in-repo pattern, not a new design.

**This is not a broken feature**, and the code is admirably explicit about why:
`src/lib/groups.ts:487` ("Read through `getPlatformDb()`, not `tx` — see this
file's header for why") and `src/lib/org-provisioning.ts:286` both deliberately
escape to the RLS-bypassing connection to read these rows, and
`src/lib/groups.ts:501-509` and `:587-592` re-validate the chosen id
server-side. It works.

The finding is that a wrong policy has been paid for with a standing
`getPlatformDb()` escape hatch on an org-scoped read path. `getPlatformDb()` is
the connection that bypasses every policy and, per F44, every grant; the
`(org)` contract forbids it in `src/app/(org)/` precisely because each use is a
place where tenant isolation is asserted by code review rather than by the
database. `src/lib/groups.ts` is in `src/lib/`, so the letter of the rule holds
— but two RLS-bypassing reads exist only because one policy predicate is wrong.

**Fix.** Split `group_types`' policy the way `app_roles`' is split: a `SELECT`
arm admitting `organization_id is null`, and `INSERT`/`UPDATE`/`DELETE` arms
that do not. Then both call sites read through `tx`, and the two
`getPlatformDb()` uses and their explanatory comments delete. Owes a
`test-rls.sql` section asserting the `join` above returns 14, not 0.

#### B-L2 — `presby_membership_is_active()` is a cross-tenant membership oracle

```

`DEFINER` over a `FORCE ROW LEVEL SECURITY` table, both ids caller-supplied, no

#### B-L3 — Two non-trigger `SECURITY DEFINER` functions carry `PUBLIC EXECUTE`

```

invoked outside a trigger context, so this is cosmetic; worth tidying in the
same statement, not worth its own work.
