## 0.15.0 — 2026-08-26

### Feature: Portal card treatment, icons, and a footer

**Value:** The congregation already knows and likes the look and feel of `fpcw-directory`, its prior church-portal system. This brings two of that system's UX cues — a subtle hover-lift on cards, and icon-labeled fields — into presby's own portal, plus a footer the portal never had at all, without pulling in `fpcw-directory`'s own hardcoded color palette. Branding stays entirely on presby's own brand-token subsystem.

#### What's New

- Every card on the portal home and directory (member tiles, person cards, household cards, deacon cards) now lifts with a subtle shadow on hover — a direct, brand-safe port of `fpcw-directory`'s own card treatment. Cards holding more than one link target (a person card's name link plus its `mailto:`/`tel:` links) get the shadow-lift only, never a whole-card `cursor-pointer`, so hovering over inert text never implies the whole card is one click target.
- Contact fields and portal tiles now carry small `lucide-react` icons (mail, phone, map pin, and a per-tile icon set), matching `fpcw-directory`'s own icon usage.
- `/o/<slug>` pages gain a real footer for the first time: the organization's own contact info (address and a working `tel:` link, when the org has one on file), a short recap of the portal's main destinations, and a copyright line. An organization with no contact info on file still gets a clean footer — nav recap and copyright only, never a broken layout.
- Nav dropdown grouping (also considered for this pass) was explicitly deferred — the portal's nav already collapses correctly on mobile from a prior fix, and grouping is being held for when a real multi-destination group exists to group.

#### Permissions

No new permission — presentation-layer only, riding whatever already gates each nav destination or card.

#### Flags

| Flag key | Default | Gates |
|----------|---------|-------|
| `org_portal.chrome_v3` | off | The card hover/icon treatment and the new footer, as one atomic rollback unit — independent of `org_portal.chrome_v2`, which is already fully live |

### Feature: Officer-terms administration

**Value:** Recording who holds session or diaconate office, when a term starts or ends, and which district a deacon is assigned to, could previously only be done by hand-editing the database — a real gap for the first congregation actually using the platform. A Stated Clerk (a real, elected office, not a new invention) can now record and end officer terms through a real screen.

#### What's New

- `/o/<slug>/admin/officers` lists the current roster; `/officers/[personId]` shows a person's full officer history.
- Recording a term captures the person, office, start date, and — for a deacon — which district, with optional election/installation dates and a minute reference. Ending a term never deletes it; it's marked ended, preserving history.
- Attempting to record a second overlapping term for the same person and office is caught with a specific message ("X already has an open term as Y — end it first") rather than a raw database error.
- Recording someone as clerk of session here is deliberately separate from granting them administrative access to the portal — the two are unlinked on purpose, and the UI says so.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `officers.manage` | Recording/ending officer terms, viewing the roster and history. Bound to the existing Stated Clerk role — no new role was created. |

#### Flags

| Flag key | Default | Gates |
|----------|---------|-------|
| `org_portal.officers` | off | Whether `/o/<slug>/admin/officers*` exists at all |

#### New Routes

- `GET /o/<slug>/admin/officers` — the officer roster
- `GET /o/<slug>/admin/officers/[personId]` — a person's officer history

### Defect Fix: Sitemap test asserted against the wrong fixture shape

**Problem:** `sitemap.xml`'s own regression test was failing on `main`, first noted while preparing the v0.14 release and left as a fast-follow at the time.

**Root Cause:** `buildSitemapEntries()` (presby-site-kit) only lists a page that opts in via `frontMatter.navLabel` — the same signal the on-page nav itself uses. The test's own mock pages carried empty front matter, so the assertion never matched real behavior; the route itself was never broken.

**Fix:** Updated the test's fixture pages to carry `navLabel`, and added a case pinning that a `navLabel`-less page is correctly excluded from the sitemap.

**Testing:**
- [x] `sitemap.xml/route.test.ts` — 3/3 passing (was 1/2)

### Defect Fix: A pagination control's markup could reveal a church's real name to an outside prober

**Problem:** `npm run check`'s brand-scope tripwire was failing on the shared pagination control, introduced with the member/directory pagination feature and unnoticed since.

**Root Cause:** The Previous/Next controls were hand-rolled button-shaped `<div>`s instead of the generated `<Button>` primitive — exactly the pattern this repo's brand-scope check exists to catch, since a hand-rolled control can silently drift outside the two brandable route groups' contract.

**Fix:** Both controls now render through the `<Button>` primitive (`variant="ghost"`), preserving the same 44px touch targets pagination already had.

**Testing:**
- [x] `pagination.test.tsx` — 5/5 passing, unchanged behavior
- [x] `npm run check` — all four tripwires pass

### Enhancement: Sign-out returns to the congregation's own site, the directory gets a real button group, and the portal uses more of the screen

**Value:** Found live-testing this release. Signing out of a congregation's portal used to land on generic platform chrome with no way back to that congregation's own identity; the directory's Members/Households/Parishes switcher was three separately-drawn buttons rather than a real control; and the whole portal sat in a narrow centered column with wide empty margins on anything wider than a laptop.

**Changes:**
- Signing out from inside a congregation's portal now lands on that congregation's own public site, not the generic platform home.
- Members / Households / Parishes now render as a single connected button group with an icon per destination, instead of three loose buttons.
- The portal's header, main content, and footer now use noticeably more of a wide screen's width.
- The officers tool is now visible in the portal's tile grid and persistent menu (previously reachable only by typing its URL directly) for anyone with permission to use it.

**Testing:**
- [x] Full unit suite, all four tripwires, and a full production build — clean
- [x] `e2e/branded-signin.spec.ts` (CLAUDE.md's mandatory smoke for any sign-in-page change) — 4/4 passing against a real dev server, including a full credentials sign-in and a full MFA-verified sign-in
- [x] Verified live in a real browser at both desktop and 360px: the wider shell, the button group, the officers tile, and the sign-out redirect

### Verified

Full unit suite green (2202 passed, 304 skipped without a live DB connection), typecheck/build/all four tripwires clean. `getOrgProfileForFooter` verified against a real Postgres connection with a cross-organization isolation proof (an org cannot read another org's contact info). The new footer and card treatment were verified to never render on an access-denied, ended-relationship, or not-found page — those stay byte-identical to platform default, matching the existing brand/nav gating discipline. Officer-terms administration includes an application-layer regression test proving a second, non-consecutive term for the same person and office is recorded independently of the first, rather than silently overwriting it — the same failure mode a prior schema-level bug (F22) once produced, now proven closed at this new layer too. The officer-terms roster was verified live in a real browser at 360px, where a real column-overflow issue was found and fixed.

**Still ahead of a real deploy:** `org_portal.chrome_v3` and `org_portal.officers` both ship seeded off — none of this is live for a real congregation yet. Nav dropdown grouping remains deferred, not built.
