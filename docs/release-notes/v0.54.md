## 0.54.4 — 2026-11-02

### Maintenance: Routine software updates

**Value:** PresbyPortal is built on open-source libraries, and their authors publish fixes and small improvements every week. This release takes 40 of the 41 updates that were waiting. Nothing about how the portal looks or works changes for you.

#### What's New

**For members, administrators and visitors.** Nothing. No screens, wording, emails, permissions or settings changed, and no help page needed an edit. Pages, dialogs, menus, icons and sign-in (including two-factor sign-in) were checked at phone width in light and dark mode.

**For the operator.**
- **Security advisories.** High-severity advisories in our tooling dropped from 3 to 2: the testing tool `vite` is no longer flagged. The remaining 2 high and 23 moderate are in supporting tools that do not ship to the live site. Fixing them needs updates that cannot be taken safely in a routine release, so they are tracked in the backlog.
- **One update held back on purpose.** The form library (`react-hook-form`) stays at 7.86.0. Its newer versions change how a form behaves if someone edits it before the page has finished loading, which is the reason every form is locked until the page is ready. We left it where it is until that is decided, and pinned it so it cannot move on its own.
- **The automatic update pull request (#71) was closed.** Its package list did not install cleanly and it could not be fully tested. The same updates were applied here and run through the full test suites instead. Four packages (`otplib`, `resend`, `lucide-react`, `ws`) installed one patch or minor version newer than that pull request named, and were tested as installed.
- **For anyone running the portal locally in developer mode.** A confirmation message (for example, after changing an email address) now appears twice. It still appears once on the live site. This is a harmless side effect of the notification library's update.

#### Known Limitations

- 2 high and 23 moderate advisories remain in supporting tools.
- The form library is held at 7.86.0 until it is ruled on.

**Technical:** Next 16.4.3, React 19.3.1, Playwright 1.64.1, `@neondatabase/serverless` 1.2.0, and 35 others; `react-hook-form` pinned exactly in `package.json` and ignored in `.github/dependabot.yml`. Work-log `2026-11-01-deps-minor-patch`.

## 0.54.3 — 2026-11-02

### Bug fix: a restored person could never be invited again

**What happened.** If an administrator archived someone who had an open sign-in invitation, and that person then opened the invitation link, the invitation was blocked for good. After the administrator restored them, their record still said "This invitation couldn't be completed because … connection to … has ended", with no button, and they could not be invited from the product again. This could only happen since 0.54.0, when Restore arrived.

**What changed.**
- **Archiving cancels an open invitation.** The archive dialog already said "It will stop working"; now it does. It reads: "An invitation to {name} is still open. It will stop working, and restoring them will not turn it back on." The person sees "This link isn't active" if they open it, and is no longer offered "Accept the invitation".
- **Restoring does not bring an old invitation back.** Open the person's record and choose "Send invitation" to send a new one. **This is a change:** before, an invitation the person had never opened kept working after you archived and restored them. Now it stops at archive.
- **No record of someone who is connected again shows "has ended".** This also clears the same dead end after undoing a participant's removal.

Every cancellation is recorded with who archived the person.

**Help:** `adding-people` and `sign-in-invitations` say that archiving cancels an invitation and restoring does not bring it back. `roles-who-can-do-what` was re-walked against this fix; `using-the-directory` and `what-presbyportal-does` were walked against 0.54.0.

**For the operator.** No migration. Production had no sign-in invitations and no stuck records when counted on 2026-11-02, so there is nothing to clean up.

**Technical:** DECISION-315 (amends DECISION-235); F417; `src/lib/community-engagement.ts` (`archivePerson`'s required side-effect argument), `src/lib/onboarding/org-invite.ts` (`revokeOpenSignInInvitationInTx`, `readStates`). Work-log `2026-11-02-archive-revokes-invite`.

## 0.54.2 — 2026-11-02

### Bug fix: builds no longer fail on a bad answer from Google Fonts

**What happened.** Every build fetched the nine typefaces from Google Fonts. About one answer in sixty comes back in a shape the Next.js build tool cannot read (vercel/next.js#99114, not fixed upstream), and the whole build then fails. With nine fonts, many builds hit one. Recent production builds failed this way (0.54.0 among them), so production kept serving an older release, and test runs failed at random.

**What changed.**
- **The fonts now ship with the app.** Each typeface (Inter, plus the eight in the four congregation font pairings) is a file in the repository, cut from the families' own published sources. They cover the same alphabets Google served: Latin with accents, Vietnamese, Greek and Cyrillic, wherever the family has them. Text looks the same.
- **Fonts load differently.** Every page preloads only Inter; a congregation's pages also download its own pairing, and no other. Sign-in drops from 308 KB of fonts to 181 KB. The help pages grow from 48 KB to 181 KB, a congregation page from 308 KB to 389 KB, and a branded public website from 308 KB to 478 KB, because each font now carries every alphabet in one file. Each file is downloaded once and then cached. Pages do not jump when the fonts arrive.
- **Two fonts are renamed inside their files.** Their licence reserves their names for unmodified copies, so Lora and Source Sans 3 appear as "PP Classic Serif" and "PP Classic Sans" if you inspect the font in a browser. They look identical.
- **Known cost.** A congregation's public website preloads Inter, which it does not use (181 KB of its 478 KB). Removing it is tracked.

**For administrators and developers.** If you inspect styles in the browser, font names now read like `classicHeading` instead of "Lora". Nothing else changes.

**Tests.** The end-to-end browser tests now run as four parallel jobs, each on its own database, so a run takes about 35 minutes instead of over 75. The contact-form tests run once per run. A test fails if anything imports fonts from Google again, and another checks that every font file still covers each alphabet.

**For the operator.** No migration. Once this release deploys, production moves to the current code. The migrations for 0.51 to 0.54 were applied to production on 2026-11-01. Before the deploy, set the contact form's Production variables (`docs/deployment.md` "Help contact form (0083)").

**Technical:** `src/lib/brand/fonts.ts` and `src/app/layout.tsx` use `next/font/local`; `src/lib/brand/font-files/` holds the fonts, their OFL licences and the rebuild kit; `font-coverage.test.ts`; `.github/workflows/e2e.yml` (`--shard=i/4`). Work-logs `2026-11-01-self-host-fonts` and `2026-11-01-e2e-shard`.

## 0.54.0 — 2026-11-01

### Feature: Who counts as a member, and what each kind of person can see

**Value:** Until now a visitor who signed in could read your whole member directory, because the system treated everyone with a current record as a member. And an administrator had no screen to say that someone was only visiting, had gone quiet, or had moved away, so those people either stayed in the directory or vanished from every list. This release gives each person one clear standing, shows it to administrators, and makes the directory follow it.

#### What's New

**The calendar for everyone with a current record, the directory for members.** Everyone with a current record at your congregation, including visitors and people marked inactive or moved away, can now see the calendar through a new Calendar viewer role, once they have a connected sign-in and your congregation uses the calendar. For people who already held the Member role, nothing changes.

The directory is different. A visitor, or a person marked inactive or moved away who is not on the roll, no longer holds the member directory permission. If they open the directory it says "You don't have permission to view the directory." The Directory tile is still on their home page for now; it just leads to that sentence. People on the roll stay listed whatever their engagement. Regular attenders and staff records are unchanged.

**Two groups and a role changed.**
- Every congregation gains a group called "All Current Records" and a role called "Calendar viewer" (it can see the calendar and nothing else). The role cannot be edited. The Roles page now lists six roles.
- "Active Membership" now holds only people on the current roll, regular attenders and staff records. Until now it also held visitors and people marked inactive or moved away.
- A role you tied to Active Membership now reaches only those people. A role you tied to All Current Records reaches everyone with a current record.

**The engagement editor.** On a person's record, administrators who can manage people can now set how the person is connected to the congregation, in four plain choices: Visitor, Regular attender, Inactive and Moved away.
- It decides who appears in the directory and what a connected sign-in can see.
- It is for your congregation's own care. It is never reported to the presbytery, and it does not change the membership roll.
- A staff record cannot be switched into or out of this, and a person on the roll cannot be marked as a visitor.
- Marking someone a regular attender lists them in the directory. Where "Connect people when they sign in" is on, it also lets them be connected to their record by signing in with an address you have on file. The dialog says this before you confirm. We record every change; we do not block it.
- You can also correct a first visit date and how someone heard about you.

**Signing in and invitations.** Signing in no longer connects visitors or people marked inactive or moved away to their record; an invitation still does. In 0.48 we said "We ask you to confirm before sending to a visitor" and "We plan to give visitors a narrower view in a later release". Both are replaced: the narrower view has arrived, so that confirmation is gone. The confirmation for a person marked do-not-contact stays.

**Archive and restore.** Administrators can archive a visitor or a person marked inactive or moved away, from their row or their record.
- The record is kept and nothing is deleted. The person moves to the Former list, and Restore puts them back from there, from their record, or from the match step when you add someone who was archived.
- A connected sign-in will not reach the congregation until the person is restored, and an open invitation to them stops working.
- Someone who still holds an office, a role or a staff position has to have that ended first. Members on the roll, participants and staff are not archived this way, and you cannot archive yourself.

**The database now guards the rosters.** The database now refuses the application's own database access writing the Session, Board of Deacons and Moderator of the Board of Deacons rosters directly. Those rosters fill only from officer terms. This closes the gap announced in 0.45. Until now it was caught by review and by the change records, not prevented. Someone with owner-level access to the database could still write them, and a tenant can still create an empty automatic group in a congregation that lacks one; those are known and recorded.

**Smaller changes.**
- A new Inactive view in Community, so people marked inactive or moved away no longer vanish.
- People on the roll who are marked inactive or moved away carry that badge in lists.
- On a phone, the Community views scroll to the active one.
- The "Everyone" list no longer says "No one yet" when only visitors exist.
- Parish household rows now tag inactive and moved-away people as such (they were tagged "Listed"). Moderators of the Board of Deacons, people who can see directory-hidden details and people who manage people can see those tags.
- "All Current Records" appears in Reimbursement settings as an extra switch, off by default. Requests charged to it go to the treasurer.
- The Groups list's "Managed from" text changed to match.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `people.manage` | Set engagement, archive, restore and correct a first visit (existing key; no new key) |
| `events.view` | The calendar; the new Calendar viewer role holds only this |
| `directory.view` | The member directory; no longer held by visitors, or by inactive or moved-away people who are not on the roll |

There is no new platform flag and no new per-congregation toggle.

#### New Routes

None. The Inactive view is a new view of the existing Community page.

**Help:** `adding-people`, `sign-in-invitations`, `roles-who-can-do-what`, `events-and-the-calendar`, `using-the-directory` and `what-presbyportal-does` were edited to match. They have not yet had their final read-through on the development database, so their "verified in" release is unchanged.

**For the operator.** Migration `0066` takes effect when it is applied, not when the code is deployed, because permissions are worked out on every request. The runbook is `docs/deployment.md` "Pre-deploy runbook: 0066".
1. Take a snapshot of production. Re-run the read-only counts P1 to P12 in the runbook, and read P2 and P5 on deploy day. P2 is the number of signed-in people who lose the directory: it was 0 on production as of 2026-10-31, so nobody loses anything at apply. P5 is the number of congregations whose people would newly gain the calendar; it was 0 for every real congregation on both databases on 2026-10-31. If P5 is above 0 on deploy day, tell those congregations.
2. Apply `0066` to production first, then deploy the code. The old code keeps working against the new database. The migration only goes forward; nothing it creates is ever deleted.
3. Create no organization between the apply and the deploy. If one is created, re-run the `backfill-calendar-viewer` block. After the apply, P11 must read 0 and 0.
4. Apply to `development` first, and run `scripts/test-rls.sql` and `scripts/parishes/test-rls-68.sql` there.

**Known limits, recorded and accepted.**
- Marking someone a regular attender lists them and can make them eligible to be connected when they sign in with an address on file. We detect this through the change records; we do not prevent it.
- A visitor's Directory tile still leads to a polite refusal, because home-page tiles do not yet know about permissions.
- The system cannot yet stop a visitor being recorded as an elder or deacon (a separate bug, already tracked), and marking a seated person who is not on the roll as a visitor is allowed.
- The invitation help and card wording say "isn't listed in the member directory", which is slightly too broad for a staff record.
- The Moderator of the Board of Deacons cannot be sent a sign-in invitation by anyone (they are refused; signing in with a second factor still connects them). No access is gained; a fix is scheduled for later.
- Treasury has its own copy of the member rule, which agrees with this release for every value the screens can store. It will be pointed at the shared rule in a later release.
- A last hands-on walk of the visitor and archived-person pages on the development database has not been done yet.
