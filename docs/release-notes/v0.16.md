## 0.16.0 — 2026-08-26

### Feature: Tenant-facing branding management

**Value:** Branding functionally belongs to the organization, not the platform. Congregations previously had no way to set their own seed color, type pairing, or logo — every brand change required a platform admin. This gives that control to the organization itself, through a new self-service role rather than by overloading an already-busy existing office.

#### What's New

- A new "Branding" tool in the Organization Administration hub lets an authorized org admin set their congregation's seed color, curated type pairing, logo, and light-only toggle.
- A new `brand_admin` role carries this single capability — deliberately not bound to the Stated Clerk office, which already carries six other permissions.
- The platform admin's own brand form and "neutralize" override remain unchanged, as a break-glass path.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `branding.manage` | Editing a congregation's own brand at `/o/<slug>/admin/branding` |

#### New Routes

- `GET/POST /o/<slug>/admin/branding` — the tenant brand editor

### Feature: Organization Administration hub

**Value:** The main portal page was becoming a mix of day-to-day tools and org-setup tasks. This splits the two: the portal home stays focused on the work a congregation does every day, and a new hub gathers everything about setting the organization up in one place.

#### What's New

- A new `/o/<slug>/admin` page lists every setup-category tool — Members, Roles, Officers, Features, Branding — as a flat card grid, reached from a new "Administration" entry in the portal's persistent menu.
- The hub performs no permission check of its own: every enabled tool shows regardless of the viewer's own grants, and each destination page remains the sole authority on what a click can actually do — the same division of labor the rest of the portal already follows.
- The already-shipped Features page is discoverable through the UI for the first time.

### Feature: Portal visual modernization pass

**Value:** Direct feedback that the portal felt flat next to presby's own public site — this brings some of that site's boldness and depth into the portal, while keeping the portal easy and uncluttered to use.

#### What's New

- The portal home's greeting gets a bordered, accented treatment rather than a flat block of color.
- Tool tiles across the home page and admin hub are now elevated cards with a soft shadow that lifts on hover, rounder corners, and a small colored icon badge — replacing an earlier full-bleed color treatment that read as flat rather than modern.
- The active item in the portal's persistent menu now carries a visible accent underline.
- A subtle one-time fade-in plays when the portal home's greeting first loads (respects a visitor's reduced-motion preference).

### Feature: Record a roll action for an existing member from the Edit screen

**Value:** Until now, the only place a roll action (profession of faith, restoration, reaffirmation, and similar) could originate was the "Add a person" wizard — a clerk had no way to record one of these for someone who already exists in the roll without re-running the new-person flow. This adds a second, dedicated entry point on the Edit-person screen for exactly that.

#### What's New

- A new "Record a roll action" section on `/o/<slug>/admin/members/<id>/edit` lets a `roll.propose` holder choose a kind, an effective date, and an optional minute reference, and submit it as a new pending roll action — same approval discipline as today: it still needs a `roll.approve` holder to approve it on the pending worklist before it takes effect.
- If a roll action is already pending review for that person, the section shows a non-blocking notice naming it — the clerk can still submit another action; nothing is silently blocked.
- **Death and transfer-out are intentionally NOT offered here yet.** This increment ships only the roll-*gain* kinds (profession of faith, reaffirmation, restoration, certificate received, other gain, and enrollment onto the baptized/affiliate/other-participant rolls) — every kind whose outcome adds to a roll rather than removing someone from one. A `death`, `certificate dismissed` (transfer out), `removed by session`, or similar termination-shaped action is deliberately excluded from this screen until a companion trigger exists to correctly end an affected person's active session/deacon terms and role grants — offering it earlier could leave a deceased or transferred-out elder showing as still seated with full permissions. That trigger is tracked as its own follow-up.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `roll.propose` (existing, unchanged) | Recording a roll action from the Edit screen |

#### Flags

- `org_portal.members_roll_action_edit` (new, seeded OFF) — an independent kill switch for just this new section, layered on top of the existing `org_portal.members_create` flag/toggle pair that already gates the Edit screen itself. No new per-org toggle: both must be on for the section to render.

### Defect Fix: Status filter selection box looked like a different, greyer control than the search box beside it

**Problem:** On the directory and members pages, the "Status" dropdown looked visibly greyer than the search box right next to it, even though both were built from the same design tokens.

**Root Cause:** The dropdown is a native browser control; without one specific style property, the browser paints its own default appearance over top of the intended styling, which reads as a heavier, greyer box next to a plain text field.

**Fix:** Removed the browser's default appearance and added a matching custom arrow indicator, so the dropdown now visually matches every other field on the page.

**Testing:**
- [x] Full unit suite, typecheck, production build, and all four tripwires — clean
- [x] Verified live: computed background color was already identical before the fix: the difference was confirmed to be the browser's own control chrome, not a token mismatch

### Feature: Role definition administration

**Value:** Until now, roles could only be assigned, never created or edited in-app — a brand-new role required a support ticket and a direct database insert. This gives an org admin a real, self-service way to define what roles exist and what each one can do, closing that gap while adding new safeguards a simple assignment screen never needed.

#### What's New

- A new "Role catalog" section on `/o/<slug>/admin/roles` lets a `roles.manage` holder create a custom role, choose exactly which permissions it carries (grouped by tier — directory, financial, pastoral/demographic/medical — so the most sensitive tier is always visible, never buried), edit an existing custom role's permission set, or deactivate one.
- A "Start from a template" option can clone a stock role (e.g. Committee Chair) into the organization's own catalog.
- Editing a role's permissions shows how many people currently hold it and states plainly that the change takes effect for all of them immediately.
- Deactivating a role ends everyone's active grant of it at the same time — it's a soft action, never a hard delete, so grant history is preserved.
- Constitutional roles (like Stated Clerk) stay read-only through this screen; only custom roles can be edited or deactivated here.
- A new `roles.manage` permission (distinct from the existing role-assignment permission) is bound to a new `Role Administrator` role, not layered onto an already-busy existing office.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `roles.manage` | Creating, editing, deactivating, or adopting a template role at `/o/<slug>/admin/roles` |

#### New Routes

- `GET/POST /o/<slug>/admin/roles/new` — create a role or adopt a template
- `GET/POST /o/<slug>/admin/roles/<id>/edit` — edit a role's permissions or deactivate it

### Feature: Tiered sensitive information for members

**Value:** Congregations need to record pastoral notes, demographic information, medical/allergy information, and disability accommodations for members — but this is the most sensitive category of data in the system, and until now there was no way to enter or restrict it at all. This gives a small number of specific offices a way to record it, with each category visible only to the office that needs it.

#### What's New

- A new "Sensitive information" screen, linked from a member's Edit page, lets an authorized office record pastoral notes, demographics, medical/allergy information, or disability accommodations for that person.
- Each of the four categories is visible only to the office holding its specific permission — a viewer without any of the four permissions never sees the section at all, and a person with no data on file looks identical to one an office isn't authorized to see, so no information about who has records leaks either way.
- Pastoral notes carry their own confidentiality level (staff / pastoral / clergy-only); a clergy-only note is never shown to a non-clergy holder of the pastoral-notes permission.
- These are the same fixed set of fields the system has always modeled — not a way for a congregation to invent its own custom fields.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `pastoral_notes.manage` | Recording/viewing pastoral notes (bound to the installed pastor) |
| `demographics.manage` | Recording/viewing demographic information (bound to the Stated Clerk) |
| `medical.manage` | Recording/viewing medical/allergy information (new Member Care Administrator role) |
| `disabilities.manage` | Recording/viewing disability accommodations (new Member Care Administrator role) |

#### New Routes

- `GET/POST /o/<slug>/admin/members/<id>/edit/sensitive` — the sensitive-information screen

### Feature: Groups and committee administration

**Value:** Congregations organize a lot of their work through committees, small groups, choirs, and teams — but until now there was no way to create or manage one in the app at all, only the automatically-generated Session and Board of Deacons rosters. This gives an org admin a real way to set up and maintain those groups, while keeping the constitutional Session/Diaconate rosters completely separate and untouched by anyone through this screen.

#### What's New

- A new "Groups" tool lets an authorized office create a committee, small group, choir, or team; add or remove members with a role (chair, leader, or member) and a start date; and edit a group's name, description, and meeting time.
- Session, Board of Deacons, and Active Membership — the three rosters generated automatically — can never be edited or have a member removed through this screen; the database itself now rejects any attempt to do so, not just the interface.
- A new `groups.manage` permission gates all of this.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `groups.manage` | Creating, editing, or managing membership for a committee/small group/choir/team at `/o/<slug>/admin/groups` |

#### New Routes

- `GET/POST /o/<slug>/admin/groups` — the group list and creation entry point
- `GET /o/<slug>/admin/groups/<id>` — a group's detail page and roster
- `GET/POST /o/<slug>/admin/groups/<id>/edit` — editing a group's own details
