## 0.25.0 — 2026-09-25

### Per-congregation heading typefaces are now visible

**Background:** Each congregation's chosen visual style already paired a heading typeface with a body typeface, but only the body face was ever wired into the rendered page. Headings rendered in the body face everywhere, so half of every configured style pairing was invisible. This release finishes the wiring. Along the way, a plan to let congregations also recolour cards, menus and borders was withdrawn after inspection showed the congregation it was meant to match does not recolour those surfaces either; a congregation's colour still applies where it always has.

**Changes:**
- Page titles and section headings on a congregation's own portal, its public website, and its sign-in page (when branded) now render in that congregation's chosen heading typeface instead of the body typeface. For a congregation using the "Classic" style, that means serif headings over sans-serif body text.
- Congregations and pages without a configured style are unaffected; their headings keep the platform typeface exactly as before.
- No new setting: this uses the type pairing a congregation has already chosen in Branding settings.

## 0.25.1 — 2026-09-25

### Organization switcher meets the minimum tap-target size on every device

**Background:** On a congregation's pages the organization switcher in the header shows only a small icon next to the congregation's logo. That button had a minimum height but no minimum width, so on a phone it was about 32 pixels wide — below the 44-pixel minimum the platform's own accessibility standard requires. It had been that way since the portal header redesign in late August; an automated test had been reporting it honestly, but nobody was reading that suite.

**Changes:**
- The switcher button is now at least 44 by 44 pixels on every page and screen size, with the icon centred. Nothing else in the header moves.
- Fixed a related test that was looking for the organization's name in a place it no longer renders.

## 0.25.2 — 2026-09-25

### Creating an authorized record is now guarded as strongly as changing one

**Background:** A second external review of the lifecycle, affiliation and statistical-reporting foundation (v0.24.1) found that two table families still let a database-owner connection *create* a row that only an authorized act should produce, even though the previous release had closed the equivalent gap on *changing* one. The rule adopted here is the reviewer's: if an immutable record represents an authorized act, creation must be guarded as strongly as mutation.

**Changes:**
- A lifecycle event (a merger, a division, a dissolution) and the record of which bodies became which are now enforced as one immutable whole. A merger can no longer be recorded with no predecessors, and the application cannot attach a predecessor to any act other than the one it has declared it is recording. The one stated exception is a database connection with migration-level access, which can still append to an already-minuted act by naming it explicitly; that path is documented as an accepted limit, not a guarantee.
- A submitted statistical return and its publication to the presbytery can now only be created together, through the one sanctioned publishing path. No application connection can fabricate a "submitted" return that no clerk ever submitted. The presbytery's typed copy of the figures is held to a narrower standard for now: it must name a real publication actually addressed to that presbytery, but the database does not yet check the figures or the year against that publication. Closing that gap is tracked and waits on a change to how the copy is written.
- Withdrawing a published return is now an all-or-nothing operation at the database level rather than two independently reachable half-steps; the withdrawal function that performs it ships in a later release, and until then no withdrawal is possible through the application.
- Creating an organization's external identifier (such as its denomination PIN) is now held to the same standard as changing one.
- Documentation now states precisely what the database can prove about a submission: that it was attested at a time, not yet by whom. Recording the attesting person waits on a platform-wide identity context.
- No functional change on any screen.

## 0.25.3 — 2026-09-25

### Corners are very slightly rounder across the whole site

**Background:** The platform's corner-rounding value had been held at its original setting since the brand foundation work in August, when a comment in the stylesheet argued for leaving it alone because changing it would repaint every screen at once. That is still true — which is exactly why the change was done on its own, after the congregation-typeface work shipped, and verified by comparing before-and-after screenshots of every page rather than by an automated diff that would have flagged every corner as a failure.

**Changes:**
- Buttons, cards, menus, and dialogs everywhere — the sign-in page, your congregation's portal, and the admin dashboard alike — now use a touch more corner rounding, matching a common modern default. Nothing moved, resized, or changed shape; only the corner curve did.
- Congregations' public websites are unaffected; they carry their own corner setting.
